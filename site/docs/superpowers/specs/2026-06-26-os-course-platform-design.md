# Дизайн: переделка сайта в платформу-учебник + курс OS (MVP: CPU-планировщики)

Дата: 2026-06-26
Статус: на ревью

## Контекст и цель

Сейчас `site/` — это один курс (**GoConcurrency**): `web/` (Next.js, App Router,
MDX, Monaco) + `grader/` (Go-сервис, гоняет `go test -race` в Judge0) +
`content/` (book / topics / tasks). См. `site/ARCHITECTURE.md`.

Цель — **переделать сайт в платформу-учебник из нескольких секций (курсов)**:
текущий Go/конкурентность — одна секция, **операционные системы** — другая,
**сети** — следующая. За основу программы курса OS берём **OSTEP**
(pages.cs.wisc.edu/~remzi/OSTEP/) — только как **учебную программу и структуру**,
не как текст.

Работа разбита на две фазы, каждая деплоится самостоятельно:

- **Фаза A — каркас платформы.** Реестр курсов, реструктуризация `content/` в
  посекционное дерево, новый роутинг `/[course]/…`, витрина курсов на корне,
  перенос существующего Go-курса в секцию `/go` (контент не меняется, только
  переезжает), сохранность прогресса.
- **Фаза B — курс OS, MVP (виртуализация CPU / планировщики).** Главы-теория,
  клиентский симулятор планировщика, квизы, код-задачи через существующий грейдер.

## Сквозной принцип — контент и голос

Весь контент курса OS пишется **оригинальным русским текстом**. OSTEP — источник
**программы и структуры**, не текста. Это решает и авторские права (мы не копируем
и не переводим, а пишем своё), и качество: адаптация под рынок (примеры на
Go/бэкенде/облаке, привязка к контексту собесов «Платформа»), тон — как в
существующих главах (`content/book/*.mdx`, голос задачи 01). Никакого нейроперевода
xv6/C-специфики — переосмысляем под аудиторию.

## Главные архитектурные решения

1. **Гибрид вычислений (под ограничение по серверным ресурсам):**
   - **Симуляторы** — на клиенте (TypeScript/React, SVG/Canvas). Ноль серверной
     нагрузки, мгновенный отклик, работают даже если грейдер недоступен.
   - **Квизы/предсказания** — на клиенте (правильные ответы статически в JSON).
   - **Код-задачи** — существующий Go-грейдер, только в момент submit.

   Сервер нагружается только когда студент запускает тесты код-задачи — как сейчас.

   *Риск:* TS-симулятор и Go-эталон код-задачи могут разойтись в расчётах.
   *Митигация (опц. для MVP):* на этапе авторинга разово прогнать Go-эталон и
   сохранить «золотой трейс» в JSON, на котором юнит-тестить TS-движок. В MVP
   допустимо без этого — симулятор исследовательский, грейдинг независим.

2. **Концепция «course» вводится мягко через параметр загрузчика + префикс роутов.**
   Существующий Go-курс физически переезжает в свою секцию, но контент не меняется.

## Секция 1 — Архитектура платформы и роутинг

Дерево контента (посекционное):
```
content/
  courses.json                 # реестр: [{ id, slug, title, description, icon, order }]
  go/                          # бывш. концурренси: book/ topics/ tasks/ (переезжает целиком)
  os/                          # book/ sims/ tasks/ quizzes/ OUTLINE.md
  (net/ … позже)
```

Роутинг (App Router):
```
/                              # витрина платформы: карточки курсов + общий прогресс
/[course]                      # обзор курса (программа, прогресс)
/[course]/book/[slug]          # глава учебника (MDX + встроенные <Sim>/<Quiz>)
/[course]/sim/[slug]           # полноэкранный симулятор (OS)
/[course]/tasks/[slug]         # код-задача (Monaco + грейдер)
/[course]/topics/[n]           # топик-интро (где есть)
```

Решения по неймингу:
- Go-секция — `/go` (широкое имя, оставляет место для других Go-тем позже).
- Корень `/` — **витрина курсов** (карточки секций, общий прогресс).

Изменения в коде:
- `lib/content.ts`, `lib/progress.ts` — параметризуются `courseId` (обратная
  совместимость через дефолт `go`).
- `lib/courses.ts` (новый) — реестр курсов из `courses.json`.
- Роуты переезжают под `/[course]/…`; со старых URL (`/book`, `/topics`, `/tasks`)
  — 301-редиректы.

## Секция 2 — Модель контента курса OS

Книга OS — MDX-главы со **встроенными** интерактивными блоками:
```mdx
<Sim id="rr-scheduler" />        {/* встроенный симулятор */}
<Quiz id="sched-metrics" />      {/* встроенный квиз */}
```

**Глава** `content/os/book/<slug>.mdx` — frontmatter `{ title, slug, order, minutes }`,
тело — MDX с тегами `<Sim>`/`<Quiz>`.

**Симулятор** `content/os/sims/<id>.json`:
```json
{ "id": "rr-scheduler", "kind": "cpu-scheduler", "title": "Round Robin",
  "defaults": { "policy": "RR", "quantum": 2,
    "jobs": [{ "name": "A", "arrival": 0, "burst": 5 }] },
  "explain": "что показывает виджет" }
```
`kind` выбирает React-рендерер; логика — клиентский TS-движок (чистая функция
`(params) → trace`), без бэкенда.

**Квиз** `content/os/quizzes/<id>.json`:
```json
{ "id": "sched-metrics", "questions": [
  { "q": "...", "type": "single|multi|number",
    "options": ["..."], "answer": 2, "explain": "почему" } ] }
```

**Код-задача** `content/os/tasks/NN/` — та же модель, что сейчас (`meta.json`,
`problem`, `theory`, `solution`, `starter.go`, `solution_test.go`, `reference.go`,
`hints.json`). Ноль нового на грейдере, кроме префикса курса.

Новый код во фронте:
- `lib/os/sim/` — движки симуляции (чистый TS, по одному на `kind`; MVP — `cpu-scheduler`).
- `components/os/sim/` — рендереры (диаграмма Ганта + панель параметров + метрики).
- `components/os/Quiz.tsx` — универсальный рендерер квизов.
- `lib/os/content.ts` — загрузка sims/quizzes (degrade gracefully).

Каждый движок — изолированная чистая функция, тестируется юнит-тестами без UI.
Рендерер не знает про «физику» — только рисует `trace`.

## Секция 3 — Симулятор CPU-планировщика (центр MVP)

Движок `cpuScheduler(params) → Trace`, детерминированный:
- **Вход:** `jobs[{ name, arrival, burst }]`, `policy ∈ {FIFO, SJF, STCF, RR, MLFQ}`,
  `quantum`, (для MLFQ — число уровней / период boost).
- **Выход (`Trace`):** сегменты `{ job, start, end, queueLevel }` + метрики на джоб
  `{ turnaround, response, wait, completion }` + агрегаты (средние).

Рендерер `components/os/sim/CpuScheduler.tsx`:
- **Диаграмма Ганта** (SVG): ось времени, цветные сегменты по процессам, маркеры arrival.
- **Панель параметров:** добавить/удалить джоб, ползунки burst/arrival, выбор политики,
  квант. Пересчёт мгновенный (`useMemo`).
- **Метрики:** таблица turnaround/response/wait + средние; (бонус) сравнение политик
  side-by-side.
- **Анимация:** play прокручивает время (requestAnimationFrame), pause/step.
- **Режим предсказания:** «скрыть результат» → студент вводит метрику/порядок →
  «проверить» сверяет с трейсом. Связывает симулятор с квизом-предсказанием.

Красота/доступность: SVG масштабируется, токены из существующей `ds/`, тёмная тема.

## Секция 4 — Объём контента MVP (CPU)

По мотивам OSTEP гл. 4–9 (процессы, API, прямое исполнение, scheduling, MLFQ),
адаптировано и переписано по-русски:
- **Главы (3–4):** «Процесс и его состояния»; «Прямое исполнение с лимитами
  (trap/timer)»; «Планирование: метрики и базовые политики (FIFO/SJF/STCF/RR)»;
  «MLFQ».
- **Симулятор (1, многоликий):** `cpu-scheduler` со всеми политиками — встраивается
  в главы с разными дефолтами + полноэкранная песочница `/os/sim/scheduler`.
- **Квизы (2–3):** предсказание порядка/метрик; «почему RR плох по turnaround»;
  гейминг MLFQ.
- **Код-задачи (2–3):** «реализуй RR по сигнатуре»; «реализуй STCF»; ревью-задача
  «почему этот планировщик голодает long jobs». Грейдинг — существующий `go test`.

Объём осознанно небольшой — срез для отладки формата; затем тиражируется на
Память / Персистентность / Сети.

## Секция 5 — Грейдер, миграция, прогресс, тесты

- **Грейдер:** `taskId` теперь `"<course>/NN"`. В `runner.go`/`main.go` парсим
  префикс → ищем тесты в `CONTENT_DIR/<course>/tasks/NN`. Старый формат `"NN"` →
  дефолт `go`. Прокси `app/api/run` пробрасывает как есть.
- **Миграция Go-курса (Фаза A):** перенос `content/{book,topics,tasks}` →
  `content/go/…`; роуты `/book,/topics,/tasks` → `/go/...` с 301-редиректами;
  `lib/content.ts`/`progress.ts` получают `courseId`.
- **Прогресс:** ключи префиксуем курсом (`go:09`, `os:01`); миграция старых ключей
  (без префикса → `go:`) при чтении.
- **Тесты:** юнит-тесты движка `cpuScheduler` (golden-трейсы эталонных политик) —
  приоритетная цель TDD; smoke на загрузчики OS-контента; `validate.go` грейдера
  расширяем на `content/go/tasks`.

## Порядок реализации

1. **Фаза A** (каркас платформы) — целиком, с редиректами и сохранением прогресса.
2. **Фаза B** (OS MVP) — сначала TS-движок планировщика (TDD) и рендерер, затем
   главы/квизы/код-задачи, затем полноэкранная песочница.
