## Зачем нужен журнал

Запись на диск не атомарна: процесс может упасть на полпути и оставить данные в
полусломанном виде. Чтобы этого избежать, изменения сначала дописывают в
**write-ahead log** — журнал, который пишется строго перед самими данными. После
краша систему восстанавливают, проигрывая журнал заново.

Главный инвариант: видимыми становятся только **закоммиченные** транзакции.
Запись `commit` — это та самая точка, после которой (и только после неё)
изменения считаются устойчивыми. Почему `commit` вообще что-то гарантирует —
разбирается в главе [«fsync и долговечность»](/os/book/fsync-durability).

## Как выглядит журнал

```text
set x=1 ─┐
set y=2  ├─ транзакция T1
commit  ─┘  ← T1 зафиксирована, применяем {x:1, y:2}

set a=5 ─┐
commit  ─┘  ← T2 зафиксирована, применяем {a:5}

set b=9 ─┐
set c=3  ├─ T3: commit НЕ дописан (краш!) ✗ отбрасываем
   ✗ CRASH
```

## Пошаговый подход

1. Заведи две map: `state` — итоговое состояние, `pending` — буфер текущей,
   ещё не зафиксированной транзакции.
2. Идём по журналу по одной записи:
   - `set` → запиши `pending[Key] = Val` (повторный set того же ключа просто
     перезатрёт прошлое значение — last write wins);
   - `commit` → перелей всё из `pending` в `state`, затем **очисти** `pending`
     (начинается новая транзакция).
3. Дошли до конца — то, что осталось в `pending` без `commit`, просто
   игнорируем (его не было в `state`).
4. Верни `state`.

## Грабли

- **Не забывай очищать `pending` после commit.** Иначе записи одной транзакции
  «протекут» в следующую и применятся даже без её собственного commit.
- **Оборванный хвост отбрасывается молча.** Не паникуй и ничего не применяй —
  это нормальный сценарий после краша.
- **Пустой журнал — это пустая map, а не `nil`.** Возвращай
  `make(map[string]int)`, чтобы вызывающему было безопасно сразу писать в неё.
- **Внутри транзакции порядок set важен,** но при применении к `state` порядок
  ключей не важен: у каждого ключа уже одно финальное значение.
