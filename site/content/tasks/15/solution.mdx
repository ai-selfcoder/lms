## Идея решения

Запускаем все реплики параллельно с общим производным отменяемым контекстом и
шлём их результаты в буферизованный канал размером `len(replicas)`. Читаем
результаты по одному: первый успех выигрывает — отменяем остальных через `cancel()`
и возвращаем. Если все упали — возвращаем последнюю ошибку. Буфер канала
гарантирует, что проигравшие реплики не утекут.

## Разбор эталона по шагам

Краевой случай и контекст:

```go
if len(replicas) == 0 {
    return "", errors.New("нет реплик для запроса")
}

ctx, cancel := context.WithCancel(ctx)
defer cancel()
```

Пустой список — явная ошибка, иначе функция вернула бы `"", nil`, что
бессмысленно. `WithCancel` создаёт потомка переданного `ctx`: его отмена не
затронет родителя, но затронет все реплики. `defer cancel()` — страховка:
гарантирует отмену на любом выходе (успех, все упали, паника). Это же и
освобождает узел контекста.

Параллельный запуск:

```go
results := make(chan replicaResult, len(replicas))
for _, replica := range replicas {
    go func(r func(ctx context.Context) (string, error)) {
        value, err := r(ctx)
        results <- replicaResult{value: value, err: err}
    }(replica)
}
```

Тут два ключевых решения. Первое — канал **буферизован на `len(replicas)`**:
сколько бы реплик ни завершилось после того, как мы уже вернули ответ, всем хватит
места в буфере, и `results <- ...` никогда не заблокируется. Это и есть защита от
утечки проигравших горутин. Второе — `replica` передаётся параметром `r` (защита
от захвата переменной цикла до Go 1.22). Каждая горутина получает один и тот же
производный `ctx`.

Сбор и выбор первого успеха:

```go
var lastErr error
for i := 0; i < len(replicas); i++ {
    res := <-results
    if res.err == nil {
        cancel() // отменяем остальные реплики
        return res.value, nil
    }
    lastErr = res.err
}
return "", lastErr
```

Читаем ровно `len(replicas)` результатов (или выходим раньше). Первый с `err == nil`
выигрывает: `cancel()` рассылает отмену остальным репликам (они слушают
`ctx.Done()` и сворачиваются), и мы сразу возвращаем значение. `defer cancel()` тут
не лишний — двойной `cancel` безопасен и идемпотентен, но явный вызов важен, чтобы
отмена случилась **до** возврата, не дожидаясь разворота `defer`.

Если результат с ошибкой — запоминаем в `lastErr` и читаем следующий. Цикл
дочитывает все результаты только в случае, когда **никто** не успел; тогда
возвращаем `lastErr` — сигнал «все реплики упали». Тест `TestQueryReplicasAllFail`
проверяет именно этот путь.

## Почему именно так

- **Нет утечек горутин.** Буфер `len(replicas)` принимает результаты всех реплик,
  даже проигравших и завершившихся после нашего возврата. Никто не виснет на
  отправке. `TestQueryReplicasFirstWins` дополнительно проверяет, что обе медленные
  реплики **увидели отмену** (счётчик `slowCancelled == 2`).
- **Быстрый ответ.** Возвращаемся по первому успеху, не дожидаясь медленных —
  тест проверяет, что общее время близко к быстрой реплике (порог 1.5 с при
  медленных по 3 с).
- **Отмена проигравших.** `cancel()` закрывает `ctx.Done()`; реплики, слушающие
  его в `select`, прекращают работу и не жгут ресурсы.
- **`-race` чист.** Координация — через канал и контекст; общей изменяемой памяти
  нет. `lastErr` пишется только в основной горутине.

## Альтернативы и их минусы

- **`errgroup` / `sync.WaitGroup`.** `errgroup` отменяет по первой *ошибке*, а нам
  нужен первый *успех* — семантика обратная, придётся инвертировать (возвращать
  ошибку при успехе). Костыльно. Ручной сбор через канал чище под эту задачу.
- **`sync.Once` + указатель на результат.** Первый успех пишет результат под `Once`
  и дёргает `cancel`. Работает, но нужен мьютекс/атомик на результат и отдельная
  синхронизация ожидания — больше движущихся частей, чем у канала.
- **Небуферизованный канал + чтение всех до конца.** Можно не возвращаться сразу, а
  дочитать все результаты в фоне. Но тогда мы либо ждём всех (теряем смысл «первый
  побеждает»), либо плодим горутину-дренаж — лишняя сложность. Буфер проще.
- **`reflect.Select`.** Незачем — у нас фиксированный канал, рефлексия только
  замедлит.

## Сложность и поведение под нагрузкой

Горутин — `len(replicas)`, память — O(N) на буфер канала и горутины. Узкое место —
самая быстрая реплика: общая латентность ≈ `min(latency_i)`, что и есть цель
паттерна (срезание хвоста p99). Цена — N-кратная нагрузка на бэкенды (все реплики
делают работу), поэтому в проде hedging часто запускают не сразу все, а с задержкой
(«послать вторую копию, только если первая не ответила за X мс»). Аллокации —
канал и N `replicaResult`, копейки.

## Что спросит интервьюер дальше

- **«Почему канал буферизован на `len(replicas)`?»** Чтобы проигравшие реплики не
  зависли на отправке после нашего возврата — иначе утечка горутин.
- **«Зачем и `cancel()` в цикле, и `defer cancel()`?»** Явный — чтобы отменить
  *до* возврата; `defer` — страховка на путях ошибки/паники. `cancel` идемпотентен.
- **«Что если все реплики упадут?»** Цикл дочитает все ошибки и вернёт последнюю.
- **«Как сделать настоящий hedging без N-кратной нагрузки?»** Слать копии с
  задержкой: вторую реплику дёргать, только если первая молчит дольше порога.
- **«Сохранится ли отмена медленных, если они не слушают `ctx`?»** Нет — `cancel`
  лишь закрывает `Done()`; реплика обязана сама реагировать на `ctx.Done()`.
