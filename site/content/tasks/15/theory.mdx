## Зачем это на собесе

Паттерн «hedged request» / «first wins»: шлём один и тот же запрос в несколько
реплик параллельно и берём ответ первой успешной, остальные отменяем. Так срезают
хвостовые задержки (p99) при чтении из реплицированных хранилищ. Интервьюер
проверяет связку [context](/book/context) для отмены проигравших + правильный
размер канала результатов, чтобы **не утекли горутины** проигравших реплик.

## Что нужно знать

Все реплики стартуют с **производным отменяемым контекстом**:
`ctx, cancel := context.WithCancel(ctx)`. По первому успеху вызываем `cancel()` —
закрывается `ctx.Done()`, и реплики, которые это слушают, прекращают работу.

Самое тонкое — **размер канала результатов**. Горутины проигравших реплик всё равно
когда-то завершатся и попытаются записать результат. Если канал небуферизованный, а
основная функция уже вернулась и не читает — они зависнут на отправке навсегда.
Лечится буфером на `len(replicas)`: места хватит всем, отправка никогда не
заблокируется.

```go
results := make(chan replicaResult, len(replicas)) // буфер = числу реплик
for _, r := range replicas {
    go func(r ...) { v, err := r(ctx); results <- replicaResult{v, err} }(r)
}
```

Третье — **логика «первый успех»**: читаем результаты по одному; первый без ошибки
выигрывает (`cancel()` + return), а если все с ошибкой — возвращаем последнюю.
Подробнее — [context](/book/context), [каналы](/book/channels).

## Идиомы и паттерны

- **`context.WithCancel(ctx)` + `defer cancel()`.** `defer` гарантирует отмену на
  любом пути выхода — и при успехе, и когда все упали.
- **Буферизованный канал результатов `len(replicas)`** — ключ к отсутствию утечек:
  проигравшие всегда смогут записать и завершиться.
- **`cancel()` по первому успеху** — broadcast отмены остальным репликам.
- **Подсчёт результатов циклом `for i := 0; i < len(replicas)`** — чтобы понять,
  что упали все, и вернуть ошибку.

## Подводные камни

- **Небуферизованный канал результатов.** Основная функция вернулась по первому
  успеху и больше не читает; проигравшие реплики, завершившись, виснут на
  `results <- ...` навсегда — утечка горутин (см.
  [утечки и гонки](/book/leaks-and-races)).

  ```go
  // как НЕ надо
  results := make(chan replicaResult) // без буфера → проигравшие зависнут на отправке
  ```

- **Забыли `defer cancel()`.** Если выйти по первому успеху, не отменив контекст,
  остальные реплики продолжат работать впустую (а контекст утечёт). `defer cancel()`
  закрывает оба сценария.

- **Не прокинули `ctx` в реплику.** Реплика должна получить производный отменяемый
  `ctx`, иначе `cancel()` ничего не остановит — тест считает отменённые реплики и
  упадёт, если они не увидели отмену.

- **Возврат при первой ошибке.** Ошибка одной реплики — не повод сдаваться: надо
  ждать остальных. Возвращать ошибку только когда **все** упали.

- **Пустой список реплик.** Часто забывают — без проверки цикл не выполнится, и
  функция вернёт пустую строку с `nil` ошибкой (некорректно). Нужна явная ошибка.

## Как подступиться

1. Обработай `len(replicas) == 0` → верни ошибку.
2. `ctx, cancel := context.WithCancel(ctx)`, `defer cancel()`.
3. `results := make(chan replicaResult, len(replicas))`. Запусти горутину на каждую
   реплику: `v, err := r(ctx); results <- ...` (передай `replica` параметром).
4. Цикл `for i := 0; i < len(replicas); i++`: читай результат; если `err == nil` —
   `cancel()` и `return value, nil`; иначе запомни ошибку.
5. После цикла верни последнюю ошибку (все упали).

Дальше — решай сам. Эталон открывай после.
