## Зачем это на собесе

Шина событий, брокер сообщений, event bus внутри сервиса — везде один и тот же
вопрос: сообщение пришло, кому его отдать? Маршрутизация по тегу/топику и
fan-out нескольким подписчикам — хлеб любой реактивной архитектуры. Здесь
проверяют, умеешь ли ты держать таблицу подписчиков потокобезопасно, доставлять
сообщение только подходящим обработчикам и при этом **не держать мьютекс во
время вызова чужого кода**.

## Что нужно знать

`map[string][]handler` — естественная структура: тег → список обработчиков. Карта
в Go **не потокобезопасна**, конкурентная запись/чтение даёт panic
(`concurrent map writes`) или гонку, поэтому доступ закрывают мьютексом. См.
[sync-примитивы](/book/sync-primitives).

Fan-out — это [паттерн](/book/patterns) «один вход, много выходов»: одно
сообщение разлетается по всем подписчикам тега.

Ключевая тонкость — **не вызывать обработчики под мьютексом**. Обработчик это
чужой код: он может быть медленным, заблокироваться или сам дёрнуть
`Subscribe` → дедлок. Поэтому под локом только снимают слепок списка, а вызывают
уже без лока:

```go
mu.Lock()
handlers := subs[tag] // читаем под локом
mu.Unlock()
for _, h := range handlers { // вызываем без лока
    h(msg)
}
```

## Идиомы и паттерны

- **Копия среза перед вызовом** — `cp := make(...); copy(cp, handlers)`. Слайс
  `subs[tag]` разделяет подложку с картой; если параллельный `Subscribe`
  сделает `append`, он может перевыделить или (хуже) переписать ту же подложку.
  Копия даёт стабильный снимок без удержания лока — это и есть «routing без
  дублирования данных»: данные сообщения мы не копируем, копируем лишь дешёвый
  список указателей на функции.
- **Единый диспетчер-горутина** + буферизованный входной канал — `Publish`
  только кладёт в канал, доставкой занимается одна горутина через
  `for msg := range in`.
- **`close(in)` как сигнал завершения** + `sync.WaitGroup` для дренажа: закрытый
  канал дочитывается до конца, и только потом `range` завершается.
- **`sync.Once`** вокруг `close`, чтобы повторный `Stop` не паниковал.

## Подводные камни

- **Вызов хендлеров под мьютексом.** Медленный или блокирующийся подписчик
  застопорит всю шину, а рекурсивный `Subscribe` из хендлера — дедлок на
  невозвратном мьютексе.

  ```go
  // как НЕ надо
  mu.Lock()
  for _, h := range subs[tag] { h(msg) } // лок держится весь fan-out
  mu.Unlock()
  ```

- **Гонка на срезе подписчиков.** Итерация по `subs[tag]` без копии, пока другой
  поток делает `append`, — классическая гонка слайса (см.
  [утечки и гонки](/book/leaks-and-races)).
- **Неизвестный тег.** `subs["unknown"]` для отсутствующего ключа возвращает
  `nil`-срез — итерация по нему просто пустая, паники нет. Главное — не делать
  лишних проверок и не падать.
- **Потеря сообщений при `Stop`.** Если просто грохнуть диспетчер, сообщения в
  буфере канала пропадут. Условие требует **дренировать** очередь — закрыть
  вход и дать `range` дочитать остаток.

## Как подступиться

1. Структура: `mu sync.Mutex`, `subs map[string][]func(Message)`, буферизованный
   `in chan Message`, `wg`, `once`.
2. `Subscribe`: под локом `subs[tag] = append(subs[tag], handler)`.
3. `Publish`: `in <- msg` (буфер скрадывает всплески).
4. `Start`: одна горутина `for msg := range in { dispatch(msg) }`, обёрнутая в
   `wg`.
5. `dispatch`: под локом снять копию `subs[msg.Tag]`, отпустить лок, вызвать
   каждый хендлер.
6. `Stop`: `once.Do(close(in))` + `wg.Wait()` — это дренирует остаток и
   завершает диспетчер.
7. Проверь: неизвестный тег ничего не ломает; два подписчика на один тег оба
   получают каждое сообщение.
