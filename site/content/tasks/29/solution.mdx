## Идея решения

Таблица подписчиков `map[string][]handler` под мьютексом, одна
горутина-диспетчер тянет сообщения из буферизованного канала и для каждого
делает fan-out: снимает под локом **копию** списка обработчиков нужного тега,
отпускает лок и вызывает их уже без него. `Stop` закрывает входной канал — это и
дренирует остаток очереди, и завершает диспетчер.

## Разбор эталона по шагам

Структура держит карту, входной канал и примитивы завершения:

```go
type Router struct {
	mu   sync.Mutex
	subs map[string][]func(Message)

	in   chan Message
	done chan struct{}
	wg   sync.WaitGroup
	once sync.Once
}
```

`in` — буферизованный (`make(chan Message, 1024)`), чтобы `Publish` не упирался
в скорость диспетчера на всплесках.

`Subscribe` просто дописывает обработчик под локом:

```go
func (r *Router) Subscribe(tag string, handler func(Message)) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.subs[tag] = append(r.subs[tag], handler)
}
```

Несколько вызовов с одним тегом накапливают список — отсюда поддержка нескольких
подписчиков на тег (тест `MultipleSubscribersPerTag`).

`Publish` ничего не маршрутизирует сам — только кладёт в канал:

```go
func (r *Router) Publish(msg Message) {
	r.in <- msg
}
```

`Start` поднимает единственный диспетчер:

```go
func (r *Router) Start() {
	r.wg.Add(1)
	go func() {
		defer r.wg.Done()
		for msg := range r.in {
			r.dispatch(msg)
		}
	}()
}
```

`for msg := range r.in` — диспетчер живёт, пока канал открыт; `close(in)` в
`Stop` завершит цикл, но **только после** того, как буфер дочитан до конца.
Именно это даёт «дренаж очереди».

Сердце маршрутизации — `dispatch`:

```go
func (r *Router) dispatch(msg Message) {
	r.mu.Lock()
	handlers := r.subs[msg.Tag]
	cp := make([]func(Message), len(handlers))
	copy(cp, handlers)
	r.mu.Unlock()

	for _, h := range cp {
		h(msg)
	}
}
```

Три важных момента:

- **`r.subs[msg.Tag]` для неизвестного тега** вернёт `nil`-срез. `len(nil) == 0`,
  копия пустая, цикл не выполняется — сообщение тихо отброшено, без паники. Ровно
  как требует условие.
- **Копия среза `cp`.** Зачем не итерировать прямо по `handlers`? Слайс из карты
  делит подложку с тем, что хранится в `subs[tag]`. Если параллельно вызовут
  `Subscribe` с тем же тегом, `append` может перевыделить массив или переписать
  ячейки — итерация словит гонку. Копия — это стабильный снимок на момент под
  локом. И заметьте: копируем мы только список **указателей на функции**, а не
  сам `Payload` сообщения — никакого дублирования данных, маршрутизация дешёвая.
- **Лок отпущен до вызовов `h(msg)`.** Обработчик — чужой код: медленный,
  блокирующийся, способный сам позвать `Subscribe`. Держи мы лок во время
  fan-out — рекурсивный `Subscribe` дал бы дедлок, а медленный хендлер
  застопорил бы всю шину.

`Stop` закрывает вход и ждёт диспетчер:

```go
func (r *Router) Stop() {
	r.once.Do(func() {
		close(r.in)
	})
	r.wg.Wait()
}
```

`close(in)` не теряет буферизованные сообщения: `range` дочитывает их все, потом
видит закрытие и выходит. `wg.Wait()` гарантирует, что после `Stop` диспетчер
завершён, а все сообщения доставлены — поэтому тест может проверять счётчики
сразу после `Stop`. `sync.Once` защищает от двойного `close`.

## Почему именно так

- **Нет гонок на карте и срезах.** Любой доступ к `subs` — под `mu`; обработчики
  зовутся по копии вне лока. Под `-race` чисто.
- **Нет дедлока.** Лок не удерживается во время чужого кода — `Subscribe` из
  хендлера безопасен.
- **Нет потери сообщений.** `close`+дренаж+`Wait` гарантируют доставку всего, что
  попало в канал до `Stop`. Тест проверяет точные счётчики (`metrics == 7` и т.д.).

## Альтернативы и их минусы

- **Канал на каждого подписчика вместо `func`.** Подписчик — это `chan Message`,
  диспетчер пишет в каналы тега. Гибче (бэкпрешер per-subscriber), но появляется
  вопрос «что если подписчик не читает» — блокировка диспетчера или нужен
  `select { default: drop }`. Для синхронных хендлеров вариант с `func` проще.
- **`sync.RWMutex`.** `Subscribe` редок, `dispatch` част — соблазн читать под
  `RLock`. Выигрыш есть при read-heavy и многих диспетчерах, но здесь диспетчер
  один, contention нет, а `RWMutex` дороже на запись. Простой `Mutex` уместнее.
- **`sync.Map`.** Подходит для «много ключей, редкая запись», но значение —
  растущий срез, который всё равно надо защищать при `append`; выигрыша мало,
  читаемость хуже.
- **Fan-out в горутину на хендлер.** `go h(msg)` распараллелит доставку, но
  ломает порядок и плодит горутины; для медленных хендлеров иногда нужно, но по
  умолчанию это усложнение без причины.

## Сложность и поведение под нагрузкой

`Publish` — O(1) (запись в канал). `dispatch` — O(k) на копию и вызовы, где k —
число подписчиков тега; аллокация копии на каждое сообщение (одна на доставку).
Узкое место — единственный диспетчер: всё сериализуется на нём. Под высокой
нагрузкой масштабируют либо несколькими диспетчерами (по шардам тегов), либо
параллельным fan-out. Буфер `in` сглаживает всплески, но при переполнении
`Publish` начнёт блокироваться — это обратное давление.

## Что спросит интервьюер дальше

- **«Как сделать отписку (`Unsubscribe`)?»** Хранить хендлеры с ID/токеном и
  удалять из среза под локом; для частых отписок — `map[id]handler` вместо среза.
- **«Что если хендлер паникует?»** Сейчас паника убьёт диспетчер. В проде
  оборачивают вызов в `recover`, чтобы один битый подписчик не валил шину.
- **«Как не терять сообщения при медленном подписчике?»** Per-subscriber канал с
  буфером и политикой переполнения (drop oldest / block / drop new).
- **«Зачем копия среза, нельзя без неё?»** Можно, если гарантировать, что
  `Subscribe` не вызывается параллельно с `dispatch`, — но это хрупко; копия
  снимает ограничение почти бесплатно.
- **«Почему один диспетчер, а не пул?»** Простота и порядок. Пул нужен, когда
  доставка — узкое место; тогда шардируют по тегу, чтобы сохранить порядок внутри
  тега.

## В проде

Эта схема — миниатюра внутренних event bus и брокеров. `Subscribe`/`Publish` с
маршрутизацией по топику — модель NATS, Redis Pub/Sub, Kafka (consumer groups по
топику). Внутри Go тот же приём «снять копию под локом, вызвать вне лока»
встречается в `net/http` (копирование заголовков), в наблюдателях метрик и
коллбэков. См. [паттерны](/book/patterns) и
[sync-примитивы](/book/sync-primitives).
