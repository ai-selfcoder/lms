## Зачем это на собесе

Это самый частый источник утечек в продовом Go: горутина-продьюсер пишет в
канал, а потребитель уходит раньше, прочитав не всё. Отправка в
небуферизированный канал блокируется до тех пор, пока кто-то не заберёт
значение, — и если читателя больше нет, горутина виснет на `ch <- i` навсегда.
Интервьюер проверяет, понимаешь ли ты, что *жизнь продьюсера должна быть связана
с жизнью потребителя*, и умеешь ли давать горутине канал отмены.

## Что нужно знать

Небуферизированный канал — это рандеву: отправитель и получатель встречаются в
одной точке. `ch <- v` не вернётся, пока другая горутина не сделает `<-ch`.

```go
ch := make(chan int) // ёмкость 0
ch <- 1              // заблокируется здесь, если никто не читает
```

Если потребитель прочитал часть значений и ушёл, незавершённая отправка зависает.
Горутина не собирается сборщиком мусора, пока заблокирована, — это и есть
[утечка горутины](/book/leaks-and-races): удержанный стек, неосвобождённые
ресурсы, и так до конца жизни процесса.

Ключевой инструмент — done-канал и [`select`](/book/select): он позволяет
отправке *конкурировать* с сигналом отмены, чтобы продьюсер мог выйти, а не
ждать вечно.

```go
select {
case ch <- v: // удалось отправить
case <-done:  // велели завершаться
}
```

Подробнее про рандеву и направления каналов — глава [каналы](/book/channels).

## Идиомы и паттерны

- **`select` с веткой `<-done` вокруг отправки.** Канонический способ сделать
  блокирующую операцию отменяемой: либо значение ушло, либо пришёл сигнал «хватит».
- **`defer close(ch)` в горутине-продьюсере.** Закрытие из единственной
  пишущей горутины — корректный сигнал «данных больше не будет»; потребитель
  ловит его через `v, ok := <-ch`.
- **Владелец канала закрывает канал.** Закрывает тот, кто пишет, и ровно один раз.
  Здесь это сам продьюсер через `defer`.

## Подводные камни

- **Наивная отправка без `select`.** `for i := 1; i <= n; i++ { ch <- i }` —
  если читатель прочитал 2 из 5, горутина зависнет на третьей отправке. Тест
  запускает 20 таких продьюсеров и считает горутины: утечка станет заметной.
- **Закрытие `done` из самого продьюсера.** `done` принадлежит потребителю —
  именно он решает, что читать больше не будет, и закрывает `done`. Продьюсер
  лишь *слушает* `done`.
- **Закрытие канала из потребителя.** Закрывать `ch` должен писатель. Если
  читатель закроет канал, в который ещё пишут, отправитель словит панику
  «send on closed channel».
- **Буфер как «решение».** Сделать канал буферизированным — не лечение: при
  `n` больше ёмкости отправка всё равно заблокируется. Размер буфера не должен
  определять корректность завершения.

## Как подступиться

1. Внутри `produce` создай небуферизированный `ch := make(chan int)`.
2. Запусти горутину с `defer close(ch)` — канал закроется при любом выходе.
3. В цикле `for i := 1; i <= n; i++` оберни отправку в `select` с двумя ветками:
   успешная отправка `ch <- i` и `<-done` с немедленным `return`.
4. Проверь мысленно: потребитель прочитал 2 из 5 и закрыл `done` — горутина
   проснётся в ветке `<-done` и выйдет, `ch` закроется через `defer`.
