## Идея решения

Каждую отправку оборачиваем в `select`, который слушает ещё и `done`. Пока
потребитель читает — побеждает ветка отправки; как только он закрыл `done` —
побеждает ветка отмены, и горутина выходит. `defer close(ch)` закрывает канал
при любом сценарии выхода.

## Разбор эталона по шагам

Создаём небуферизированный канал и единственную пишущую горутину:

```go
ch := make(chan int)
go func() {
	defer close(ch)
	...
}()
return ch
```

`defer close(ch)` отрабатывает и при штатном завершении цикла (отправили все `n`
значений), и при досрочном выходе по `done`. Канал закрывает писатель и ровно
один раз — потребитель спокойно ловит закрытие через `v, ok := <-ch`.

Сердце решения — цикл с отменяемой отправкой:

```go
for i := 1; i <= n; i++ {
	select {
	case ch <- i:
	case <-done:
		return
	}
}
```

`select` ждёт, какая из двух операций станет возможной первой. Если потребитель
читает — готова ветка `ch <- i`, значение уходит, идём дальше. Если потребитель
закрыл `done` — чтение из закрытого канала никогда не блокирует, ветка `<-done`
немедленно готова, и `return` завершает горутину. `defer close(ch)` срабатывает
на выходе.

Важно, что `done` имеет тип `<-chan struct{}` — продьюсер может только *читать*
сигнал, но не закрывать его. Владелец `done` — потребитель.

## Почему именно так

- **Нет утечки.** После `close(done)` любая зависшая на отправке горутина
  просыпается в ветке `<-done` и выходит. `TestProduceNoLeakOnPartialRead`
  запускает 20 продьюсеров, у каждого читает 2 из 5, затем `close(done)` и через
  `settleGoroutines` проверяет, что число горутин вернулось к baseline. Наивная
  версия без `select` оставила бы 20 зависших горутин.
- **Канал корректно закрывается.** `TestProduceClosesChannelAfterFullRead`
  читает через `for range ch` все 3 значения и ждёт закрытия — `defer close(ch)`
  это гарантирует.
- **Гонок нет.** Один писатель, закрытие из него же; `-race` чист.

## Альтернативы и их минусы

- **`context.Context` вместо `done`.** В проде чаще `select { case ch <- i:
  case <-ctx.Done(): return }`. Семантически то же самое, плюс таймауты и
  дедлайны; `done`-канал — это «ручной» контекст. Минусов почти нет, это
  естественная эволюция.
- **Буферизированный канал.** `make(chan int, n)` позволит продьюсеру записать
  всё разом и выйти. Но это работает, только если буфер вмещает всё; для
  бесконечного или большого потока не масштабируется и маскирует проблему,
  а не решает её.
- **Без отмены вообще.** Полагаться, что потребитель *всегда* дочитает до конца, —
  хрупкий контракт: любая ошибка или ранний `break` на стороне читателя даёт
  утечку.

## Сложность и поведение под нагрузкой

Одна горутина и один канал на вызов `produce`. Аллокаций минимум: канал плюс
стек горутины. `select` с двумя ветками — копеечная операция планировщика.
Завершение мгновенное: при `close(done)` все продьюсеры просыпаются на ближайшем
`select`. Масштабируется линейно по числу продьюсеров.

## Что спросит интервьюер дальше

- **«Что если убрать `select` и просто писать в канал?»** Утечка: при частичном
  чтении продьюсер навсегда зависнет на отправке.
- **«Кто должен закрывать `ch`, а кто `done`?»** `ch` — писатель (продьюсер),
  `done` — потребитель (владелец сигнала отмены).
- **«Поможет ли буфер?»** Только если он вмещает все значения; в общем случае нет.
- **«Как переписать на `context`?»** Заменить `done` на `ctx.Done()` —
  получаем отмену по таймауту и дедлайну бесплатно.
- **«Как обнаружить такую утечку в проде?»** `pprof goroutine` покажет растущее
  число горутин, застрявших на `chansend`; см. [утечки и гонки](/book/leaks-and-races).

## В проде

Этот паттерн — основа любого генератора и пайплайна в Go. Стандартный
[`context`](/book/context) реализует ровно эту идею: `ctx.Done()` —
done-канал, который закрывают при отмене. Конструкции `for-select` с веткой
отмены встречаются в `database/sql`, `net/http` (отмена запроса при разрыве
соединения) и в `errgroup`. Правило «свяжи жизнь продьюсера с потребителем
через канал отмены» — must-have для предотвращения goroutine leak.
