## Зачем это на собесе

Параллелить обработку легко; сложно — параллелить и при этом сохранить **порядок**
вывода. Стримы, транскодеры, ETL-пайплайны часто обязаны выдавать результаты в той
же последовательности, что и вход, даже если элемент #5 посчитался раньше #2.
Интервьюер проверяет, знаешь ли ты элегантный паттерн «канал каналов» (future) —
и понимаешь, почему он лучше наивного «собрать всё, потом отсортировать».

## Что нужно знать

Простой fan-out/fan-in порядок **не** сохраняет: воркеры пишут в общий выходной
канал кто когда закончил (см. [паттерны](/book/patterns)). Чтобы вернуть порядок,
нужна точка пересборки.

Элегантный приём — **future-канал на каждый вход**: канал ёмкости 1, в который
ровно один воркер положит результат. Сам future кладётся в упорядоченную очередь
**в момент поступления входа**, поэтому очередь futures хранит исходный порядок:

```go
type job struct {
    value  int
    result chan int // future: сюда воркер положит результат
}
```

Коллектор читает futures по порядку очереди и блокируется на каждом, пока тот не
готов:

```go
for j := range ordered {
    out <- <-j.result // дождаться именно j-го результата, затем следующего
}
```

Пока коллектор ждёт `j`, остальные воркеры считают `j+1, j+2…` параллельно — их
результаты копятся в собственных future-каналах (буфер 1 не даёт воркеру
заблокироваться). Параллелизм есть, порядок сохранён.

## Идиомы и паттерны

- **Chan-of-chans / future.** Каждому входу — свой канал-результат; порядок задаёт
  отдельная очередь этих каналов, а не порядок завершения воркеров.
- **Диспетчер раздаёт в две очереди.** Один и тот же `job` уходит и в `ordered`
  (для коллектора, сохраняет порядок), и в `tasks` (на исполнение воркерами).
- **Буфер 1 на future.** `make(chan int, 1)` — воркер кладёт результат и сразу
  свободен, не дожидаясь коллектора. Это и есть источник параллелизма.
- **`defer close(out)` в коллекторе + `wg.Wait()`.** Коллектор закрывает выход
  ровно один раз — после того как пройдёт все futures и дождётся воркеров.

## Подводные камни

- **Reorder-буфер по индексу как «костыль».** Можно складывать в `map[int]int` и
  выдавать по растущему индексу — работает, но это ручной буфер с ростом памяти на
  «дыры». Future-вариант проще и аккуратнее.
- **Небуферизованный future.** `make(chan int)` заставит воркера ждать, пока
  коллектор дойдёт до его результата — параллелизм схлопнется почти до
  последовательного. Нужен буфер 1.
- **Двойное закрытие / закрытие не тем.** Закрывать `out` должен один владелец —
  коллектор. Воркеры закрывать `out` или `ordered` не имеют права.
- **Утечка при раннем выходе.** Если коллектор закроет `out` и выйдет, не дождавшись
  воркеров (`wg.Wait()`), оставшиеся воркеры могут зависнуть на отправке в свой
  future — следи за порядком завершения.
- **Дедлок на пустом входе.** Если диспетчер не закроет `tasks` и `ordered`, циклы
  `for range` зависнут. На пустом `in` всё должно корректно схлопнуться и закрыть
  `out`.

## Как подступиться

1. Заведи `out`, `ordered chan job` (буфер), `tasks chan job` (буфер).
2. **Диспетчер**: на каждый `v` из `in` создай `job{v, make(chan int, 1)}`,
   положи его в `ordered` и в `tasks`. После `in` закрой оба канала.
3. **Воркеры** (`workers` штук, под `WaitGroup`): `for j := range tasks { j.result <- work(j.value) }`.
4. **Коллектор**: `defer close(out)`; `for j := range ordered { out <- <-j.result }`;
   затем `wg.Wait()`.
5. Проверь мысленно: вход 0..9, где #9 считается быстрее #2 — `out` всё равно
   0,1,2,…

Дальше — реализуй сам. Разбор открывай после.
