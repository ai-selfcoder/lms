## Идея решения

На каждый вход создаётся `job` с собственным future-каналом (буфер 1). Диспетчер
кладёт `job` в две очереди: `ordered` (хранит исходный порядок) и `tasks` (на
исполнение). Воркеры считают параллельно и пишут результат в future своей задачи.
Коллектор идёт по `ordered` по порядку и пересылает результаты в `out`. Порядок
задаёт очередь futures, а не то, какой воркер закончил раньше.

## Разбор эталона по шагам

Единица работы связывает значение с его future:

```go
type job struct {
    value  int
    result chan int // future: сюда попадёт ровно один результат
}
```

Три канала и нормализация `workers`:

```go
out := make(chan int)
ordered := make(chan job, 1024) // очередь futures «в порядке входа»
tasks := make(chan job, 1024)   // очередь на исполнение
```

`ordered` и `tasks` буферизованы, чтобы диспетчер не блокировался на каждом
элементе и развязывал стадии.

Диспетчер раздаёт один и тот же `job` в обе очереди:

```go
go func() {
    for v := range in {
        j := job{value: v, result: make(chan int, 1)}
        ordered <- j
        tasks <- j
    }
    close(tasks)
    close(ordered)
}()
```

Ключевой момент — `ordered <- j` происходит **в момент поступления входа**,
поэтому `ordered` несёт ровно исходный порядок. `result` — буфер 1: воркер сможет
положить результат и сразу освободиться, не дожидаясь коллектора. После входа оба
канала закрываются — это сигнал завершения для воркеров и коллектора.

Воркеры считают параллельно:

```go
var wg sync.WaitGroup
wg.Add(workers)
for i := 0; i < workers; i++ {
    go func() {
        defer wg.Done()
        for j := range tasks {
            j.result <- work(j.value)
        }
    }()
}
```

Каждый воркер берёт произвольную задачу из `tasks` и кладёт результат в её
**собственный** future. Благодаря буферу 1 запись `j.result <- ...` никогда не
блокирует воркера — он тут же берёт следующую задачу. Порядок завершения здесь
любой, и это нормально.

Коллектор восстанавливает порядок:

```go
go func() {
    defer close(out)
    for j := range ordered {
        out <- <-j.result
    }
    wg.Wait()
}()
```

`out <- <-j.result` — две операции: сначала `<-j.result` блокируется, пока
**именно j-й** результат не готов, затем значение уходит в `out`. Пока коллектор
ждёт `j`, остальные воркеры считают `j+1, j+2, …` — их результаты копятся в
future-каналах. Так держится и параллелизм, и строгий порядок. `defer close(out)`
закрывает выход ровно один раз — коллектор единственный владелец `out`.
`wg.Wait()` после цикла гарантирует, что к моменту возврата все воркеры
завершились (хотя `ordered` уже исчерпан, это страховка от утечки и чистый выход).

## Почему именно так

- **Порядок гарантирован.** `ordered` строится в порядке входа, коллектор читает
  его строго последовательно. Тест задаёт переменную задержку, при которой поздние
  элементы заканчиваются раньше, и проверяет, что `out` всё равно 0,2,4,…
- **Реальный параллелизм.** Future с буфером 1 развязывает воркеров и коллектора:
  пока ждём медленный ранний элемент, остальные считаются. На медленном `work`
  это даёт ускорение в `workers` раз.
- **Нет гонок и утечек.** Каждый future пишется ровно одним воркером и читается
  ровно коллектором — синхронизация по каналу, без общей памяти. Закрытия
  каскадны: `in` → `close(tasks)/close(ordered)` → воркеры выходят, коллектор
  допроходит `ordered` → `close(out)`. На пустом входе всё схлопывается и `out`
  закрывается. `-race` чист.

## Альтернативы и их минусы

- **Reorder-буфер по индексу.** Воркеры шлют `{index, result}` в один канал,
  коллектор копит их в `map[int]int` и выдаёт по растущему счётчику. Работает, но
  это ручной буфер: память растёт на «дыры» (если #100 готов, а #2 нет, всё ждёт в
  map), и кода больше. Future-вариант выражает ту же идею структурно и чище.
- **Собрать всё в срез, затем отсортировать.** Простой, но не стримовый: ждём
  весь вход, держим всё в памяти, нет ранней выдачи. Для бесконечных потоков
  неприменимо.
- **Один воркер.** Тривиально сохраняет порядок, но теряет параллелизм — смысл
  задачи в том, чтобы совместить и то, и другое (тест гоняет и `workers=1`, и
  `workers=10`).

## Сложность и поведение под нагрузкой

Память — O(числа задач «в полёте»): сколько входов между текущей позицией
коллектора и хвостом диспетчера, столько живых future-каналов. При сильно
неравномерном `work` (один медленный элемент в начале) буфер может раздуться —
это плата за порядок. Каждый future — отдельная аллокация канала; для очень
больших потоков это заметно, и тогда уместен пул или reorder-буфер фиксированного
размера. Контеншна нет: вся синхронизация — через каналы, без разделяемого
состояния.

## Что спросит интервьюер дальше

- **«Почему `result` буферизован на 1?»** Чтобы воркер не блокировался в ожидании
  коллектора и сразу брал следующую задачу. Небуферизованный future почти убивает
  параллелизм.
- **«Что ограничивает рост памяти?»** Самый медленный элемент в голове очереди:
  пока он не готов, все последующие готовые результаты ждут в своих future. Можно
  ограничить число задач «в полёте» (bounded `ordered`).
- **«Кто и почему закрывает `out`?»** Коллектор — единственный владелец выхода;
  закрытие из нескольких мест — паника double-close.
- **«Зачем `wg.Wait()`, если `ordered` уже пуст?»** Гарантия чистого завершения и
  отсутствия зависших воркеров; делает поведение детерминированным под `-race`.
- **«Как добавить отмену по `context`?»** Прокинуть `ctx` во все стадии и выходить
  по `ctx.Done()`, аккуратно закрывая каналы, чтобы не было утечек.

## В проде

Этот паттерн — ядро упорядоченных пайплайнов: транскодинг видео (кадры считаются
параллельно, склеиваются по порядку), потоковая обработка с гарантией порядка в
партиции (Kafka-консьюмеры), параллельный парсинг с сохранением последовательности
строк. Идею future/«канал каналов» подробно разбирают в *Concurrency in Go*; в
стандартной библиотеке родственный приём — `errgroup` для fan-out, а сохранение
порядка обычно строят поверх. База — [каналы](/book/channels) и
[паттерны](/book/patterns).
