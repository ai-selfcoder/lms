## Идея решения

Три стадии, между ними каналы. Каждая стадия — пул горутин `range вход → выход`,
а закрывает свой выходной канал отдельная горутина по `WaitGroup`. Закрытие
источника запускает каскад: каждая стадия доедает вход, закрывает выход, что
становится сигналом «вход закончился» для следующей. Результат собирается `range`
по последнему каналу.

## Разбор эталона по шагам

Нормализация — чтобы пул был непустым:

```go
if readers < 1 {
    readers = 1
}
// то же для parsers, validators
```

Источник (нулевая стадия) — один «кран»:

```go
rawIn := make(chan string)
go func() {
    for _, l := range lines {
        rawIn <- l
    }
    close(rawIn)
}()
```

Льёт все строки и закрывает `rawIn` **после** последней. Это закрытие — старт всего
каскада.

Стадия Reader — пул плюс закрывающая горутина:

```go
rawOut := make(chan string)
var rwg sync.WaitGroup
rwg.Add(readers)
for i := 0; i < readers; i++ {
    go func() {
        defer rwg.Done()
        for l := range rawIn {
            rawOut <- l
        }
    }()
}
go func() {
    rwg.Wait()
    close(rawOut)
}()
```

Здесь видна вся механика. `readers` горутин читают `rawIn` и перекладывают в
`rawOut`. Когда `rawIn` закрыли (источником), каждый `range` завершается, каждая
горутина делает `rwg.Done()`. Отдельная горутина ждёт `rwg.Wait()` — то есть пока
**все** ридеры доели — и закрывает `rawOut` ровно один раз. Закрытие из горутин
стадии было бы паникой double-close.

Стадия Parser — тот же шаблон, плюс разбор:

```go
parsed := make(chan LogRecord)
var pwg sync.WaitGroup
pwg.Add(parsers)
for i := 0; i < parsers; i++ {
    go func() {
        defer pwg.Done()
        for l := range rawOut {
            level, msg, _ := strings.Cut(l, "|")
            parsed <- LogRecord{Level: level, Msg: msg}
        }
    }()
}
go func() {
    pwg.Wait()
    close(parsed)
}()
```

`strings.Cut(l, "|")` бьёт строку по первому `|`. Если разделителя нет — `level`
получит всю строку, `msg` будет пустым, и такую запись отбракует валидатор. Вход —
`rawOut`, его закрытие (предыдущей стадией) каскадно завершает парсеры.

Стадия Validator — фильтрация:

```go
valid := make(chan LogRecord)
var vwg sync.WaitGroup
vwg.Add(validators)
for i := 0; i < validators; i++ {
    go func() {
        defer vwg.Done()
        for rec := range parsed {
            if rec.Level == "" || !validLevel(rec.Level) {
                continue
            }
            valid <- rec
        }
    }()
}
go func() {
    vwg.Wait()
    close(valid)
}()
```

`validLevel` пропускает только `INFO/WARN/ERROR`; пустой и прочие уровни
отсеиваются `continue` — в `valid` они не попадают. Это объясняет, почему из
8 входных строк тест ждёт ровно 5.

Сбор результата:

```go
var result []LogRecord
for rec := range valid {
    result = append(result, rec)
}
return result
```

Вызывающая горутина блокируется на `range valid`, пока каскад закрытий не дойдёт
до `valid`. Как только последний валидатор доел `parsed` и закрылся `valid` —
цикл завершается, возвращается срез.

## Почему именно так

- **Закрытие — ровно один раз на канал.** Каждый промежуточный канал закрывает
  одна выделенная горутина после `Wait`. Double-close невозможен.
- **Нет потери данных.** Каждая стадия дочитывает вход до `close`, а выход
  закрывается строго после. Все 5 валидных записей доходят.
- **Нет утечек.** Закрытие источника каскадно завершает все горутины всех стадий.
  После возврата живых горутин нет — тест чист под `-race`.
- **Порядок не гарантирован.** Внутри стадии несколько горутин конкурируют за
  выход, поэтому записи перемешиваются. Условие задачи это и разрешает — тест
  сравнивает мультимножество, а не порядок.

## Альтернативы и их минусы

- **Одна горутина на стадию.** Проще закрывать (нет `WaitGroup`), но теряется
  параллелизм внутри стадии — узкое место на тяжёлом парсинге/валидации.
- **`context` для отмены.** В прод-конвейер добавляют `ctx` и `select` на отправке,
  чтобы прервать поток на полпути. Здесь не требуется — вход конечен и весь
  обрабатывается.
- **Без промежуточных каналов, цепочка функций на одном пуле.** Меньше каналов и
  горутин, но теряется потоковость: стадии не перекрываются по времени, нельзя
  по-разному масштабировать (тяжёлый парсинг — больше парсеров).
- **Слияние Parser+Validator в одну стадию.** Меньше каналов, но хуже читаемость
  и нельзя независимо тюнить пулы.

## Сложность и поведение под нагрузкой

Горутин — `1 + readers + parsers + validators` плюс три закрывающих; память O(их
суммы), не зависит от числа строк. Все промежуточные каналы небуферизованы — стадии
синхронизируются рандеву, что даёт естественный backpressure: быстрая стадия ждёт
медленную. Масштабируется тюнингом размера пула под узкое место (в тесте парсеров
10 — намёк, что парсинг считается тяжёлым). Аллокации — по `LogRecord` на строку,
неизбежно.

## Что спросит интервьюер дальше

- **«Кто и когда закрывает промежуточный канал?»** Выделенная горутина после
  `wg.Wait()` стадии — ровно один раз.
- **«Что если потребитель бросит чтение `valid`?»** Валидаторы зависнут на
  `valid <- rec` — утечка вверх по конвейеру. Лечится `ctx` в `select` на отправке.
- **«Как добавить отмену по таймауту?»** Прокинуть `ctx`, на каждой отправке
  `select { case out <- v: case <-ctx.Done(): return }`.
- **«Зачем разное число горутин по стадиям?»** Чтобы дать больше параллелизма
  узкому месту (тяжёлой стадии).
- **«Сохранится ли порядок строк?»** Нет — пулы перемешивают. Нужен порядок —
  один воркер на стадию или индексы + досборка.

## В проде

Pipeline — классика из *Go Concurrency Patterns*: так строят парсеры логов,
стриминговый ETL, обработку чанков при загрузке. Тот же приём «`WaitGroup` +
закрывающая горутина» — в fan-in (задача 09). В реальных системах стадии часто
оборачивают в `errgroup` для отмены по ошибке и прокидывают `context`. Связанные
главы — [паттерны](/book/patterns), [каналы](/book/channels),
[утечки и гонки](/book/leaks-and-races).
