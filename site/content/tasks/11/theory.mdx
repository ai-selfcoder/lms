## Зачем это на собесе

Конвейер — базовый способ организовать потоковую обработку: данные текут через
стадии `Reader → Parser → Validator`, на каждой стадии свой пул горутин, между
стадиями — каналы. Так строят ETL, парсинг логов, обработку загрузок. Интервьюер
смотрит на главное и самое каверзное в pipeline — **корректное закрытие каналов
между стадиями**: каждый канал закрывается ровно один раз и только после того, как
все горутины предыдущей стадии закончили в него писать.

## Что нужно знать

Стадия — это пул из N горутин, читающих из входного канала и пишущих в выходной.
Когда входной канал закрывают, `range` в каждой горутине завершается, горутина
умирает. Но выходной канал нельзя закрывать из самих горутин стадии — их
несколько, и любая попытка «закрыть после своего цикла» приведёт к double-close
или записи в закрытый канал.

Решение то же, что в fan-in (задача 09): **`WaitGroup` на горутины стадии +
отдельная закрывающая горутина**:

```go
var wg sync.WaitGroup
wg.Add(n)
for i := 0; i < n; i++ {
    go func() { defer wg.Done(); for x := range in { out <- f(x) } }()
}
go func() { wg.Wait(); close(out) }()
```

Этот блок повторяется для каждой стадии. Закрытие распространяется каскадом: закрыли
вход первой стадии → её горутины доели → закрылся её выход → это вход второй
стадии → и так до конца. Подробнее — главы [каналы](/book/channels) и
[паттерны](/book/patterns).

## Идиомы и паттерны

- **Стадия = пул + закрывающая горутина.** Один и тот же шаблон на каждую стадию:
  N воркеров `range in → out`, и `wg.Wait(); close(out)` отдельно.
- **Источник как нулевая стадия.** Одна горутина льёт `lines` в первый канал и
  закрывает его — это «кран», запускающий каскад.
- **`strings.Cut` для разбора.** `level, msg, _ := strings.Cut(l, "|")` разбивает
  по первому разделителю — ровно то, что нужно парсеру.
- **Сбор результата в `range`** по последнему каналу: вызывающая горутина просто
  `for rec := range valid { result = append(...) }`, и цикл завершится, когда
  каскад закрытий дойдёт до `valid`.

## Подводные камни

- **Закрытие выхода из горутины стадии.** Если каждая из N горутин стадии сделает
  `close(out)` после своего `range`, вторая поймает панику double-close.

  ```go
  // как НЕ надо
  go func() {
      for l := range in { out <- parse(l) }
      close(out) // паника при N > 1
  }()
  ```

- **Забыли закрыть промежуточный канал.** Если не запустить `wg.Wait(); close(out)`
  для стадии, следующая стадия навсегда зависнет в `range` по незакрытому каналу —
  утечка всех горутин ниже по конвейеру (см. [утечки](/book/leaks-and-races)).

- **Закрыли источник раньше времени.** Горутина-источник должна закрыть первый
  канал **после** того, как залила все `lines`, а не до. Иначе часть данных
  потеряется или запись пойдёт в закрытый канал.

- **Захват переменной цикла.** До Go 1.22 индекс/переменную из `for i` в горутину
  надо передавать аргументом. Здесь горутины не зависят от `i`, но в общем случае
  про это помнят.

## Как подступиться

1. Нормализуй счётчики стадий (минимум 1 в каждой).
2. **Источник:** горутина льёт `lines` в `rawIn`, затем `close(rawIn)`.
3. **Reader:** пул `readers` горутин `range rawIn → rawOut`; отдельно
   `rwg.Wait(); close(rawOut)`.
4. **Parser:** пул `parsers` горутин `range rawOut`, `strings.Cut` → `parsed`;
   отдельно `pwg.Wait(); close(parsed)`.
5. **Validator:** пул `validators` горутин `range parsed`, отбрасывает невалидные
   уровни, валидные → `valid`; отдельно `vwg.Wait(); close(valid)`.
6. Собери результат `for rec := range valid`.

Дальше — решай сам. Эталон открывай после.
