## Идея решения

Два независимых счётчика. Первый сериализует доступ к `int64` через
`sync.Mutex`. Второй делает инкремент и чтение атомарными операциями
`sync/atomic` без блокировки. Оба гарантируют ровно `1 000 000` под `-race`.

## Разбор эталона по шагам

Счётчик на мьютексе:

```go
type MutexCounter struct {
	mu sync.Mutex
	n  int64
}

func (c *MutexCounter) Inc() {
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

func (c *MutexCounter) Value() int64 {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}
```

`Lock`/`Unlock` делают `c.n++` критической секцией: в любой момент инкремент
выполняет ровно одна горутина, потерянных обновлений нет. В `Inc()` `Unlock`
написан явно — это горячий путь, и лишний `defer` там нежелателен. В `Value()`
`defer` уместен: один выход, читаемее. Чтение тоже под `Lock` — иначе читатель
мог бы увидеть значение, записываемое прямо сейчас (формальная гонка).

Счётчик на атомиках:

```go
type AtomicCounter struct {
	n int64
}

func (c *AtomicCounter) Inc() {
	atomic.AddInt64(&c.n, 1)
}

func (c *AtomicCounter) Value() int64 {
	return atomic.LoadInt64(&c.n)
}
```

`atomic.AddInt64` выполняет чтение-инкремент-запись одной атомарной инструкцией
процессора — без мьютекса и без критической секции. `atomic.LoadInt64`
гарантирует, что мы прочитаем целостное (не «полузаписанное») значение. Все
обращения к `c.n` идут через `atomic` — это обязательное условие корректности.

Оба счётчика держат состояние по указателю-получателю: `sync.Mutex` нельзя
копировать после использования, и атомарные операции работают по адресу поля.

## Почему именно так

- **Нет гонок.** `TestMutexCounter` и `TestAtomicCounter` запускают 1000 горутин
  по 1000 инкрементов под `-race`. Mutex сериализует, atomic делает операцию
  неделимой — оба дают ровно `1 000 000`.
- **Чтение тоже синхронно.** По модели памяти Go даже чтение `int64` без
  синхронизации параллельно с записью — гонка. `Lock`/`LoadInt64` это закрывают.
- **Нулевое значение валидно.** `TestCountersZeroValue` проверяет, что свежий
  счётчик возвращает 0 — оба готовы к работе без явной инициализации.

## Альтернативы и их минусы

- **`atomic.Int64` (Go 1.19+).** Типобезопаснее: `c.n.Add(1)`, `c.n.Load()` —
  невозможно случайно обратиться к полю «мимо» атомика. Современный код
  предпочитает её; функции `atomic.AddInt64` остаются для совместимости.
- **`sync.RWMutex`.** Для чистого счётчика бессмысленно: инкремент — это запись,
  а `RWMutex` выгоден лишь при доминировании чтений (см. задачу 06). Тут он
  только добавит накладных расходов.
- **Шардированный счётчик (по одному на ядро/горутину) с суммированием при
  чтении.** Снимает contention при экстремальной записи (как `expvar`/метрики
  Prometheus), но усложняет `Value()`. Оправдан только при доказанном узком
  месте.

## Сложность и поведение под нагрузкой

Обе операции — O(1). Разница в contention. Под высокой конкуренцией **atomic
обычно быстрее**: одна аппаратная FAA-инструкция дешевле, чем захват мьютекса с
возможной парковкой горутины и переключением контекста при контеншне. Мьютекс
выигрывает, когда критическая секция большая или защищает несколько полей сразу
— тогда атомик не выразит инвариант. Для одного `int64` atomic — почти всегда
правильный выбор. И atomic, и mutex упираются в кэш-когерентность одной
кэш-линии: при тысячах горутин счётчик становится точкой синхронизации железа
(cache-line ping-pong) — отсюда идея шардирования.

## Что спросит интервьюер дальше

- **«Почему `c.n++` — гонка?»** Это read-modify-write из трёх шагов; два потока
  могут потерять инкремент.
- **«Что быстрее под нагрузкой и почему?»** Atomic — одна CAS/FAA дешевле
  блокировки с парковкой; мьютекс лучше для больших секций и нескольких полей.
- **«Можно ли читать `Value` без синхронизации?»** Нет — гонка по модели памяти;
  нужен `Load`/`Lock`.
- **«Чем `atomic.Int64` лучше `atomic.AddInt64`?»** Типобезопасность: нельзя
  обратиться к полю не атомарно.
- **«Как ускорить при экстремальной записи?»** Шардировать счётчик, суммировать
  при чтении — убирает contention на одной кэш-линии.

## В проде

Атомарные счётчики — основа метрик (`expvar`, клиент Prometheus), реф-каунтеров,
лимитеров. `sync.WaitGroup` и `sync.Once` внутри устроены на атомиках.
`sync.Mutex` защищает составное состояние, где атомика недостаточно. Подробнее —
[sync: примитивы](/book/sync-primitives), [atomic](/book/atomic) и
[модель памяти](/book/memory-model).
