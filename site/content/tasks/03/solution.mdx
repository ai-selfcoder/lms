## Идея решения

Бесконечный `for-select`, где отправка очередного числа конкурирует с таймером
бездействия. После каждой успешной отправки таймер безопасно сбрасывается на
500ms. Если за это время никто не прочитал — срабатывает `<-timer.C`, горутина
выходит, `defer close(ch)` сигналит потребителю об окончании.

## Разбор эталона по шагам

Канал, горутина и таймер с отложенным освобождением:

```go
ch := make(chan int)
go func() {
	defer close(ch)
	timer := time.NewTimer(500 * time.Millisecond)
	defer timer.Stop()
	...
}()
return ch
```

`defer close(ch)` гарантирует сигнал «поток окончен» при любом выходе.
`defer timer.Stop()` освобождает таймер рантайма, чтобы он не висел в куче.

Главный цикл — две конкурирующие ветки:

```go
for {
	select {
	case ch <- rand.Int():
		if !timer.Stop() {
			select {
			case <-timer.C:
			default:
			}
		}
		timer.Reset(500 * time.Millisecond)
	case <-timer.C:
		return
	}
}
```

Разберём по частям.

Ветка `ch <- rand.Int()` готова, только когда есть читатель: значит, отправка
успешна → надо «обнулить» отсчёт бездействия. Это делает блок безопасного сброса:

```go
if !timer.Stop() {
	select {
	case <-timer.C:
	default:
	}
}
timer.Reset(500 * time.Millisecond)
```

`timer.Stop()` возвращает `false`, если таймер уже сработал и тик *мог* попасть в
`timer.C`. Тогда мы вычерпываем его неблокирующим `select` с `default` — иначе
следующий `<-timer.C` прочитал бы устаревшее значение и завершил генератор
преждевременно. После очистки `Reset` запускает новый отсчёт на 500ms. Это
ровно тот рецепт, что описан в документации `time.Timer`.

Ветка `<-timer.C` готова, когда 500ms прошли без успешной отправки (читатель
замолчал). `return` выходит из горутины, `defer close(ch)` закрывает канал.

## Почему именно так

- **Таймаут считает именно бездействие.** Сброс привязан к ветке успешной
  отправки, а не к итерации цикла. Пока читатель берёт значения — таймер всё
  время продлевается; как только перестал — отсчёт доходит до конца.
- **Нет ложного срабатывания.** Drain перед `Reset` исключает чтение
  «протухшего» тика. `TestGeneratorClosesOnIdle` допускает одно «застрявшее»
  значение и затем требует `ok == false`.
- **Нет утечки.** `TestGeneratorNoLeak` читает пару значений, ждёт 700ms и через
  `settleGoroutines` проверяет возврат к baseline. Без таймаута генератор
  завис бы навсегда.

## Альтернативы и их минусы

- **`time.After(500*ms)` прямо в `select`.** Лаконично, но каждый виток цикла
  создаёт новый таймер, который живёт до срабатывания — в горячем цикле это
  утечка таймеров и лишняя нагрузка на GC. `NewTimer` + `Reset`
  переиспользует один объект.
- **`context.WithTimeout` на каждую отправку.** Можно, но контекст одноразовый:
  пришлось бы пересоздавать его после каждого значения — дороже и многословнее,
  чем `Reset`.
- **Отдельная горутина-«сторож».** Запустить вторую горутину, которая следит за
  активностью, — лишняя синхронизация и ещё один источник гонок. Один `select`
  проще и безопаснее.

## Сложность и поведение под нагрузкой

Одна горутина, один канал, один переиспользуемый таймер — константная память.
Каждая отправка делает `Stop`/`Reset` — дешёвые операции рантайм-таймеров.
`rand.Int()` из `math/rand` берёт глобальный мьютекс; под экстремальной
нагрузкой это могло бы стать узким местом, но для генератора-одиночки
несущественно. Завершение — мгновенное по срабатыванию таймера.

## Что спросит интервьюер дальше

- **«Почему `Reset` без `Stop`/drain опасен?»** В `timer.C` может лежать старый
  тик; следующий `<-timer.C` прочитает его и завершит генератор раньше.
- **«Почему сброс именно в ветке отправки, а не в начале цикла?»** Иначе таймаут
  считал бы «время работы», а не «время бездействия», и при зависшем читателе
  не сработал бы.
- **«Чем `NewTimer`+`Reset` лучше `time.After`?»** Не плодит таймеры на каждой
  итерации, меньше давление на GC.
- **«В Go 1.23 что-то изменилось с таймерами?»** Да, поведение `Stop`/`Reset`
  и сборки незавершённых таймеров стало проще (тик больше не «застревает»), но
  рецепт drain остаётся совместимым и безопасным.

## В проде

Паттерн «idle timeout» — основа сетевых серверов: `net.Conn.SetReadDeadline`,
read/idle-таймауты в `net/http.Server`, heartbeat-стримы gRPC. Безопасный
`Stop`/drain/`Reset` встречается везде, где таймер переиспользуется в цикле —
например, в реализациях rate limiter и backoff. См. [select](/book/select)
и [утечки и гонки](/book/leaks-and-races).
