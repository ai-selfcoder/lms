## Зачем это на собесе

Источник данных, который сам себя гасит при простое, — типичный кирпич
real-time систем: стрим, который закрывается, если клиент перестал читать;
поллер, который останавливается без подписчиков. Здесь проверяют две вещи:
умеешь ли ты конкурировать отправку с таймером в одном `select` и знаешь ли ты
коварную механику `time.Timer` — её правильный `Stop`/`Reset`, иначе словишь
утечку или ложное срабатывание.

## Что нужно знать

`time.Timer` — это канал `C`, в который через заданное время прилетает одно
значение. В `select` он конкурирует с другими ветками:

```go
timer := time.NewTimer(500 * time.Millisecond)
select {
case ch <- v:   // успели отправить
case <-timer.C: // вышло время — таймаут
}
```

«Бездействие» здесь означает: между двумя успешными отправками прошло больше
500ms. Значит, таймер нужно *сбрасывать после каждой успешной отправки*, а не на
каждой итерации. Подробнее про мультиплексирование — [select](/book/select).

Закрытие канала через `defer close(ch)` — сигнал потребителю «поток окончен»: его
`v, ok := <-ch` вернёт `ok == false`. Это спасает от [утечки горутины](/book/leaks-and-races):
без таймаута генератор писал бы вечно и завис, как только читатель ушёл.

## Идиомы и паттерны

- **`for { select { ... } }`** — бесконечный генератор, где одна ветка пишет
  данные, другая ловит таймаут.
- **Сброс таймера = «drain + Reset».** Канонический безопасный сброс:

  ```go
  if !timer.Stop() {
      select {
      case <-timer.C: // вычерпываем уже сработавший тик
      default:
      }
  }
  timer.Reset(500 * time.Millisecond)
  ```

- **`defer timer.Stop()` и `defer close(ch)`** — освобождаем таймер и сигналим
  о завершении при любом выходе.

## Подводные камни

- **Сброс таймера на каждой итерации, а не после успешной отправки.** Если
  читатель завис, отправка не происходит, но таймер всё равно «продлевается» —
  таймаут бездействия никогда не сработает, генератор не завершится.
- **`Reset` без `Stop`/drain.** Документация прямо предупреждает: `Reset`
  нельзя звать, пока в `timer.C` может лежать старое значение. Иначе следующий
  `<-timer.C` прочитает *устаревший* тик и завершит генератор раньше времени.

  ```go
  // как НЕ надо:
  timer.Reset(500 * time.Millisecond) // в C мог остаться прошлый тик
  ```

- **`time.After` в цикле.** Каждый вызов `time.After` создаёт *новый* таймер,
  который не собирается мусором до срабатывания. В горячем цикле это утечка
  таймеров; `time.NewTimer` + `Reset` переиспользует один.
- **Забыли `close(ch)`.** Потребитель не узнает, что поток окончен, и зависнет
  на `<-ch`.

## Как подступиться

1. Создай небуферизированный `ch` и горутину с `defer close(ch)`.
2. Внутри — `timer := time.NewTimer(500*ms)` и `defer timer.Stop()`.
3. `for { select { case ch <- rand.Int(): ...; case <-timer.C: return } }`.
4. В ветке успешной отправки сделай безопасный сброс: `Stop` → drain → `Reset`.
5. В ветке `<-timer.C` — `return` (сработает `defer close(ch)`).
6. Проверь мысленно: читатель взял пару значений и замолчал на 700ms → ветка
   `<-timer.C` срабатывает, горутина выходит, канал закрывается.

Реши сам, затем открывай разбор эталона.
