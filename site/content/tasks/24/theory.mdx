## Зачем это на собесе

В Go паника распространяется вверх по стеку горутины, и если её не поймать —
рушится **вся программа**, а не одна задача. Пул, выполняющий чужой код (хендлеры,
плагины, пользовательские функции), обязан изолировать сбой: упала одна задача —
воркер восстановился и взял следующую. Интервьюер проверяет, понимаешь ли ты
семантику `panic`/`recover`/`defer` и умеешь ли строить отказоустойчивый
исполнитель без утечек.

## Что нужно знать

`recover` работает **только** внутри `defer` и только в той же горутине, где
произошла паника. Это ключевое ограничение (см. [горутины](/book/goroutines)):

```go
func safe(fn func()) {
    defer func() {
        if r := recover(); r != nil {
            // паника поймана, горутина выживает
        }
    }()
    fn()
}
```

`recover()` возвращает значение, переданное в `panic(...)`, или `nil`, если
паники не было. Важно: ловить надо **на каждую задачу отдельно**, а не один раз на
весь цикл воркера — иначе первая же паника завершит воркер.

Базовый воркер читает задачи через `for range` по каналу — цикл сам завершится,
когда канал закроют, а `sync.WaitGroup` даст дождаться всех воркеров (см.
[sync](/book/sync-primitives)):

```go
for task := range tasks { run(task) }
```

## Идиомы и паттерны

- **Per-task recover-обёртка.** Отдельная функция `runSafely(task)` со своим
  `defer recover()`. Когда она возвращается (нормально или после паники),
  управление возвращается в цикл `for range` — воркер живёт дальше.
- **Паника → значение → канал ошибок.** Пойманную панику оборачивают в `error`
  (`fmt.Errorf("...: %v", r)`) и шлют в `errs`. Так вызывающий узнаёт о сбоях, не
  теряя их.
- **`for range` по каналу + `WaitGroup`.** Канонический способ дренировать
  очередь и дождаться завершения: закрытие `tasks` останавливает все циклы,
  `wg.Wait()` ловит момент, когда последний воркер вышел.

## Подводные камни

- **`recover` вне `defer`.** Прямой вызов `recover()` в теле функции всегда
  вернёт `nil` и панику не поймает. Только из отложенной функции.
- **Один `recover` на весь цикл.** Если обернуть весь `for range` одним `defer`,
  первая паника раскрутит стек до этого `defer`, выйдет из цикла — и воркер
  умрёт. Восстановление должно быть в области одной задачи.
- **`recover` в чужой горутине.** Запуск `task()` в новой горутине без `defer`
  внутри неё уронит процесс — родительский `recover` его не поймает:

```go
// как НЕ надо: recover снаружи не спасёт
go task() // если task паникует — крах всей программы
```

- **Дедлок на `errs`.** Если `errs` небуферизованный и никто его не читает, воркер
  заблокируется на отправке ошибки и `Wait()` никогда не вернётся. В проде —
  буфер или гарантированный читатель.

## Как подступиться

1. Храни `workers`, `tasks <-chan func()`, `errs chan<- error`, `wg`.
2. `Start`: `wg.Add(workers)`, запусти `workers` горутин-воркеров.
3. Воркер: `defer wg.Done()`, затем `for task := range tasks { runSafely(task) }`.
4. `runSafely(task)`: `defer func(){ if r := recover(); r != nil { errs <- ... } }()`,
   потом вызови `task()` (с проверкой на `nil`).
5. `Wait`: просто `wg.Wait()`.
