## Идея решения

Каждая задача выполняется внутри маленькой обёртки с `defer recover()`. Паника
ловится в границах **одной** задачи: обёртка возвращается, а цикл `for range`
воркера продолжает брать следующие задачи. Пойманная паника превращается в
`error` и уходит в канал `errs`. Завершение — через `for range` по закрытому
`tasks` и `sync.WaitGroup`.

## Разбор эталона по шагам

Состояние минимально — каналы извне и `WaitGroup`:

```go
type SafePool struct {
    workers int
    tasks   <-chan func()
    errs    chan<- error
    wg      sync.WaitGroup
}
```

Направления каналов (`<-chan`, `chan<-`) фиксируют контракт: пул только читает
задачи и только пишет ошибки.

`Start` поднимает фиксированное число воркеров:

```go
func (p *SafePool) Start() {
    p.wg.Add(p.workers)
    for i := 0; i < p.workers; i++ {
        go p.worker()
    }
}
```

`wg.Add(p.workers)` вызывается **до** запуска горутин — иначе `Wait()` мог бы
вернуться раньше, чем последний воркер успел зарегистрироваться.

Воркер дренирует канал задач:

```go
func (p *SafePool) worker() {
    defer p.wg.Done()
    for task := range p.tasks {
        p.runSafely(task)
    }
}
```

`for range p.tasks` сам завершится, когда `tasks` закроют — это сигнал «задач
больше не будет». Ключевая деталь: каждая итерация зовёт `runSafely`, а не
`task()` напрямую. Поэтому паника одной задачи не выкидывает нас из цикла.

Сердце устойчивости — обёртка:

```go
func (p *SafePool) runSafely(task func()) {
    defer func() {
        if r := recover(); r != nil {
            p.errs <- fmt.Errorf("паника в задаче: %v", r)
        }
    }()
    if task != nil {
        task()
    }
}
```

Почему это работает: когда `task()` паникует, начинается раскрутка стека. Она
доходит до `defer` внутри `runSafely`, там вызывается `recover()` — он гасит
панику и возвращает её значение. Функция `runSafely` завершается **нормально**,
управление возвращается в `for range`, воркер жив. `recover()` обязан быть внутри
`defer` и в той же горутине, что паника, — оба условия здесь выполнены. Проверка
`task != nil` страхует от nil-функции.

`Wait` тривиален:

```go
func (p *SafePool) Wait() {
    p.wg.Wait()
}
```

Он вернётся, когда все воркеры выйдут из `for range`, то есть после закрытия
`tasks` и обработки всех задач.

## Почему именно так

- **Изоляция сбоя на уровне задачи.** Граница `recover` — ровно одна задача,
  поэтому паника не «съедает» воркер и не теряет последующие задачи. Тест
  `TestSafePoolContinuesAfterPanic` чередует панику и нормальную задачу на
  **одном** воркере и проверяет, что все нормальные выполнились.
- **Точный учёт.** Число отправленных в `errs` ошибок равно числу паник, число
  выполненных нормальных задач — равно их количеству. Тест сверяет оба счётчика
  атомарно.
- **Нет гонок и утечек.** Воркеры не делят изменяемого состояния (счётчики в
  тесте — atomic), завершаются по закрытию канала, `wg` ловит момент выхода.
  `-race` чист.

## Альтернативы и их минусы

- **Один `defer recover()` на весь цикл воркера.** После первой же паники стек
  раскрутится до этого `defer`, цикл прервётся, воркер умрёт — пул деградирует с
  каждой паникой. Неверно.
- **`recover` + перезапуск воркера.** Ловить панику в самом `worker()` и
  перезапускать его новой горутиной. Работает, но это лишние аллокации горутин и
  усложнение; обёртка на задачу проще и не теряет позицию в очереди.
- **Логировать панику вместо `errs`.** Допустимо, но тогда вызывающий не может
  программно среагировать (метрика, alert, retry). Канал ошибок гибче.

## Сложность и поведение под нагрузкой

`defer`/`recover` на каждой задаче стоит немного: установка `defer` — дешёвая
операция, а сам `recover` отрабатывает только при панике. Для нормального пути
накладные расходы пренебрежимо малы. Горутин ровно `workers`, состояния они не
делят — контеншна нет. Узкое место — канал `errs`: при шквале паник он не должен
блокировать воркеров, иначе пропускная способность просядет (нужен буфер или
быстрый читатель).

## Что спросит интервьюер дальше

- **«Что вернёт `recover()` вне `defer`?»** Всегда `nil` — паника не будет
  поймана. Recover «видит» панику только из отложенной функции.
- **«Поймает ли родительский `recover` панику в дочерней горутине?»** Нет. Каждая
  горутина обязана восстанавливаться сама; непойманная паника в любой горутине
  валит весь процесс.
- **«Стоит ли ловить все паники подряд?»** Нет — паника на программерской ошибке
  (nil-разыменование, выход за границу) часто значит «состояние повреждено».
  Иногда правильнее упасть. Здесь мы изолируем *задачи*, а не маскируем баги.
- **«Как добавить стек паники в ошибку?»** `runtime/debug.Stack()` внутри
  `recover` — записать трейс в лог/метрику.
- **«Что если `errs` переполнится?»** Воркер заблокируется на отправке. Решения:
  буфер, неблокирующая отправка через `select { default }`, дроп с метрикой.

## В проде

Этот паттерн стоит за устойчивостью серверов: `net/http` оборачивает каждый
хендлер так, что паника в одном запросе не роняет сервер (`http.Server` ловит её
и закрывает соединение). gRPC-перехватчики `recovery` делают то же. Очереди задач
(asynq, machinery, фоновые воркеры) изолируют сбой джобы recover-обёрткой и шлют
ошибку в DLQ/метрику. Фундамент — семантика [горутин](/book/goroutines) и
[sync](/book/sync-primitives), а охота за утечками — глава
[leaks-and-races](/book/leaks-and-races).
