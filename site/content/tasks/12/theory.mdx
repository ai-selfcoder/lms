## Зачем это на собесе

Batcher решает прод-задачу «не дёргай бэкенд на каждое событие»: накапливаем
события и сбрасываем их пачкой — по размеру (накопилось 100) или по времени
(прошло 50 мс). Так работают буферизация записей в БД, отправка метрик, агрегация
логов. Интервьюер проверяет умение держать состояние в одной горутине, совмещать
два условия сброса в `select`, и — самое сложное — **корректно остановиться**:
сбросить остаток и завершить фоновую горутину без утечки.

## Что нужно знать

Главная идиома — **одна горутина владеет состоянием**. Буфер событий живёт внутри
неё, а наружу торчат только каналы. Тогда не нужен мьютекс: `Add` шлёт событие в
канал, горутина одна читает и аппендит. Это «канал вместо мьютекса» из
[sync](/book/sync-primitives) и [каналов](/book/channels).

Сброс по двум условиям — это `select` с двумя источниками: канал событий и тик
таймера.

```go
ticker := time.NewTicker(50 * time.Millisecond)
for {
    select {
    case ev := <-in:
        buf = append(buf, ev)
        if len(buf) >= 100 { flush(buf); buf = buf[:0] }
    case <-ticker.C:
        flush(buf); buf = buf[:0]
    }
}
```

Третье — **остановка**. Закрытие входного канала — это сигнал «больше событий не
будет». Горутина видит `ok == false`, сбрасывает остаток и выходит. А `Stop`
должен дождаться, что горутина действительно вышла — для этого нужен `done`-канал.
Подробнее — [select](/book/select).

## Идиомы и паттерны

- **Горутина-владелец состояния.** Буфер и таймер живут в `run()`; `Add` и `Stop`
  общаются с ней только через каналы. Нет общей памяти — нет мьютексов и гонок.
- **`select` на два условия сброса.** Размер проверяется после `append`, время —
  по `ticker.C`. Любое срабатывание чистит буфер.
- **Закрытие входа как «poison pill».** `close(in)` в `Stop` — сигнал завершения;
  горутина по `ok == false` дренирует остаток и выходит.
- **`done`-канал для синхронной остановки.** `Stop` блокируется на `<-done`, пока
  `run()` не закроет `done` через `defer` — гарантия «горутина точно умерла».
- **Копия буфера перед `flush`.** В колбэк отдаётся копия, а внутренний буфер
  переиспользуется через `buf = buf[:0]` — иначе колбэк увидит, как буфер
  перезаписывается под ним.

## Подводные камни

- **Сброс пустой пачки.** По тику таймера буфер может быть пуст — `flush` пустого
  среза бессмысленен и засоряет приёмник. Проверяй `if len(buf) == 0 { return }`.

- **Отдать `flush` сам буфер, не копию.** Если передать `b.flush(buf)` и тут же
  сделать `buf = buf[:0]` и аппендить дальше, колбэк (особенно если он
  асинхронный или хранит срез) увидит затёртые данные — гонка по данным.

  ```go
  // как НЕ надо
  b.flush(buf)   // отдали внутренний срез
  buf = buf[:0]  // и сразу переиспользуем тот же массив
  ```

- **`Stop` не дожидается горутину.** Если `Stop` просто `close(in)` и вернётся,
  остаток может не успеть сброситься, а горутина — утечь. Нужен `<-done`.

- **Утечка таймера.** `time.NewTicker` держит ресурс; без `defer ticker.Stop()`
  он живёт после горутины. Об утечках — [утечки и гонки](/book/leaks-and-races).

- **Блокировка `Add` навсегда.** `Add` пишет в небуферизованный канал — если
  `run()` уже вышла (после `Stop`), `Add` зависнет. Контракт: не звать `Add` после
  `Stop`.

## Как подступиться

1. Структура: `in chan Event`, `done chan struct{}`, `flush func([]Event)`.
   `NewBatcher` создаёт каналы и запускает `go b.run()`.
2. В `run()`: `defer close(b.done)`, буфер `make([]Event, 0, 100)`, тикер на 50 мс,
   `defer ticker.Stop()`.
3. Локальный `doFlush`: если буфер пуст — выйти; иначе скопировать, вызвать `flush`,
   обрезать `buf = buf[:0]`.
4. Цикл `select`: на событии — `append` и проверка `>= 100`; на `ok == false` —
   `doFlush()` и `return`; на `ticker.C` — `doFlush()`.
5. `Add` шлёт в `in`. `Stop`: `close(in)`, затем `<-done`.
