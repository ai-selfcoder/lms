## Идея решения

Одна фоновая горутина владеет буфером и таймером. `Add` шлёт событие в канал,
горутина аппендит и сбрасывает пачку при достижении 100 или по тику 50 мс. `Stop`
закрывает входной канал (сигнал «событий больше нет»), горутина сбрасывает остаток
и выходит, а `Stop` дожидается её через `done`-канал.

## Разбор эталона по шагам

Структура и конструктор:

```go
type Batcher struct {
    in    chan Event
    done  chan struct{}
    flush func(batch []Event)
}

func NewBatcher(flush func(batch []Event)) *Batcher {
    b := &Batcher{
        in:    make(chan Event),
        done:  make(chan struct{}),
        flush: flush,
    }
    go b.run()
    return b
}
```

Наружу торчат только два канала. `in` — для событий, `done` — чтобы `Stop` понял,
что горутина завершилась. Всё состояние (буфер, таймер) спрятано внутри `run()` —
поэтому мьютекс не нужен вообще.

Тело горутины — настройка:

```go
func (b *Batcher) run() {
    defer close(b.done)

    buf := make([]Event, 0, batchSize)
    ticker := time.NewTicker(flushInterval)
    defer ticker.Stop()
```

`defer close(b.done)` — единственная точка закрытия `done`; срабатывает при любом
выходе из `run()` и разблокирует `Stop`. Буфер сразу с ёмкостью `batchSize` —
аппенды до 100 не реаллоцируют. `defer ticker.Stop()` освобождает таймер, иначе он
утечёт.

Локальный сброс:

```go
doFlush := func() {
    if len(buf) == 0 {
        return
    }
    batch := make([]Event, len(buf))
    copy(batch, buf)
    b.flush(batch)
    buf = buf[:0]
}
```

Три важные детали в пяти строках:

- `if len(buf) == 0 { return }` — пустые пачки не сбрасываем (тик по пустому буферу
  не дёргает `flush`).
- `batch := make + copy` — в колбэк уходит **копия**. Внутренний `buf` сразу
  переиспользуется, и колбэк не увидит затирания. Без копии была бы гонка по данным.
- `buf = buf[:0]` — обрезаем длину до нуля, но сохраняем ёмкость; следующая пачка
  аппендится в тот же массив без аллокаций.

Главный цикл:

```go
for {
    select {
    case ev, ok := <-b.in:
        if !ok {
            doFlush()
            return
        }
        buf = append(buf, ev)
        if len(buf) >= batchSize {
            doFlush()
        }
    case <-ticker.C:
        doFlush()
    }
}
```

Две ветви `select`:

- `ev, ok := <-b.in`. Если `ok == false`, канал закрыт (`Stop`) — сбрасываем
  остаток и выходим. Иначе аппендим и, если набрали `batchSize`, сбрасываем по
  размеру.
- `<-ticker.C` — тик 50 мс, сброс по времени (если буфер не пуст).

Тикер тикает с фиксированным периодом независимо от сбросов по размеру. Это
немного упрощает семантику «50 мс после последнего сброса» (строго после сброса
тикер не перезапускается), но для требований задачи достаточно: пачка всё равно не
ждёт дольше периода.

`Add` и `Stop`:

```go
func (b *Batcher) Add(event Event) {
    b.in <- event
}

func (b *Batcher) Stop() {
    close(b.in)
    <-b.done
}
```

`Add` просто шлёт в канал — потокобезопасно, так как читатель один. `Stop` закрывает
`in` (горутина увидит `ok == false`, сбросит остаток) и блокируется на `<-b.done`,
пока `run()` не завершится через `defer close(b.done)`. Это делает `Stop`
синхронным: после возврата гарантированно нет живой горутины и остаток сброшен —
именно это проверяет `TestBatcherStopFlushesRemainder`.

## Почему именно так

- **Нет гонок без мьютекса.** Буфер трогает только одна горутина; синхронизация —
  через каналы. `-race` чист. Тест использует свой мьютекс в `collector`, потому
  что `flush` может звать его конкурентно в общем случае, но здесь — последовательно.
- **Нет утечек.** `Stop` дренирует и дожидается горутины; `defer ticker.Stop()`
  чистит таймер. После `Stop` ничего не живёт.
- **Пачка ≤ 100.** Сброс по размеру срабатывает ровно на `>= batchSize`, поэтому
  пачка не превышает 100 — это проверяет `TestBatcherBySize` на 250 событиях.
- **Каждое событие сброшено ровно раз.** `buf = buf[:0]` после копии не теряет и не
  дублирует — тест проверяет уникальность всех ID.

## Альтернативы и их минусы

- **Мьютекс + буфер в структуре, отдельная горутина-таймер.** Состояние общее, под
  `mu`. Работает, но появляются гонки-кандидаты, нужен аккуратный лок вокруг
  буфера, и легко ошибиться. Модель «одна горутина-владелец» проще и безопаснее.
- **`time.Timer` с `Reset` после каждого сброса** вместо `Ticker`. Даёт точную
  семантику «ровно 50 мс после последнего сброса», но `Reset` коварен (нужно
  правильно дренировать канал), легко получить баг. `Ticker` проще и достаточен.
- **Буферизованный `in`.** Снизит блокировку `Add` под всплеском, но усложнит
  дренаж в `Stop` (надо вычитать остаток буфера канала). Здесь не нужно.

## Сложность и поведение под нагрузкой

Горутина одна, память — O(batchSize) на буфер. `Add` — один `chan send`,
амортизированно дёшев, но блокируется до приёма горутиной: под очень высоким RPS
эта рандеву-синхронизация становится узким местом (один читатель). Аллокация — по
одному `make([]Event, len)` на сброс (копия для колбэка); ёмкость буфера
переиспользуется. Под бёрстом события сбрасываются пачками по 100; в тишине —
таймером не чаще раза в 50 мс, и пустые тики бесплатны.

## Что спросит интервьюер дальше

- **«Зачем копировать буфер перед `flush`?»** Иначе колбэк увидит затирание при
  переиспользовании `buf[:0]` — гонка по данным.
- **«Что если `Add` вызвать после `Stop`?»** Паника записи в закрытый канал или
  вечная блокировка. Контракт — не звать; в проде защищаются `recover` или флагом.
- **«Почему `Stop` ждёт `done`?»** Чтобы гарантировать сброс остатка и отсутствие
  утечки — `Stop` синхронный.
- **«Как сделать `flush` асинхронным?»** Слать копию в отдельный воркер-пул; буфер
  всё равно отдаём копией, так что безопасно.
- **«`Ticker` vs `Timer.Reset`?»** `Ticker` проще, но тикает независимо от сбросов;
  `Reset` точнее по семантике, но капризен.

## В проде

Batching — повсюду: буферизация записей в Kafka/ClickHouse, агрегация метрик
(Prometheus remote write батчит), отправка трейсов в OTLP-экспортёрах. Модель
«одна горутина-владелец состояния, общение через каналы» — каноничный Go-подход к
shared state без мьютексов. Связанные главы — [каналы](/book/channels),
[select](/book/select), [sync](/book/sync-primitives),
[утечки и гонки](/book/leaks-and-races).
