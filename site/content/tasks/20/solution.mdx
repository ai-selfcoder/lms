## Идея решения

BFS идёт волнами по уровням (0..2, три итерации). Каждый уровень обрабатывается
параллельно: на каждую вершину — горутина, опрашивающая `getFriends` под
семафором на 10 слотов. Общее состояние (`visited`, `result`, `firstErr`) живёт
под одним мьютексом, новые вершины собираются в `next` и становятся следующим
`frontier`. `WaitGroup` — барьер между волнами.

## Разбор эталона по шагам

Общее состояние и семафор:

```go
var mu sync.Mutex
visited := map[int]bool{startID: true} // старт уже «посещён»
result := make(map[int]bool)
var firstErr error

sem := make(chan struct{}, maxConcurrency) // 10
frontier := []int{startID}
```

`visited` сразу содержит `startID`: его соседей мы запрашиваем, но саму стартовую
вершину повторно не обходим. В `result` он попадёт лишь если кто-то укажет его
своим другом (как в тесте — вершина 1 как друг 2 и 3). `sem` — семафор на 10
одновременных вызовов.

Цикл по уровням:

```go
for depth := 0; depth < maxDepth && len(frontier) > 0; depth++ {
	var wg sync.WaitGroup
	var nextMu sync.Mutex
	var next []int
	...
	wg.Wait()
	if firstErr != nil {
		return nil, firstErr
	}
	frontier = next
}
```

Ровно `maxDepth` итераций (три рукопожатия) — ни одной лишней. `wg.Wait()` —
барьер: следующий уровень начинается только когда текущий полностью собран.

Горутина на вершину:

```go
for _, id := range frontier {
	wg.Add(1)
	go func(id int) {
		defer wg.Done()

		sem <- struct{}{}        // занять слот
		defer func() { <-sem }() // освободить даже при раннем return

		friends, err := getFriends(id)
		if err != nil {
			mu.Lock()
			if firstErr == nil {
				firstErr = err
			}
			mu.Unlock()
			return
		}
		...
	}(id)
}
```

Три ключевых момента:

- **`id` передан параметром** — нет бага захвата переменной цикла.
- **Семафор занимается внутри горутины**, прямо вокруг `getFriends`. Если бы слот
  брали до `go`, ограничивался бы темп запуска горутин, а не число *параллельных
  вызовов*. `defer func(){ <-sem }()` гарантирует освобождение слота на любом
  пути выхода (в т.ч. при ошибке) — нет дедлока семафора.
- **Первая ошибка фиксируется под мьютексом**, остальные молча игнорируются.

Сбор результата и новых вершин:

```go
mu.Lock()
var newOnes []int
for _, f := range friends {
	result[f] = true
	if !visited[f] {
		visited[f] = true
		newOnes = append(newOnes, f)
	}
}
mu.Unlock()

if len(newOnes) > 0 {
	nextMu.Lock()
	next = append(next, newOnes...)
	nextMu.Unlock()
}
```

Под `mu`: *каждый* друг попадает в `result` (даже уже посещённый — так вершина 1
оказывается в ответе), но в обход следующего уровня (`next`) идут только
**новые** вершины — это и есть защита от циклов: посещённую вершину не запросим
второй раз. `next` копится под отдельным `nextMu`, чтобы не держать основной
мьютекс дольше необходимого.

Финальная сборка:

```go
out := make([]int, 0, len(result))
for id := range result {
	out = append(out, id)
}
return out, nil
```

`result` — множество, поэтому дубликатов в ответе нет по построению.

## Почему именно так

- **Нет гонок.** Любое касание `visited`/`result`/`firstErr` — под `mu`, `next` —
  под `nextMu`. `-race` чист (есть happens-before через мьютексы, см.
  [модель памяти](/book/memory-model)).
- **Конкурентность ограничена.** Семафор на 10 жёстко держит `maxLive <= 10` —
  тест проверяет это атомарным счётчиком.
- **Циклы безопасны.** `visited` гарантирует, что каждую вершину запрашиваем не
  более раза → обход конечен. Тест с графом `1↔2↔3` не виснет.

## Альтернативы и их минусы

- **`golang.org/x/sync/errgroup` + `SetLimit`.** Идиоматичнее: `g.SetLimit(10)`
  заменяет ручной семафор, `g.Wait()` возвращает первую ошибку. По сути та же
  схема, меньше ручного кода — в проде брали бы его.
- **Полностью асинхронный обход без уровней.** Одна общая очередь задач и пул
  воркеров, глубину носим вместе с вершиной. Гибче, но сложнее отслеживать
  «все задачи завершились» (нужен счётчик активных), легче словить дедлок.
- **`sync.Map` вместо `visited` под мьютексом.** `LoadOrStore` атомарно проверяет
  «первый ли я на этой вершине». Убирает явный лок, но `result` всё равно надо
  собирать отдельно, выигрыш невелик.

## Сложность и поведение под нагрузкой

Время — O(V+E) логически, но ограничено сверху 10 параллельными медленными
вызовами на уровень: глубина 3 × (размер уровня / 10) × latency. Память — O(V) на
`visited`/`result`. Узкое место — `getFriends` (сеть), поэтому семафор настраивают
под лимиты downstream. Мьютекс на общем состоянии — секунды держится наносекунды
(пара операций с map), контеншен незначителен по сравнению с сетевыми задержками.

## Что спросит интервьюер дальше

- **«Как добавить отмену по контексту?»** Прокинуть `ctx`, проверять
  `ctx.Done()` перед/во время `getFriends`; с `errgroup` — `errgroup.WithContext`
  отменяет остальных при первой ошибке.
- **«Почему BFS, а не DFS?»** Нужна глубина (число рукопожатий) — BFS естественно
  считает её по уровням; DFS пришлось бы носить depth и легко уйти вглубь.
- **«Что если граф огромный?»** `visited` не влезет в память — выносят в внешнее
  хранилище/Bloom-фильтр, обход делают распределённым.
- **«Почему `result` включает уже посещённые, а `next` — нет?»** Достижимость и
  «нужно ли обходить дальше» — разные вопросы: в ответ вершина входит, повторно
  её соседей не запрашиваем.
- **«Детерминирован ли порядок результата?»** Нет — это множество; для
  стабильности сортируют (тест так и делает).

## В проде

Эта схема — основа параллельных краулеров, обхода графа зависимостей (build
systems), рекомендательных «друзья друзей», fan-out к шардам. В реальном Go-коде
ручной семафор заменяют на `errgroup` с `SetLimit` и `context` для отмены.
Навык — совместить ограниченную конкурентность, защиту от повторной обработки и
безопасную сборку результата — переносится на десятки highload-задач.
