## Идея решения

Реестр `map[string]*call` под мьютексом хранит «летящие» вызовы. Первый пришедший
на ключ становится лидером: создаёт `call`, делает `wg.Add(1)`, запускает `fn` и
по завершении делает `wg.Done()`. Остальные находят тот же `call`, отпускают
мьютекс и ждут на `wg.Wait()`, а потом читают общий результат. После завершения
ключ удаляется, чтобы следующая волна получила свежие данные.

## Разбор эталона по шагам

Структуры:

```go
type call struct {
	wg  sync.WaitGroup
	val interface{}
	err error
}

type Group struct {
	mu sync.Mutex
	m  map[string]*call
}
```

`call` — это «один полёт fn»: барьер `wg` плюс место под результат. `Group`
работает как нулевое значение, поэтому map создаётся лениво.

Вход и поиск существующего вызова:

```go
g.mu.Lock()
if g.m == nil {
	g.m = make(map[string]*call)
}
if c, ok := g.m[key]; ok {
	g.mu.Unlock()      // ВАЖНО: отпускаем лок перед ожиданием
	c.wg.Wait()
	return c.val, c.err
}
```

Если по ключу уже кто-то летит — мы ведомый: **сначала отпускаем `g.mu`**, потом
ждём `c.wg.Wait()`. Порядок критичен: лидеру в конце нужен `g.mu` для `delete`;
ждать под локом — гарантированный дедлок. После `Wait()` читаем `c.val/c.err` —
барьер `wg` дал happens-before, поэтому записи лидера видны без гонки.

Лидер создаёт вызов и запускает `fn` вне мьютекса:

```go
c := new(call)
c.wg.Add(1)
g.m[key] = c
g.mu.Unlock()       // отпускаем лок ДО медленного fn

c.val, c.err = fn()
c.wg.Done()         // будим всех ведомых
```

Ключевой момент производительности — `g.mu.Unlock()` **до** `fn()`. Мьютекс
защищает только реестр, а не выполнение `fn`. Пока лидер делает медленный
сетевой вызов, мьютекс свободен: новые горутины успевают зайти, найти `c` и
встать в ожидание — вот почему 20 вызовов сливаются в один.

Удаление и возврат:

```go
g.mu.Lock()
delete(g.m, key)
g.mu.Unlock()
return c.val, c.err
```

`delete` убирает «отлетевший» вызов: следующая волна по тому же ключу не получит
устаревший результат, а выполнит `fn` заново.

## Почему именно так

- **Дедупликация работает.** Окно между «лидер положил `c` в map» и «лидер
  удалил `c`» покрывает всё время `fn`; любой, кто зашёл в это окно, разделит
  результат. Тест держит `fn` на канале `release`, гарантируя, что все 20
  горутин войдут до завершения — и видит `calls == 1`.
- **Нет гонок.** Реестр трогается только под `g.mu`; результат передаётся через
  `wg`-барьер (`Done` happens-before `Wait`, см.
  [модель памяти](/book/memory-model)). `-race` чист.
- **Нет дедлоков.** Ведомые никогда не ждут под `g.mu`; лидер берёт `g.mu` только
  на короткие операции с map.

## Альтернативы и их минусы

- **Канал результата вместо `WaitGroup`.** `call` хранит `done chan struct{}`;
  лидер закрывает его в конце, ведомые делают `<-c.done`. Эквивалентно по смыслу;
  `WaitGroup` чуть лаконичнее для «один сигнал многим».
- **`sync.Map` без явного мьютекса.** Можно `LoadOrStore` структуру `call`
  атомарно. Убирает ручной лок, но логику «кто лидер» всё равно надо выразить
  через возврат `loaded bool`, и удаление сложнее. Выигрыш невелик.
- **Без удаления ключа (кеш результата).** Если оставлять `call` в map, получится
  кеш «навсегда» — но тогда залипнет и ошибка, и устаревшее значение. Для кеша
  нужен отдельный слой с TTL; singleflight отвечает только за дедупликацию
  *одновременных* вызовов.

## Сложность и поведение под нагрузкой

`Do` — O(1) на операцию с map плюс время `fn` у лидера. Память — один `call` на
активный ключ. Contention минимален: мьютекс держится только на доступ к map, а
не на `fn`, поэтому при тысячах одновременных запросов к одному ключу узким
местом становится сам `fn` (один вызов), а не лимитер. Это и есть выигрыш:
N запросов → 1 поход в БД.

## Что спросит интервьюер дальше

- **«Что если `fn` паникует?»** Текущий код не сделает `wg.Done()` → ведомые
  зависнут. Прод-версия ловит панику в `defer` и распространяет её всем.
- **«Чем отличается `DoChan` в x/sync?»** Возвращает канал с результатом —
  удобно для `select` с контекстом/таймаутом.
- **«Что такое `Forget(key)`?»** Принудительно убирает «летящий» вызов, чтобы
  следующий вызвал `fn` заново, не дожидаясь текущего (например, если он завис).
- **«Поле `shared` в результате x/sync?»** Флаг «результат был разделён» —
  диагностика того, что вызовы реально слились.
- **«Как добавить TTL-кеш поверх?»** Слой кеша проверяет значение; при промахе
  идёт через singleflight, чтобы промахи по одному ключу не размножились.

## В проде

Это ровно `golang.org/x/sync/singleflight.Group` — его используют DNS-резолверы,
кеши конфигов, прогрев горячих ключей в Redis/БД. Паттерн «один реальный вызов,
много ожидающих» встречается везде, где дорогой ресурс запрашивают конкурентно:
от загрузки сертификатов до агрегации фичефлагов. На собесе просят написать ядро
руками, чтобы проверить понимание `Mutex` + `WaitGroup` + happens-before.
