## Зачем это на собесе

Singleflight решает «cache stampede»: популярный ключ протух, и сотни горутин
одновременно ломятся в БД за одним и тем же значением. Вместо N одинаковых
запросов выполняется **ровно один**, а его результат раздаётся всем ожидающим.
Это прод-паттерн (его реализует `golang.org/x/sync/singleflight`), и интервьюер
проверяет, умеешь ли ты строить «барьер дедупликации» на `map + Mutex +
WaitGroup` без гонок и дедлоков.

## Что нужно знать

**`sync.WaitGroup` как одноразовый барьер.** Здесь `WaitGroup` используется не
для пула воркеров, а как сигнал «результат готов»: лидер делает `wg.Add(1)`,
считает, потом `wg.Done()`; ожидающие зовут `wg.Wait()` и просыпаются, когда
лидер закончил. См. [sync](/book/sync-primitives).

**`map` под `Mutex` как реестр «летящих» вызовов.** Ключ → указатель на
структуру `call` с результатом. Первый пришедший на ключ становится лидером и
кладёт `call` в map; остальные находят его и ждут.

```go
type call struct {
	wg  sync.WaitGroup
	val interface{}
	err error
}
```

**Разделяемое чтение результата после барьера.** Лидер пишет `c.val`/`c.err` до
`wg.Done()`, ожидающие читают их после `wg.Wait()`. Это корректно: `Wait`/`Done`
дают happens-before (см. [модель памяти](/book/memory-model)), поэтому записи
лидера видны читателям без гонки.

## Идиомы и паттерны

- **Двойная работа с мьютексом.** Мьютекс защищает только сам `map` — он берётся
  на короткое время, чтобы найти/создать `call`, и **отпускается до запуска `fn`**.
  Иначе пока лидер делает медленный сетевой вызов, все остальные стоят на
  мьютексе — никакой дедупликации не выйдет, всё сериализуется.
- **`g.mu.Unlock()` перед `c.wg.Wait()`.** Ожидающий обязан отпустить мьютекс
  *до* ожидания, иначе лидер не сможет удалить запись и случится дедлок.
- **Ленивая инициализация map.** `if g.m == nil { g.m = make(...) }` под
  мьютексом — `Group` используется как нулевое значение `var g Group`.
- **Удаление ключа после завершения.** `delete(g.m, key)` под мьютексом, чтобы
  следующая «волна» по тому же ключу снова выполнила `fn` (свежие данные).

## Подводные камни

- **Держать мьютекс во время `fn`.** Самая частая ошибка: критическая секция
  охватывает медленный вызов. Тогда вызовы не сливаются, а выстраиваются в
  очередь — теряется весь смысл.
- **Дедлок «жду под локом».** Если ожидающий делает `c.wg.Wait()`, не отпустив
  `g.mu`, а лидер в конце берёт `g.mu` для `delete` — обе горутины встают
  навсегда.
- **Гонка на `c.val`/`c.err`.** Запись лидера и чтение ожидающего обязаны быть
  разделены `wg`-барьером. Чтение результата «мимо» `Wait()` — data race под
  `-race`.
- **Паника в `fn`.** Если `fn` паникует, `wg.Done()` может не выполниться →
  ожидающие зависнут навсегда. Прод-версия оборачивает вызов в `defer`/recover.
- **Кеширование «навсегда».** Если не удалять ключ, ошибка одного вызова
  «залипнет» для всех будущих — поэтому запись живёт только на время полёта.

## Как подступиться

1. Поля `Group`: `mu sync.Mutex`, `m map[string]*call`.
2. В `Do`: под мьютексом инициализируй map; если `call` по ключу уже есть —
   **отпусти мьютекс**, `c.wg.Wait()`, верни `c.val, c.err`.
3. Иначе создай `c`, `c.wg.Add(1)`, положи в map, **отпусти мьютекс**.
4. Вне мьютекса: `c.val, c.err = fn()`, затем `c.wg.Done()`.
5. Снова под мьютексом `delete(g.m, key)`; верни результат.
6. Проверь тест: 20 горутин на один ключ → `calls == 1`, у всех одинаковые
   `val`/`err`; разные ключи → отдельные вызовы.
