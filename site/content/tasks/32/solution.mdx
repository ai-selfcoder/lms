## Идея решения

Минимум держат **постоянные** воркеры (без таймера), всплеск — **эластичные**
(с таймером простоя). Диспетчер читает входные задачи и пытается отдать готовому
воркеру неблокирующе; не вышло — поднимает эластичного (пока не упёрся в `max`),
иначе блокирующе ждёт освобождения. Эластичный воркер, не получивший задачу за
`idleTimeout`, выходит сам — так пул сдувается обратно к минимуму. Счётчики
`active`/`peak` живут под мьютексом, и потолок проверяется атомарно с инкрементом.

## Разбор эталона по шагам

Структура разделяет вход, внутреннюю раздачу и учёт:

```go
type ElasticPool struct {
	minWorkers  int
	maxWorkers  int
	idleTimeout time.Duration
	tasks       <-chan func()

	jobs chan func()
	quit chan struct{}

	wg       sync.WaitGroup
	stopOnce sync.Once

	mu     sync.Mutex
	active int
	peak   int
}
```

`tasks` — внешний вход, `jobs` — небуферизованный внутренний канал «диспетчер →
воркер»: передача через него — это и есть «воркер готов». `mu` защищает
`active`/`peak`.

`Start` поднимает `min` постоянных воркеров и диспетчер:

```go
func (p *ElasticPool) Start() {
	for i := 0; i < p.minWorkers; i++ {
		p.spawn(true)
	}
	p.wg.Add(1)
	go p.dispatch()
}
```

`spawn(true)` — постоянные, никогда не засыпают; именно они гарантируют минимум.

`dispatch` тянет задачи и раздаёт:

```go
func (p *ElasticPool) dispatch() {
	defer p.wg.Done()
	for {
		select {
		case <-p.quit:
			return
		case task, ok := <-p.tasks:
			if !ok {
				return
			}
			p.assign(task)
		}
	}
}
```

`assign` — логика эластичности:

```go
func (p *ElasticPool) assign(task func()) {
	for {
		select {
		case p.jobs <- task:
			return
		case <-p.quit:
			return
		default:
		}

		if p.spawn(false) {
			select {
			case p.jobs <- task:
				return
			case <-p.quit:
				return
			}
		}

		select {
		case p.jobs <- task:
			return
		case <-p.quit:
			return
		}
	}
}
```

Три ступени:

1. **Неблокирующая попытка отдать** (`select` с `default`). Если какой-то воркер
   прямо сейчас сидит на `<-p.jobs`, задача уходит мгновенно — лишних воркеров не
   поднимаем.
2. **Свободных нет → `spawn(false)`** поднимает эластичного. Если получилось,
   новый воркер вот-вот встанет на `jobs`; повторяем отдачу уже блокирующе (он
   точно её заберёт).
3. **`spawn` вернул `false` (упёрлись в `max`)** — поднять некого, поэтому
   блокирующе ждём, пока освободится любой воркер (`p.jobs <- task`), либо `quit`.

`spawn` — атомарная проверка потолка и инкремент:

```go
func (p *ElasticPool) spawn(permanent bool) bool {
	p.mu.Lock()
	if p.active >= p.maxWorkers {
		p.mu.Unlock()
		return false
	}
	p.active++
	if p.active > p.peak {
		p.peak = p.active
	}
	p.mu.Unlock()

	p.wg.Add(1)
	go p.worker(permanent)
	return true
}
```

Ключевое: `if active >= max` и `active++` — **под одним локом**. Это снимает
TOCTOU-гонку, иначе два параллельных `spawn` пробили бы `max`. `peak`
обновляется тут же — фиксируем исторический максимум.

Воркер — две ветки логики:

```go
func (p *ElasticPool) worker(permanent bool) {
	defer p.wg.Done()
	defer func() {
		p.mu.Lock()
		p.active--
		p.mu.Unlock()
	}()

	if permanent {
		for {
			select {
			case <-p.quit:
				return
			case task := <-p.jobs:
				task()
			}
		}
	}

	timer := time.NewTimer(p.idleTimeout)
	defer timer.Stop()
	for {
		select {
		case <-p.quit:
			return
		case task := <-p.jobs:
			task()
			if !timer.Stop() {
				select {
				case <-timer.C:
				default:
				}
			}
			timer.Reset(p.idleTimeout)
		case <-timer.C:
			return
		}
	}
}
```

Разберём:

- **`defer active--` под локом** — выполняется при выходе по любой ветке (`quit`,
  idle-timeout). Счётчик всегда консистентен, Active не «зависает».
- **Постоянный воркер** слушает только `quit`/`jobs` — таймера нет, он держит
  минимум вечно.
- **Эластичный воркер** добавляет ветку `<-timer.C`: простояли `idleTimeout` без
  задачи — выходим, пул сдувается.
- **Корректный `Reset`.** После задачи нужно перезапустить таймер. `timer.Stop()`
  возвращает `false`, если таймер уже «выстрелил»; тогда в `timer.C` лежит тик,
  который надо осушить (`select { case <-timer.C: default: }`), иначе
  следующий `select` ложно выйдет «по таймауту». Только после этого `Reset`. Это
  тот самый канонический танец с `time.Timer`, который любят спрашивать.

`Stop` глушит всех через `quit`:

```go
func (p *ElasticPool) Stop() {
	p.stopOnce.Do(func() {
		close(p.quit)
		p.wg.Wait()
	})
}
```

`close(quit)` будит и диспетчер, и всех воркеров (broadcast закрытием); `wg`
учитывает и постоянных, и эластичных, и диспетчер — `Wait` дожидается всех.
`sync.Once` — идемпотентность.

`Peak`/`Active` просто читают счётчики под локом.

## Почему именно так

- **Границы соблюдены.** `active` никогда не пробьёт `max` (атомарная проверка в
  `spawn`) и не упадёт ниже `min` (постоянные воркеры без таймера). Тест проверяет
  `min < Peak ≤ max` под нагрузкой и `Active ≈ min` после простоя.
- **Нет гонок.** Любой доступ к `active`/`peak` — под `mu`; раздача — через
  каналы. Под `-race` чисто.
- **Нет утечек.** Все горутины учтены в `wg` и выходят по `quit`; эластичные
  дополнительно гаснут по idle. `Stop` дожидается всех.

## Альтернативы и их минусы

- **Семафор на буфер-канале вместо подсчёта.** Ограничить параллелизм
  буфером `make(chan struct{}, max)`. Просто для «не больше N», но не выражает
  «min постоянных + idle-timeout для лишних» — нет понятия живого воркера и его
  засыпания. Для эластичности нужен явный учёт.
- **Все воркеры эластичные, без `permanent`.** Тогда минимум не гарантирован:
  длинный простой убьёт всех, и первый же запрос после паузы заплатит за
  холодный старт. `permanent` — это «прогретое ядро».
- **`atomic` вместо мьютекса для счётчиков.** Инкремент/декремент — да, но
  «проверить `< max` и увеличить атомарно» через `atomic` требует CAS-цикла;
  плюс `peak` обновлять синхронно с `active` под одним критерием проще мьютексом.
  При низком contention `Mutex` читаемее и достаточно быстр.
- **Горутина на задачу (`go task()`).** Бесконечная эластичность без потолка —
  всплеск породит сколько угодно горутин, OOM под нагрузкой. Потолок `max` — это
  защита, ради которой пул и существует.

## Сложность и поведение под нагрузкой

Под устойчивой нагрузкой пул быстро выходит на нужное число воркеров (≤ max) и
работает без новых spawn — амортизированно дёшево. Каждый spawn — горутина плюс
короткая критическая секция. Память — O(active) горутин и стеков. Idle-timeout
даёт гистерезис: после всплеска пул сдувается не мгновенно, а через `idleTimeout`
— это сглаживает «дребезг» при рваной нагрузке. Узкое место учёта — общий `mu`,
но критические секции крошечные; при экстремальном contention переходят на
шардированные счётчики.

## Что спросит интервьюер дальше

- **«Почему `min < Peak`, а не `≤`?»** Под всплеском `min` постоянных не хватает,
  диспетчер обязан поднять хотя бы одного эластичного — Peak строго больше min.
- **«Зачем осушать `timer.C` перед `Reset`?»** Иначе оставшийся тик заставит
  следующий `select` ложно выйти «по таймауту» — воркер умрёт, не простаивая.
- **«Как сдержать `spawn` от пробоя `max` при гонке?»** Проверка `active >= max`
  и `active++` — под одним локом; это атомарный «test-and-increment».
- **«Что если задача дольше idleTimeout?»** Пока воркер выполняет `task()`, он не
  в `select` — таймер не «уволит» его посреди работы; `Reset` только после
  возврата `task()`.
- **«Чем это отличается от `ThreadPoolExecutor`?»** Прямая аналогия:
  `minWorkers` ≈ corePoolSize, `maxWorkers` ≈ maximumPoolSize, `idleTimeout` ≈
  keepAliveTime, `tasks`/`jobs` ≈ workQueue.

## В проде

Это модель эластичных пулов везде: Java `ThreadPoolExecutor` (core/max/keepAlive),
пулы соединений к БД (`database/sql` `SetMaxIdleConns`/`SetMaxOpenConns`/
`SetConnMaxIdleTime` — буквально idle-timeout соединений), worker-пулы очередей с
autoscaling. Идея «горячее ядро + временные сверх-воркеры + сон по простою» —
стандарт балансировки между латентностью холодного старта и расходом ресурсов.
