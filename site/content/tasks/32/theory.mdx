## Зачем это на собесе

Постоянный пул фиксированного размера — либо простаивает на затишье, либо не
тянет всплеск. Эластичный пул решает обе беды: держит минимум «горячих»
воркеров, под нагрузкой временно поднимает дополнительных (до потолка), а
простаивающих гасит по таймауту. Так устроены пулы потоков (`ThreadPoolExecutor`
core/max), пулы соединений, autoscaling. Здесь проверяют, умеешь ли ты управлять
**динамическим** числом горутин: считать живых под защитой, не пробить границы
`[min, max]` и завершать лишних по idle-timeout без утечек.

## Что нужно знать

Idle-timeout воркера — это `select`, где наряду с каналом задач сидит таймер. Не
пришла задача за `idleTimeout` — воркер выходит:

```go
timer := time.NewTimer(idle)
for {
    select {
    case task := <-jobs:
        task()
        timer.Reset(idle) // была работа — продлеваем
    case <-timer.C:
        return            // простояли — спим вечным сном
    }
}
```

`time.Timer.Reset` требует аккуратности: перед `Reset` остановленный таймер,
который уже «выстрелил», надо осушить, иначе словите ложное срабатывание. См.
[select](/book/select) о таймерах в выборе и
[sync-примитивы](/book/sync-primitives) о защите счётчиков.

Счётчики `active`/`peak` — общее состояние из многих горутин (диспетчер
инкрементит при spawn, воркер декрементит при выходе), значит мьютекс или атомики.

## Идиомы и паттерны

- **Постоянные vs эластичные воркеры** — флаг `permanent`. Постоянный живёт всегда
  (`min`), эластичный имеет таймер простоя.
- **Диспетчер раздаёт задачи через внутренний канал** — пытается отдать готовому
  воркеру неблокирующе (`select { case jobs<-task: default: }`), не вышло —
  поднимает эластичного, пока не упёрся в `max`, иначе блокирующе ждёт
  освобождения.
- **`spawn` под мьютексом проверяет потолок** `active < max` — атомарно
  «проверить и увеличить», иначе гонка пробьёт границу.
- **`time.Timer` с корректным `Stop`/`Reset`** для idle-timeout.
- **`peak`** обновляется при каждом увеличении `active` под тем же локом.

## Подводные камни

- **Гонка на проверке потолка.** Если `if active < max { active++ }` без лока,
  два диспетчера-потока могут одновременно увидеть «можно» и пробить `max`.
  Проверка и инкремент — под одним мьютексом.

  ```go
  // как НЕ надо: TOCTOU-гонка
  if active < max { // оба прочитали max-1
      active++       // стало max+1
      go worker()
  }
  ```

- **Воркеры опускаются ниже min.** Если все воркеры эластичные с таймером,
  простой убьёт всех и пул «умрёт». Минимум должны держать `permanent`-воркеры
  без таймера.
- **Неверный `Reset` таймера.** `timer.Reset` на «выстреливший» таймер без
  осушения `timer.C` оставит в канале старый тик → следующий `select` мгновенно
  выйдет по «таймауту». Перед `Reset` — `Stop` + дренаж `C`.
- **Утечка/паника при `Stop`.** Динамическое число воркеров; забыли учесть всех в
  `WaitGroup` или закрыли канал задач, в который кто-то пишет → паника или
  зависание (см. [утечки и гонки](/book/leaks-and-races)). Сигнал останова —
  через `close(quit)`, который слушают и воркеры, и диспетчер.
- **Декремент `active` не в `defer`.** Воркер вышел по любой ветке — `active--`
  должен случиться всегда, иначе счётчик «зависнет» и Active соврёт.

## Как подступиться

1. Поля: `min`, `max`, `idle`, входной `tasks <-chan func()`, внутренний `jobs
   chan func()`, `quit chan struct{}`, `wg`, `mu` + `active`/`peak`, `Once`.
2. `Start`: `spawn(true)` ровно `min` раз (постоянные), плюс горутина-диспетчер.
3. `spawn(permanent)`: под локом `if active >= max { return false }`; иначе
   `active++`, обнови `peak`, `go worker(permanent)`, верни `true`.
4. Диспетчер: `for { select { case <-quit: return; case task, ok := <-tasks: ...
   assign(task) } }`.
5. `assign`: попробуй `select { case jobs<-task: default: }`; не вышло — `spawn(false)`
   и повтори отдачу; если `spawn` вернул `false` (упёрлись в max) — блокирующе
   жди `jobs<-task` или `quit`.
6. `worker(permanent)`: постоянный — `select` на `quit`/`jobs`; эластичный —
   плюс ветка `<-timer.C` для выхода по простою, с корректным `Reset` после
   задачи. В `defer` — `active--`.
7. `Stop`: `once.Do(close(quit))` + `wg.Wait()`.
8. Проверь: всплеск поднимает Peak > min (но ≤ max); после простоя Active падает
   к ~min; все задачи выполнены; Stop не виснет.
