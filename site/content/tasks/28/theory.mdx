## Зачем это на собесе

В любом сетевом сервисе у задачи есть «срок годности»: запрос отменили, клиент
отвалился, дедлайн истёк. Воркер-пул, который продолжает молотить уже никому не
нужную задачу, — это занятый воркер, который не берёт полезную работу. Здесь
проверяют, понимаешь ли ты, что [context](/book/context) — это не «ещё один
аргумент», а механизм отмены, на который **исполнитель обязан реагировать**, и
умеешь ли ты построить пул, где отменённая задача мгновенно освобождает воркера.

## Что нужно знать

Контекст несёт сигнал отмены через канал `Done()`, который закрывается при
`cancel()` или дедлайне. Закрытый канал читается без блокировки — это и есть
способ «проснуться» по отмене:

```go
select {
case <-ctx.Done():
    return // нас отменили — выходим
case <-work:
    // ...
}
```

Важно: контекст сам **ничего не прерывает**. Если `Run` крутит `for {}` и не
смотрит на `ctx.Done()`, никакая отмена его не остановит. Отмена — это
кооперативный протокол: вызывающий закрывает `Done()`, а исполнитель должен сам
его проверять. См. главу [context](/book/context) о дереве отмены и о том,
почему отмена не вытесняет горутину.

Сам пул — классический [worker pool](/book/patterns): N горутин читают задачи из
общего канала через `for range`.

## Идиомы и паттерны

- **`for t := range tasks`** — воркер живёт, пока канал открыт; `close(tasks)`
  завершает всех воркеров разом (broadcast через закрытие канала).
- **Передача `ctx` задачи в `Run(ctx)`** — пул не владеет контекстом, он лишь
  прокидывает его в тело задачи, чтобы та могла реагировать на отмену.
- **Быстрый отказ через `select { case <-ctx.Done(): default: }`** — если
  контекст уже мёртв до старта, нет смысла даже звать `Run`.
- **`sync.WaitGroup` + `sync.Once`** для корректного `Stop`: закрыть канал один
  раз и дождаться всех воркеров.

## Подводные камни

- **Воркер сам блокирует `Run` вместо отмены.** Если думать «я в воркере сделаю
  `select` на `ctx.Done()` и брошу `Run`» — это не работает: запущенную
  `Run(ctx)` нельзя «отнять» из вне, горутина с ней останется висеть. Реагировать
  на отмену обязан **сам `Run`**, а воркер свободен ровно тогда, когда `Run`
  вернулся.

  ```go
  // как НЕ надо: Run всё равно крутится в фоне, воркер «свободен» формально,
  // а горутина утекла
  go t.Run(ctx)
  select { case <-ctx.Done(): }
  ```

- **Double-close канала задач.** `Stop`, вызванный дважды, паникует на повторном
  `close`. Лечится `sync.Once`.
- **Утечка на `Stop`.** Забыли `wg.Wait()` — `Stop` вернулся, а воркеры ещё
  живы; если они пишут в закрытые/общие структуры, словите гонку (см.
  [утечки и гонки](/book/leaks-and-races)).
- **`nil`-контекст.** `t.Ctx` может быть `nil`; `ctx.Done()` по `nil` паникует.
  Нужно отдельно обработать «контекста нет».

## Как подступиться

1. Заведи небуферизованный `tasks chan CtxTask` и `sync.WaitGroup`.
2. `Start`: запусти `workers` горутин, каждая — `for t := range p.tasks`.
3. В теле воркера: если `t.Run == nil` — пропусти; если `t.Ctx == nil` — просто
   позови `t.Run(nil)`.
4. Перед запуском проверь `select { case <-ctx.Done(): continue; default: }` —
   отменённую до старта задачу не выполняем.
5. Иначе зови `t.Run(ctx)` **синхронно** — пусть сам `Run` реагирует на отмену;
   как только он вернулся, воркер берёт следующую задачу.
6. `Stop`: `once.Do(close(tasks))` + `wg.Wait()`.
7. Проверь сценарий: пул из 1 воркера, первая задача висит на `<-ctx.Done()`,
   отмена контекста должна освободить воркера для следующей задачи.
