## Идея решения

Обычный воркер-пул на канале задач, но каждая задача несёт свой `ctx`, и воркер
прокидывает его в `Run(ctx)` **синхронно**. Воркер не пытается «прервать» задачу
извне — он лишь даёт ей контекст и ждёт возврата. Ответственность за реакцию на
отмену лежит на самой `Run`; как только она вернулась (нормально или по отмене),
воркер свободен. Это ключевой инвариант: занятость воркера = «`Run` ещё не
вернулась», не больше и не меньше.

## Разбор эталона по шагам

Структура пула — канал задач, `WaitGroup` для воркеров и `Once` для безопасного
закрытия:

```go
type CtxPool struct {
	workers int
	tasks   chan CtxTask
	wg      sync.WaitGroup
	once    sync.Once
}
```

Канал `tasks` небуферизованный: `Submit` блокируется, пока какой-то воркер не
готов принять задачу. Это важно для теста «отменённая задача освобождает
воркера» — `Submit` следующей задачи висит, пока занятый воркер не освободится.

`Start` поднимает воркеров. `wg.Add` делается **до** запуска горутин, иначе
возможна гонка с `wg.Wait` в `Stop`:

```go
func (p *CtxPool) Start() {
	p.wg.Add(p.workers)
	for i := 0; i < p.workers; i++ {
		go p.work()
	}
}
```

Сердце — цикл воркера:

```go
func (p *CtxPool) work() {
	defer p.wg.Done()
	for t := range p.tasks {
		if t.Run == nil {
			continue
		}
		ctx := t.Ctx
		if ctx == nil {
			t.Run(nil)
			continue
		}
		select {
		case <-ctx.Done():
			continue
		default:
			t.Run(ctx)
		}
	}
}
```

Разберём по частям:

- **`for t := range p.tasks`** — воркер живёт, пока канал открыт. `close(tasks)`
  в `Stop` завершит цикл во всех воркерах сразу.
- **`t.Run == nil` / `t.Ctx == nil`** — защита от вырожденных задач: пустую
  пропускаем, бесконтекстную выполняем как есть. Без проверки `nil`-контекста
  `ctx.Done()` ниже паникует.
- **`select { case <-ctx.Done(): continue; default: }`** — быстрый отказ. Если
  контекст уже отменён к моменту, когда воркер взял задачу, ветка `Done()`
  сработает мгновенно, и мы перейдём к следующей задаче, не вызывая `Run`.
  `default` нужен, чтобы не блокироваться, когда контекст ещё жив, — тогда
  выполняется `t.Run(ctx)`.
- **`t.Run(ctx)` — синхронно.** Вот главный момент. Мы не запускаем `Run` в
  отдельной горутине и не пытаемся «отобрать» её по `ctx.Done()`. Воркер просто
  ждёт возврата `Run`. Если внутри `Run` написано `<-ctx.Done()`, то при отмене
  контекста `Run` вернётся сама — и воркер освободится. Именно так устроен тест:
  зависшая задача делает `<-c.Done()`, `cancel()` будит её, `Run` возвращается,
  воркер берёт следующую задачу.

`Stop` закрывает канал один раз и ждёт воркеров:

```go
func (p *CtxPool) Stop() {
	p.once.Do(func() {
		close(p.tasks)
	})
	p.wg.Wait()
}
```

`sync.Once` защищает от двойного `close` (паники), `wg.Wait()` гарантирует, что
после `Stop` ни одной живой горутины пула не осталось.

## Почему именно так

- **Нет утечки горутин.** Воркеров ровно `workers`, и все завершаются по
  `close(tasks)`. `Run` выполняется в той же горутине воркера — никаких
  «осиротевших» горутин с задачей.
- **Нет «застрявшего» воркера** при условии, что `Run` уважает контекст. Воркер
  занят ровно столько, сколько работает `Run`; отмена контекста — это сигнал
  именно для `Run`. Тест с пулом из одного воркера это и ловит.
- **Нет гонок.** Общее состояние — только канал и `WaitGroup`, оба
  потокобезопасны. Под `-race` чисто.

## Альтернативы и их минусы

- **Запускать `Run` в отдельной горутине и «бросать» по `ctx.Done()`.** Соблазн:
  воркер делает `go Run(ctx)` и `select` на `Done()`, чтобы «освободиться»
  быстрее. Минус фатальный — `Run` нельзя прервать снаружи, горутина с ней
  останется висеть до собственного возврата. Получаем утечку и иллюзию контроля.
  Контекст в Go **кооперативный**: отменить можно только то, что само проверяет
  отмену.
- **Буферизованный `tasks`.** Ускоряет `Submit`, но ломает обратное давление:
  очередь растёт без границ, а тест на «освобождение воркера» становится
  недетерминированным. Для этой задачи небуферизованный канал точнее выражает
  семантику.
- **Один общий контекст на весь пул.** Не подходит: по условию у каждой задачи
  свой `Ctx`, отмена одной не должна влиять на другие.

## Сложность и поведение под нагрузкой

Память — O(workers) горутин плюс канал. Пропускная способность ограничена числом
воркеров: задачи сериализуются на небуферизованном канале. Аллокаций на задачу
нет (структура `CtxTask` передаётся по значению, без боксинга). Под высокой
нагрузкой узкое место — `Submit`, который блокируется при всех занятых воркерах;
это и есть встроенное обратное давление.

## Что спросит интервьюер дальше

- **«А если `Run` игнорирует контекст?»** Тогда воркер будет занят до её
  естественного конца — пул бессилен. Отмена работает только при кооперации;
  для жёсткого прерывания нужен другой механизм (отдельный процесс, `os` сигналы).
- **«Как ограничить время выполнения каждой задачи сверху?»** Оборачивать в
  `context.WithTimeout(t.Ctx, d)` перед `Run` и не забыть `cancel()`.
- **«Сколько горутин после `Stop`?»** Ровно ноль воркеров: `close` + `wg.Wait()`.
- **«Почему `Add` до `go`, а не внутри горутины?»** Иначе `Stop` мог бы вызвать
  `Wait()` раньше, чем горутина сделала `Add`, — гонка и преждевременный выход.
- **«Что вернёт `Submit` после `Stop`?»** Паника: запись в закрытый канал. В
  проде это закрывают флагом/`select` с `done` или отдельным методом.

## В проде

Тот же приём — «прокинь контекст вглубь, реагируй на `Done()`» — лежит в основе
`net/http` (`Request.Context()` отменяется при разрыве соединения),
`database/sql` (`QueryContext` прерывает запрос по отмене) и
`golang.org/x/sync/errgroup` с `WithContext`. Везде один принцип: контекст —
кооперативный сигнал, исполнитель обязан его проверять. См.
[context](/book/context) и [паттерны](/book/patterns).
