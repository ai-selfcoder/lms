## Идея решения

На каждую задачу — отдельная горутина с `time.Ticker`, которая по тику кладёт
функцию задачи в общий канал. Фиксированный пул воркеров разбирает этот канал и
исполняет функции. Завершение строго двухфазное: сначала глушим тикеры
(продюсеров), затем закрываем канал и дожидаемся воркеров (консьюмеров) — иначе
тик попадёт в закрытый канал и всё упадёт.

## Разбор эталона по шагам

Структура разводит продюсеров и консьюмеров и держит два `WaitGroup`:

```go
type Scheduler struct {
	workers int
	jobs    []scheduledJob

	tasks chan func()
	quit  chan struct{}

	tickerWG sync.WaitGroup
	workerWG sync.WaitGroup

	stopOnce sync.Once
}
```

`tasks` буферизован (`make(chan func(), 1024)`) — всплеск тиков не блокирует
тикеры мгновенно. Два отдельных `WaitGroup` нужны именно потому, что тикеры и
воркеры останавливаются в **разные** фазы.

`Add` просто копит задачи (вызывается до `Start`):

```go
func (s *Scheduler) Add(interval time.Duration, job func()) {
	s.jobs = append(s.jobs, scheduledJob{interval: interval, job: job})
}
```

`Start` поднимает пул и по тикеру на задачу:

```go
func (s *Scheduler) Start() {
	for i := 0; i < s.workers; i++ {
		s.workerWG.Add(1)
		go s.worker()
	}
	for _, j := range s.jobs {
		s.tickerWG.Add(1)
		go s.runTicker(j)
	}
}
```

Воркер предельно прост — тянет функции из канала, пока он открыт:

```go
func (s *Scheduler) worker() {
	defer s.workerWG.Done()
	for fn := range s.tasks {
		fn()
	}
}
```

`for fn := range s.tasks` завершится ровно при `close(tasks)` — это сигнал
консьюмерам.

Тикер — продюсер с двойной защитой от `quit`:

```go
func (s *Scheduler) runTicker(j scheduledJob) {
	defer s.tickerWG.Done()
	ticker := time.NewTicker(j.interval)
	defer ticker.Stop()
	for {
		select {
		case <-s.quit:
			return
		case <-ticker.C:
			select {
			case s.tasks <- j.job:
			case <-s.quit:
				return
			}
		}
	}
}
```

Здесь два важных места:

- **`defer ticker.Stop()`** — обязательная очистка тикера; без неё внутренний
  таймер рантайма остаётся жить.
- **Вложенный `select` на отправке.** Внешний `select` ловит тик, но между тиком
  и отправкой планировщик мог уйти в `Stop`. Если просто написать `s.tasks <-
  j.job`, отправка может зависнуть (буфер полон, воркеры выходят) — горутина
  утечёт. Вложенный `select { case s.tasks <- j.job: case <-s.quit: return }`
  гарантирует выход по сигналу останова даже посреди отправки.

Останов — двухфазный, под `Once`:

```go
func (s *Scheduler) Stop() {
	s.stopOnce.Do(func() {
		close(s.quit)
		s.tickerWG.Wait()
		close(s.tasks)
		s.workerWG.Wait()
	})
}
```

Порядок здесь — не косметика, а корректность:

1. **`close(s.quit)`** — все тикеры получают сигнал и начинают выходить.
2. **`s.tickerWG.Wait()`** — дожидаемся, пока **все** тикеры точно завершились.
   Только теперь гарантировано, что никто больше не напишет в `tasks`.
3. **`close(s.tasks)`** — безопасно: продюсеров уже нет, send-on-closed
   невозможен. Закрытие завершает `for range` в воркерах.
4. **`s.workerWG.Wait()`** — дожидаемся воркеров; буфер при этом дочитывается.

`sync.Once` делает `Stop` идемпотентным — повторный вызов не закроет каналы
дважды.

## Почему именно так

- **Нет паники send-on-closed.** `tasks` закрывается только после `tickerWG.Wait`
  — единственные писатели уже мертвы.
- **Нет утечки горутин.** Тикеры выходят по `quit` (в т.ч. посреди отправки),
  воркеры — по `close(tasks)`; оба ждутся `WaitGroup`. Тест меряет
  `runtime.NumGoroutine()` и не должен видеть прироста.
- **Нет «зомби»-запусков.** После `Stop` тикеры остановлены, новых `job` в канал
  не попадёт; тест проверяет, что счётчик не растёт после паузы.
- **Под `-race` чисто** — общее состояние только каналы и `WaitGroup`.

## Альтернативы и их минусы

- **Горутина-исполнитель на задачу (`for { <-ticker.C; job() }`).** Проще, но
  если `job()` дольше интервала, она задержит следующий тик именно этой задачи, и
  число «рабочих» горутин = числу задач. Пул же делит исполнителей и сглаживает
  нагрузку. Под много задач пул — управляемее.
- **`time.AfterFunc` на каждое срабатывание.** `AfterFunc` сам запускает функцию
  в **своей** горутине из пула таймеров — теряется контроль над параллелизмом
  (можно словить всплеск одновременных запусков) и сложнее чисто остановить.
  Для разовых отложенных задач `AfterFunc` хорош, для управляемой периодики —
  тикер+пул честнее.
- **Один тикер с минимальным шагом + проверка «кому пора».** Колесо таймеров
  (timing wheel) — масштабируется на десятки тысяч задач, но это заметно сложнее;
  для десятков задач «тикер на задачу» проще и достаточно.
- **Закрыть `tasks` первым.** Перевернутый порядок в `Stop` ломает всё:
  очередной тик пишет в закрытый канал → паника. Двухфазность обязательна.

## Сложность и поведение под нагрузкой

Горутин — `workers + len(jobs)` (тикеры) + диспетчерских таймеров рантайма по
числу тикеров. Память — O(задач) под тикеры и буфер канала. Узкое место —
если суммарная нагрузка тиков превышает пропускную способность пула, буфер
наполняется и тикеры начинают ждать на отправке (через `select` с `quit` — без
зависания). Это естественное обратное давление: лишние тики не теряются молча, а
притормаживают продюсеров. Точность периода ограничена планировщиком и
гранулярностью таймеров (десятки мкс — мс).

## Что спросит интервьюер дальше

- **«Что если задача дольше своего интервала?»** Тики копятся в буфере, пул
  выполняет их с отставанием; при переполнении тикеры притормаживают. Часто
  хотят «не накапливать» — тогда дропают тик при занятом воркере
  (`select { case tasks<-job: default: }`).
- **«Как добавлять задачи после `Start`?»** Защитить `jobs` мьютексом и стартовать
  новый тикер на лету — текущий код принимает задачи только до `Start`.
- **«Зачем два `WaitGroup`, нельзя один?»** Один не различает фазы: нужно
  дождаться *именно тикеров* перед `close(tasks)`. С одним `WaitGroup` порядок не
  выразить.
- **`time.Ticker.Stop()` закрывает канал `C`?»** Нет, только перестаёт слать
  тики. Поэтому выход из тикера — по `quit`, а не по закрытию `C`.
- **«Как сделать первый запуск немедленным?»** Выполнить `job` один раз до цикла
  или использовать тикер с отдельным начальным таймером.

## В проде

Это упрощённая модель `robfig/cron` и встроенных шедулеров (Kubernetes CronJob,
периодические reconcile-loops в контроллерах). Связка «источник времени
(`Ticker`) + пул исполнителей + кооперативный graceful stop» — стандарт. Под
огромное число таймеров реальные системы переходят на timing wheel (так устроены
таймеры в Netty, в ядре Linux). Базовые кирпичи — `time.Ticker`,
`time.AfterFunc`, [select](/book/select), [паттерны](/book/patterns) и
[sync-примитивы](/book/sync-primitives).
