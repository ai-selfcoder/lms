## Зачем это на собесе

Периодические задачи есть в каждом сервисе: обновить кэш каждые 30с, собрать
метрики каждые 5с, разослать дайджест раз в час. Наивно — «горутина с `for {
sleep; do }` на каждую задачу», но под сотни задач это сотни горутин и неуправляемое
завершение. Здесь проверяют, умеешь ли ты развести **планирование** (когда
запускать) и **исполнение** (кто запускает) — тикеры решают «когда», общий
[воркер-пул](/book/patterns) решает «кем», — и чисто всё это остановить без
утечек.

## Что нужно знать

`time.Ticker` шлёт значение в канал `C` с заданным периодом — идеальный источник
«пора запускать»:

```go
t := time.NewTicker(interval)
defer t.Stop() // обязательно: иначе тикер живёт и течёт
for range t.C {
    // настало время
}
```

`Ticker.Stop()` **не закрывает** канал `C`, он лишь перестаёт слать тики; забыть
`Stop` — утечка ресурса тикера. См. [select](/book/select) о том, как слушать
тикер вместе с сигналом останова.

Пул — N воркеров, читающих из общего канала задач через `for fn := range tasks`.
Разводя «по тикеру на задачу» от «фиксированного пула исполнителей», мы держим
число горутин под контролем.

## Идиомы и паттерны

- **Тикер-горутина на задачу** кладёт `job` в общий канал по каждому тику —
  «продюсер».
- **Пул воркеров** разбирает общий канал — «консьюмеры». Так редкая задача не
  занимает выделенную горутину-исполнитель.
- **Два этапа завершения через два `WaitGroup`**: сначала остановить продюсеров
  (тикеры), потом закрыть канал и дождаться консьюмеров (воркеров). Порядок
  критичен.
- **`select` тика против `quit`** — и при тике, и при отправке в канал слушать
  `quit`, чтобы не повиснуть на отправке в момент останова.
- **`sync.Once`** вокруг `Stop` — идемпотентность.

## Подводные камни

- **Запись в закрытый канал → паника.** Если в `Stop` закрыть `tasks` раньше, чем
  остановлены тикеры, очередной тик попытается `tasks <- job` в закрытый канал и
  упадёт. Отсюда строгий порядок: **сначала** глушим тикеры, **потом** закрываем
  канал.

  ```go
  // как НЕ надо
  close(tasks)        // а тикер ещё жив...
  // ...тик → tasks <- job → panic: send on closed channel
  ```

- **Блокировка на отправке при останове.** Тик случился, воркеры уже выходят,
  буфер полон — `tasks <- job` виснет навсегда. Нужен `select { case tasks<-job:
  case <-quit: return }`.
- **Забыли `ticker.Stop()`.** Утечка тикера (внутренний таймер рантайма живёт).
- **Утечка горутин при `Stop`.** Не дождались `WaitGroup` — тикеры/воркеры ещё
  крутятся, а тест меряет `runtime.NumGoroutine()` и поймает прирост (см.
  [утечки и гонки](/book/leaks-and-races)).
- **«Зомби»-запуски после Stop.** Если задача может попасть в канал уже после
  сигнала останова, она выполнится после `Stop` — тест это ловит, сравнивая
  счётчик до и после паузы.

## Как подступиться

1. Храни список задач (`interval`, `job`), общий `tasks chan func()` (с буфером),
   `quit chan struct{}`, два `WaitGroup` — для тикеров и воркеров — и `Once`.
2. `Start`: подними `workers` воркеров (`for fn := range tasks { fn() }`) и по
   горутине-тикеру на каждую задачу.
3. Тикер: `for { select { case <-quit: return; case <-ticker.C: ... } }`. На тике
   — отправь `job` в `tasks`, но через `select` с `quit`, чтобы не зависнуть.
4. `Stop` (под `Once`): `close(quit)` → `tickerWG.Wait()` → `close(tasks)` →
   `workerWG.Wait()`. Именно в этом порядке.
5. Проверь: частая задача (20мс) выполняется заметно чаще редкой (100мс); после
   `Stop` счётчик не растёт; `NumGoroutine` возвращается к базе.
