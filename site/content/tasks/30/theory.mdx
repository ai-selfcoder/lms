## Зачем это на собесе

Деплой, SIGTERM от Kubernetes, ротация подов — сервису дают конечное время на
завершение (`terminationGracePeriodSeconds`), и нужно: перестать брать новую
работу, доделать что успеешь, а про недоделанное честно сообщить (вернуть в
очередь, залогировать, заалертить). Это классический graceful shutdown. Здесь
проверяют, умеешь ли ты остановить пул **с ограничением по времени** и точно
знать, какие задачи остались «в полёте».

## Что нужно знать

Два независимых события — «воркеры доделали всё» и «время вышло» — сводятся
одним `select`. Завершение `WaitGroup` нельзя ждать в `select` напрямую, поэтому
его оборачивают в горутину, которая закрывает канал:

```go
finished := make(chan struct{})
go func() { wg.Wait(); close(finished) }()

select {
case <-finished:           // успели
case <-time.After(timeout): // не успели
}
```

`time.After` возвращает канал, который «выстрелит» через заданное время — готовый
таймаут для [select](/book/select). См. также [context](/book/context):
`context.WithTimeout` — тот же дедлайн, но для отмены вглубь.

Чтобы знать, кто не успел, нужно отслеживать **множество выполняющихся прямо
сейчас** ID — добавлять при старте задачи, удалять при завершении. Это общее
состояние из многих горутин, значит — мьютекс (см.
[sync-примитивы](/book/sync-primitives)).

## Идиомы и паттерны

- **`done chan struct{}` как сигнал «не брать новое»** + `close(done)` —
  broadcast всем воркерам разом.
- **`select` в воркере на `done` и на канал задач** — воркер либо берёт задачу,
  либо видит сигнал останова.
- **`map[int]struct{}` под мьютексом** — множество in-flight ID; `struct{}` не
  занимает память на значениях.
- **`WaitGroup` + горутина-обёртка** для «ждать, но с таймаутом».
- **Снимок незавершённых под локом** — пройти по `map` и собрать оставшиеся ID.

## Подводные камни

- **`Stop`, который ждёт всех безусловно.** `wg.Wait()` без таймаута повиснет на
  медленной задаче на 1с/10с/навсегда. Условие требует вернуться **примерно за
  таймаут**, не дожидаясь застрявших.
- **Гонка на множестве in-flight.** `map` пишется из воркеров (`markStart`/
  `markDone`) и читается в `Stop` — без мьютекса это `concurrent map writes`
  panic или гонка (см. [утечки и гонки](/book/leaks-and-races)).

  ```go
  // как НЕ надо: конкурентная запись в map без лока
  inFlight[id] = struct{}{} // из воркера
  delete(inFlight, id)      // из другого воркера → panic/race
  ```

- **Воркер не реагирует на `done`.** Если воркер только `range tasks` и не
  слушает `done`, при незакрытом канале задач он не остановится. Нужен `select`
  на оба источника.
- **Состояние гонки на самой задаче.** Если задача доделается ровно в момент
  таймаута, важно, чтобы `markDone` под тем же локом убрал её из множества — иначе
  получите ложно-«незавершённую».

## Как подступиться

1. Структура: `tasks <-chan Job`, `done chan struct{}`, `wg sync.WaitGroup`,
   `mu` + `inFlight map[int]struct{}`.
2. Воркер: `for { select { case <-done: return; case job, ok := <-tasks: ... } }`.
   При получении задачи — `markStart(id)`, `job.Run()`, `markDone(id)`.
3. `markStart`/`markDone` — добавление/удаление в `inFlight` под мьютексом.
4. `Stop(timeout)`: `close(done)`, затем гонка `finished` против
   `time.After(timeout)` через `select`.
5. После `select` — под локом собрать оставшиеся в `inFlight` ID и вернуть их.
6. Проверь: быстрые задачи (< timeout) ушли из множества и не попали в результат;
   медленные, ещё крутящиеся, — попали; `Stop` вернулся за ~timeout, а не за 1с.
