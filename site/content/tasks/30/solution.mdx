## Идея решения

Воркеры читают задачи и для каждой держат запись «я её сейчас выполняю» в
множестве `inFlight` (по ID) под мьютексом: добавили перед `Run`, удалили после.
`Stop` закрывает `done` (воркеры перестают брать новое), затем ждёт завершения
текущих **не дольше таймаута** через гонку `WaitGroup` против `time.After`. Что
осталось в `inFlight` по истечении времени — те самые незавершённые ID.

## Разбор эталона по шагам

Структура: вход, сигнал останова, `WaitGroup` и защищённое множество in-flight:

```go
type Pool struct {
	tasks   <-chan Job
	workers int

	done chan struct{}
	wg   sync.WaitGroup

	mu       sync.Mutex
	inFlight map[int]struct{}
}
```

Воркер слушает **оба** источника — сигнал останова и канал задач:

```go
func (p *Pool) worker() {
	defer p.wg.Done()
	for {
		select {
		case <-p.done:
			return
		case job, ok := <-p.tasks:
			if !ok {
				return
			}
			p.markStart(job.ID)
			if job.Run != nil {
				job.Run()
			}
			p.markDone(job.ID)
		}
	}
}
```

- **`select` на `p.done` и `p.tasks`.** `close(done)` в `Stop` мгновенно будит
  все воркеры (broadcast закрытием), и они выходят, не дожидаясь новых задач.
  Ветка `case job, ok := <-p.tasks` с проверкой `ok` корректно завершает воркера
  и если входной канал закрыли извне.
- **`markStart` → `Run` → `markDone`.** Ключевая последовательность: задача
  считается «в полёте» ровно пока крутится её `Run`. Если в момент таймаута
  `Run` ещё не вернулась, запись в множестве осталась — и попадёт в результат.
- **Важная тонкость.** Воркер, уже зашедший в `Run`, **не реагирует** на `done`
  до завершения `Run` — `done` проверяется только в начале цикла. Это намеренно:
  мы не прерываем текущую задачу, а даём ей доделаться (или истечь таймауту).

Учёт in-flight — под мьютексом:

```go
func (p *Pool) markStart(id int) {
	p.mu.Lock()
	p.inFlight[id] = struct{}{}
	p.mu.Unlock()
}

func (p *Pool) markDone(id int) {
	p.mu.Lock()
	delete(p.inFlight, id)
	p.mu.Unlock()
}
```

`map[int]struct{}` — множество без значений. Оба метода зовутся из разных
воркеров, поэтому каждый доступ — под `mu`. Без лока это `concurrent map writes`.

Сердце — `Stop`:

```go
func (p *Pool) Stop(timeout time.Duration) []int {
	close(p.done)

	finished := make(chan struct{})
	go func() {
		p.wg.Wait()
		close(finished)
	}()

	select {
	case <-finished:
	case <-time.After(timeout):
	}

	p.mu.Lock()
	unfinished := make([]int, 0, len(p.inFlight))
	for id := range p.inFlight {
		unfinished = append(unfinished, id)
	}
	p.mu.Unlock()
	return unfinished
}
```

Разберём:

- **`close(p.done)`** — воркеры перестают брать новые задачи. Те, кто уже внутри
  `Run`, доделывают (или нет — это решит таймаут).
- **`wg.Wait()` в отдельной горутине + `close(finished)`.** `Wait()` сам по себе
  блокирующий и его нельзя положить в `select`. Обёртка превращает «все
  завершились» в читаемый из `select` канал.
- **`select { case <-finished: case <-time.After(timeout): }`** — гонка двух
  событий. Если все воркеры успели — выходим по `finished` раньше таймаута. Если
  застряла медленная задача — выходим по `time.After`, **не дожидаясь** её. Это
  и даёт тест `StopReturnsPromptly`: `Stop` возвращается за ~100мс, а не за 1с.
- **Снимок `inFlight` под локом.** Всё, что осталось в множестве после `select`,
  — задачи, чья `Run` ещё крутится. Собираем их ID в срез (ёмкость
  предвыделена под `len`) и возвращаем. Быстрые задачи к этому моменту уже сделали
  `markDone` и в множестве отсутствуют.

## Почему именно так

- **Stop всегда возвращается за разумное время.** Верхняя граница — `timeout`
  (плюс копейки на снимок). Медленная задача не держит `Stop`.
- **Результат точный.** Инвариант «в `inFlight` ровно те, чья `Run` сейчас
  выполняется» поддерживается парой `markStart`/`markDone` под общим локом.
  Быстрые ушли, медленные остались — ровно как в тесте (`{100, 101}`).
- **Нет гонок.** Множество читается/пишется только под `mu`; `WaitGroup` и
  закрытие каналов потокобезопасны. Под `-race` чисто.

## Альтернативы и их минусы

- **`context.WithTimeout` вместо `done`+`time.After`.** Идиоматично и красиво:
  `ctx, cancel := WithTimeout(...)`, воркеры и `Run` слушают `ctx.Done()`. Но это
  работает, только если **сама `Run` уважает контекст**. В этой задаче `Run` —
  непрозрачная `func()` без контекста, прервать её нельзя; поэтому мы и считаем
  «незавершённые», а не «отменяем». Если бы у задач был контекст — `context` был
  бы предпочтительнее.
- **Считать незавершённые через счётчик, а не множество.** Счётчик скажет
  «сколько», но не «какие именно ID». Условие требует вернуть конкретные ID —
  нужно множество.
- **`atomic` вместо мьютекса для множества.** На `map` атомиков нет; пришлось бы
  городить `sync.Map`, что для «собрать снимок ключей» неудобнее обычного
  `Mutex`. Здесь contention низкий — простой `Mutex` оптимален.
- **Жёстко убивать задачи по таймауту.** В Go горутину нельзя прервать снаружи;
  «убить» можно только кооперативно через контекст. Поэтому мы фиксируем факт
  «не успела», а не прерываем.

## Сложность и поведение под нагрузкой

`markStart`/`markDone` — O(1) под коротким локом; contention растёт с числом
воркеров, но критическая секция крошечная (одна вставка/удаление в map). Снимок в
`Stop` — O(in-flight). Память — O(одновременно выполняемых задач). Под нагрузкой
узкое место не в учёте, а в самих задачах; `Stop` ограничен сверху таймаутом
независимо от числа застрявших.

## Что спросит интервьюер дальше

- **«Как сделать задачи прерываемыми?»** Дать `Job` контекст
  (`Run(ctx)`), в `Stop` отменять его; тогда уважающие контекст задачи завершатся
  досрочно, а не попадут в «незавершённые».
- **«Куда девать незавершённые ID в проде?»** Вернуть в очередь/в `requeue`,
  записать в WAL, заалертить — чтобы их подхватил следующий инстанс.
- **«Почему `Wait` в горутине, а не просто `Wait`?»** Чтобы его можно было
  положить в `select` против таймаута; голый `Wait` заблокировал бы `Stop`.
- **«Гонка: задача доделалась ровно в момент таймаута — она в результате?»**
  Зависит от того, успел ли `markDone` взять лок до снимка. Оба под одним `mu`,
  так что результат консистентен — либо «успела», либо «нет», без порчи данных.
- **«Что если `Stop` вызвать дважды?»** Второй `close(done)` паникует — в проде
  оборачивают в `sync.Once`.

## В проде

Это ровно модель graceful shutdown HTTP-сервера: `http.Server.Shutdown(ctx)`
перестаёт принимать соединения и ждёт активные запросы до дедлайна контекста.
Тот же паттерн — в Kubernetes (`SIGTERM` → grace period →`SIGKILL`), в воркерах
очередей (доделать текущие сообщения, остальное вернуть в очередь). Сводка
«гонка `Wait` против `time.After`» — стандартный приём для «ждать, но не вечно».
