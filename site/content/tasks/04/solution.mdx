## Идея решения

Два `select` подряд. Первый — неблокирующая попытка прочитать `high` (с
`default`): пока в high есть данные, мы обрабатываем только его. Когда high пуст
прямо сейчас — переходим во второй, блокирующий `select` по обоим каналам, что
даёт low шанс и не жжёт процессор. Закрытые каналы обнуляются в `nil` и выходят
из игры; цикл живёт, пока жив хоть один канал.

## Разбор эталона по шагам

Аккумулятор и условие цикла:

```go
result := make([]int, 0)

for high != nil || low != nil {
	...
}
return result
```

Цикл крутится, пока хотя бы один канал не `nil`. Обнуление закрытого канала —
способ «выключить» его, поэтому условие `high != nil || low != nil` и есть
корректное «пока не закрыты оба».

Шаг 1 — приоритетная неблокирующая попытка high:

```go
select {
case v, ok := <-high:
	if !ok {
		high = nil
		continue
	}
	result = append(result, v)
	continue
default:
}
```

`default` делает попытку неблокирующей: если в high прямо сейчас есть значение —
берём его и `continue` (снова к высокому приоритету); если high закрыт —
`high = nil` и `continue`; если high просто пуст — падаем в `default` и идём
дальше. Именно это даёт high приоритет: пока в нём что-то есть, до low мы не
доходим.

Шаг 2 — блокирующее ожидание любого из каналов:

```go
select {
case v, ok := <-high:
	if !ok {
		high = nil
		continue
	}
	result = append(result, v)
case v, ok := <-low:
	if !ok {
		low = nil
		continue
	}
	result = append(result, v)
}
```

Сюда мы попадаем, только когда high пуст в этот момент. Блокирующий `select`
(без `default`) честно ждёт, что появится первым, — и так low получает шанс
быть обработанным, а процессор не крутится вхолостую. Если высокоприоритетный
канал снова наполнится, мы вернёмся к нему на шаге 1 следующей итерации.

Закрытие любого канала обнуляет его переменную; `nil`-канал в `select`
блокируется навсегда, то есть ветка фактически отключается, и `select` ждёт
только оставшийся живой канал.

## Почему именно так

- **Приоритет high.** `TestProcessPriorityHighFirst` предзаполняет оба канала и
  требует, чтобы до первого low прошло минимум 3 из 5 high. Шаг 1 с `default`
  жадно вычерпывает high первым.
- **Нет голодания low.** Между «пачками» high шаг 2 — блокирующий `select`, где
  low равноправен. `TestProcessPriorityNoStarvation` (50 high + 5 low) требует
  все 5 low — если бы их не давали обработать, отправитель low завис бы и тест
  упал по таймауту.
- **Нет busy-loop.** `default` ведёт не в пустой `continue`, а во второй,
  блокирующий `select`, который усыпляет горутину до появления данных.
- **Корректное завершение.** Обнуление в `nil` гасит ветки закрытых каналов;
  когда оба `nil` — цикл выходит. `TestProcessPriorityOnlyLow` проверяет
  завершение даже при пустом high.

## Альтернативы и их минусы

- **Один `select` без приоритета.** Проще, но даёт равновероятный выбор —
  приоритет high теряется. Не проходит `HighFirst`.
- **Жадное чтение high в внутреннем цикле без выхода к low.** Сильный
  приоритет, но при бесконечном потоке high low голодает и его отправитель
  виснет. Двухступенчатая схема — компромисс: «high вперёд, но low не забыт».
- **Приоритетная очередь (heap) с мьютексом.** Если приоритетов много или нужна
  строгая упорядоченность — да. Но для двух каналов это оверинжиниринг:
  `select` решает задачу без структур данных и блокировок.

## Сложность и поведение под нагрузкой

Каждое значение проходит через один-два `select` — O(1) на элемент, всего O(N).
`result` растёт через `append` с амортизированным удвоением; при известном
размере можно было бы предвыделить `make([]int, 0, n)`. Память — линейна по
числу обработанных значений. Под нагрузкой узкое место — пропускная способность
каналов, а не логика приоритета; `select` дёшев.

## Что спросит интервьюер дальше

- **«Почему наивный `select` не даёт приоритет?»** Готовые ветки выбираются
  псевдослучайно — high и low равновероятны.
- **«Зачем `default` в первом `select`?»** Сделать попытку high неблокирующей:
  есть данные — берём, нет — идём ждать оба.
- **«Зачем `ch = nil`?»** `nil`-канал в `select` блокируется навсегда — так
  выключаем ветку закрытого канала без отдельных флагов.
- **«Как не словить busy-loop?»** `default` ведёт во второй блокирующий
  `select`, а не в пустой `continue`.
- **«А если приоритетов три и больше?»** Цепочка неблокирующих `select` по
  убыванию приоритета либо heap под мьютексом — выбор по числу уровней.

## В проде

Приоритетный `select` встречается в планировщиках задач, прокси и брокерах
сообщений: control-сообщения важнее data-сообщений, отмена важнее новой работы.
Похожую логику «сначала срочное, потом обычное» используют worker pool'ы и
шедулеры (паттерны из главы [паттерны](/book/patterns)). Трюк с `nil`-каналом для
выключения веток — стандартный приём из главы [select](/book/select),
применяемый в реализациях стейт-машин и пайплайнов.
