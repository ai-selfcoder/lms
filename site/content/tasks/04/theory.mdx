## Зачем это на собесе

Приоритетная обработка двух потоков — частая прод-задача: системные команды
важнее пользовательских, control-plane важнее data-plane, retry важнее новых
запросов. При этом низкоприоритетный поток не должен голодать. Здесь проверяют
тонкое знание `select`: его ветки выбираются *случайно* при готовности
нескольких, поэтому «сначала high» нельзя получить наивно — нужен трюк с
неблокирующей попыткой и `default`.

## Что нужно знать

Главное: при нескольких готовых ветках `select` выбирает одну **псевдослучайно**.

```go
select {
case v := <-high: // если готовы оба,
case v := <-low:  // выбор между ними равновероятен — приоритета НЕТ
}
```

Чтобы дать high приоритет, делают **неблокирующую** попытку прочитать его
первым через `select` с `default`:

```go
select {
case v := <-high:
	// есть high — обрабатываем его
default:
	// high пуст прямо сейчас — падаем в общий select
}
```

Второй ключевой приём — **`nil`-канал в `select` навсегда блокируется**, то есть
ветка с ним фактически выключается. Это идеальный способ «убрать» закрытый канал:

```go
var ch chan int        // nil
select {
case <-ch:             // никогда не сработает
case <-other:
}
```

Подробнее — главы [select](/book/select) и [каналы](/book/channels).

## Идиомы и паттерны

- **Двухступенчатый `select`.** Сначала неблокирующая попытка `high` с
  `default`; если пусто — блокирующий `select` по обоим каналам. Так high
  всегда вперёд, но если его нет — мы не крутим busy-loop, а честно ждём.
- **Обнуление закрытого канала.** При `v, ok := <-ch; !ok` присваиваем
  `ch = nil` — ветка выключается, в `select` остаётся только живой канал.
- **Условие выхода `high != nil || low != nil`.** Цикл крутится, пока жив хоть
  один канал; оба `nil` → выходим.

## Подводные камни

- **Наивный `select` без `default`.** Даёт равновероятный выбор — приоритета нет.
  `TestProcessPriorityHighFirst` это ловит: при предзаполненных каналах low не
  должен «вылезать» раньше большинства high.
- **Busy-loop при `default`.** Если в `default` ничего не ждать (просто
  `continue`), при двух пустых, но не закрытых каналах процессор закрутится
  на 100%. Поэтому `default` ведёт во *второй, блокирующий* `select`.
- **Чтение из закрытого канала в бесконечном цикле.** Закрытый канал в `select`
  всегда готов и отдаёт `ok == false` — без обнуления в `nil` цикл превратится в
  busy-loop по закрытому каналу.
- **Голодание low.** Если читать high «жадно» в цикле, не давая low шанса,
  отправитель low заблокируется навсегда. `TestProcessPriorityNoStarvation`
  шлёт 50 high и 5 low — все 5 low обязаны быть обработаны.

## Как подступиться

1. `result := make([]int, 0)`; цикл `for high != nil || low != nil`.
2. Шаг 1: неблокирующий `select { case v, ok := <-high: ...; default: }`.
   Если high закрыт — `high = nil`; если есть значение — `append`, `continue`.
3. Шаг 2 (high пуст прямо сейчас): блокирующий `select` по `high` и `low`;
   при закрытии любого — обнуляй его в `nil`.
4. Проверь: 50 high + 5 low → high идут первыми, но все 5 low тоже попадают в
   результат, потому что между «пачками» high шаг 2 даёт low шанс.

Реши сам, потом открывай разбор.
