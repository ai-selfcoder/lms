## Зачем это на собесе

Rate limiter — самый частый «highload»-вопрос: им защищают БД, внешние API и
себя самого от перегрузки. Token bucket любят, потому что он одновременно держит
средний `rps` и разрешает короткие всплески (burst) до ёмкости бакета.
Интервьюер проверяет, понимаешь ли ты, как считать токены «по времени» без
фонового таймера, и умеешь ли сделать горячий путь потокобезопасным и быстрым —
ровно то, что нужно в проде, где `Allow()` зовут миллионы раз в секунду.

## Что нужно знать

**Идея алгоритма.** Есть «ведро» ёмкостью `rps` токенов. Каждый разрешённый
запрос тратит один токен. Токены капают обратно со скоростью `rps` в секунду.
Пусто — `Allow()` возвращает `false`, не блокируя.

Ключевой приём — **refill по времени, а не по таймеру**. Не нужна фоновая
горутина, дёргающая счётчик: на каждом вызове смотрим, сколько времени прошло с
прошлого пополнения, и доливаем пропорционально:

```go
elapsed := now.Sub(last)
add := int(float64(rps) * elapsed.Seconds())
// доливаем add токенов, но не выше ёмкости rps
```

**Потокобезопасность.** `Allow()` зовут из множества горутин, значит состояние
(`tokens`, `lastFill`) — разделяемое. Любой `tokens--` без синхронизации — это
data race, который ловит `-race` (см. [модель памяти](/book/memory-model)).
Защита — либо `sync.Mutex`, либо набор атомиков (см. [atomic](/book/atomic) и
[sync](/book/sync-primitives)).

**Инъекция времени.** Чтобы тесты были детерминированными, источник времени
полезно вынести в поле `now func() time.Time` — в проде это `time.Now`.

## Идиомы и паттерны

- **Mutex вокруг короткой критической секции.** Refill + проверка + декремент —
  несколько арифметических операций; под мьютексом они занимают наносекунды,
  contention минимален. Это полностью идиоматично: «mutex для состояния, каналы
  для оркестрации».
- **`defer mu.Unlock()`** сразу после `Lock()` — чтобы не потерять разблокировку
  ни на одной ветке `return`.
- **Лениво считаем время.** Никаких `time.Ticker`/`time.AfterFunc` на каждый
  лимитер — это лишние горутины и аллокации. Время сравниваем «по запросу».
- **Clamp до ёмкости.** После долива `if tokens > rps { tokens = rps }` — иначе
  за долгий простой бакет «переполнится» и пропустит гигантский всплеск.

## Подводные камни

- **Гонка на счётчике.** Наивное
  ```go
  if rl.tokens > 0 { rl.tokens-- ; return true } // без мьютекса — гонка!
  ```
  под нагрузкой и теряет токены, и падает под `-race`. Проверка и декремент
  должны быть атомарны *вместе*.
- **Обновление `lastFill` на каждый вызов.** Если двигать `lastFill = now`
  всегда, даже когда долили 0 токенов, то при частых вызовах `elapsed` каждый раз
  крошечный, `add` округляется в 0, а `lastFill` всё равно сдвигается — бакет
  никогда не пополнится. Двигать метку нужно только когда реально что-то долили.
- **Целочисленное округление.** `int(float64(rps)*elapsed.Seconds())` при очень
  частых вызовах даёт 0 — это нормально, токены «накопятся» к следующему разу,
  если не сбрасывать `lastFill` зря (см. пункт выше).
- **Фоновый таймер на каждый лимитер.** Тысячи лимитеров → тысячи горутин и
  будильников. Refill по времени убирает их полностью.

## Как подступиться

1. Поля: `rps`, `tokens int`, `lastFill time.Time`, `mu sync.Mutex`,
   `now func() time.Time`. В конструкторе `tokens = rps` (полный бакет — burst
   доступен сразу).
2. В `Allow()` под мьютексом: посчитай `elapsed`, долей `add` токенов с
   ограничением сверху, **сдвинь `lastFill` только если `add > 0`**.
3. Если `tokens > 0` — декремент и `true`; иначе `false`.
4. Проверь себя тестом из условия: 1000 быстрых вызовов при `rps=100` дают около
   100 `true` (всплеск быстрый, доливается почти ноль), а после `Sleep(1.1s)`
   бакет снова полон.
