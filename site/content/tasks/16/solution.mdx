## Идея решения

Храним число токенов и метку последнего пополнения. На каждый `Allow()` под
мьютексом доливаем токены пропорционально прошедшему времени (без фоновых
таймеров), затем, если токен есть, тратим его и возвращаем `true`. Всё состояние
под одним `sync.Mutex` — критическая секция крошечная, гонок нет.

## Разбор эталона по шагам

Состояние и конструктор:

```go
type RateLimiter struct {
	mu       sync.Mutex
	rps      int
	tokens   int
	lastFill time.Time
	now      func() time.Time
}

func NewRateLimiter(rps int) *RateLimiter {
	return &RateLimiter{
		rps:      rps,
		tokens:   rps,        // бакет полон — burst доступен сразу
		lastFill: time.Now(),
		now:      time.Now,   // инъекция времени для тестов
	}
}
```

Бакет стартует полным: первый всплеск из `rps` запросов проходит мгновенно — это
и есть «разрешённый burst». Поле `now` — точка подмены времени в тестах.

Горячий путь под мьютексом:

```go
func (rl *RateLimiter) Allow() bool {
	rl.mu.Lock()
	defer rl.mu.Unlock()

	now := rl.now()
	elapsed := now.Sub(rl.lastFill)
	if elapsed > 0 {
		add := int(float64(rl.rps) * elapsed.Seconds())
		if add > 0 {
			rl.tokens += add
			if rl.tokens > rl.rps {
				rl.tokens = rl.rps
			}
			rl.lastFill = now
		}
	}
	...
}
```

Здесь три тонких момента:

- **Refill по времени.** `add = rps * elapsed_seconds` — сколько токенов «накапало»
  за прошедшее время. Никакого `time.Ticker`: один и тот же результат, но без
  фоновой горутины и аллокаций.
- **Clamp `if rl.tokens > rl.rps`.** За долгий простой бакет не должен накопить
  больше ёмкости, иначе пропустит всплеск размером с этот простой.
- **`lastFill = now` только внутри `if add > 0`.** Это защита от «вечно пустого»
  бакета: при частых вызовах `elapsed` мал, `add` округляется в 0; если бы метку
  двигали всё равно, время «съедалось» бы по кусочку и токены не накопились бы
  никогда. Двигаем метку только когда реально что-то долили — остаток времени
  переносится на следующий вызов.

Трата токена:

```go
	if rl.tokens > 0 {
		rl.tokens--
		return true
	}
	return false
```

Проверка и декремент — под тем же мьютексом, поэтому они атомарны как единое
целое: два потока не «увидят» один и тот же последний токен.

## Почему именно так

- **Нет гонок.** Всё разделяемое состояние (`tokens`, `lastFill`) читается и
  пишется только под `rl.mu`. `-race` чист, потому что между всеми обращениями
  есть happens-before через мьютекс (см. [модель памяти](/book/memory-model)).
- **`Allow()` не блокирует.** Внутри нет каналов и ожиданий — только арифметика
  под коротким локом. Это быстрый предикат, а не «подожди своей очереди».
- **Тест проходит по построению.** Быстрый всплеск 1000 вызовов: время почти не
  идёт, `add≈0`, проходит ровно стартовый запас ~100. После `Sleep(1.1s)`:
  `elapsed≈1.1s`, `add≈110`, clamp до 100 — снова ~100 проходов.

## Альтернативы и их минусы

- **Атомики вместо мьютекса.** Можно держать `tokens` и `lastFill` в атомиках и
  крутить CAS-цикл. Быстрее под экстремальным contention, но логика «долить +
  clamp + потратить» в одном CAS неудобна и легко ломается. Для типичной нагрузки
  мьютекс с наносекундной секцией не является узким местом — см.
  [atomic](/book/atomic).
- **Фоновый refill горутиной + `time.Ticker`.** Раз в период кладём токены в
  буферизованный канал, `Allow()` делает `select { case <-tokens: default: }`.
  Красиво и тоже неблокирующе, но это горутина и таймер на каждый лимитер —
  дорого при тысячах лимитеров.
- **`golang.org/x/time/rate`.** Прод-стандарт: тот же token bucket, но с
  `Allow`, `Wait(ctx)`, `Reserve`, дробной скоростью `rate.Limit`. На реальном
  сервисе берут именно его; на собесе просят написать «руками», чтобы проверить
  понимание.

## Сложность и поведение под нагрузкой

`Allow()` — O(1), без аллокаций (zero-alloc на горячем пути: только арифметика).
Под высоким contention все горутины сериализуются на одном мьютексе, но
критическая секция — несколько инструкций, так что пропускная способность очень
высокая. Если лимитер становится узким местом — шардируют по ключу (как
[ShardedMap](/book/sync-primitives)) или переходят на атомики.

## Что спросит интервьюер дальше

- **«Чем token bucket отличается от leaky bucket?»** Token bucket разрешает
  всплески до ёмкости и не блокирует; leaky bucket сглаживает поток и заставляет
  ждать (см. задачу 17).
- **«Как сделать блокирующий `Wait()`?»** Считаем, когда появится токен, и спим
  до этого момента через `time.Timer`, уважая `ctx`.
- **«Дробный rps, например 2.5/с?»** Хранить токены как `float64` или считать в
  «нанотокенах»; ровно так делает `x/time/rate` через `rate.Limit`.
- **«Точность под высокой частотой вызовов?»** Из-за целочисленного округления
  возможен дрейф; хранение остатка времени (не сдвигать `lastFill` при `add==0`)
  его устраняет.
- **«Распределённый rate limit на кластер?»** Локального бакета мало — выносят
  счётчики в Redis (например, скрипт INCR+EXPIRE) или sliding-window-лог.

## В проде

Token bucket — это `golang.org/x/time/rate.Limiter`, лимитеры в gRPC/HTTP
middleware, клиентских SDK облаков (AWS, GCP) и API gateway. Тот же принцип
«считать по времени, не по таймеру» используется в биллинге и троттлинге. Понимание
этой задачи напрямую переносится на защиту любого внешнего ресурса от перегрузки.
