## Зачем это на собесе

Внешний API почти всегда имеет лимит: «не больше 50 запросов в секунду». Если
запустить пул из 10 воркеров без общего тормоза, они дружно превысят квоту и
поймают `429`/бан. Задача проверяет, умеешь ли ты ограничивать **суммарный** темп
по всему пулу (а не на воркера), совмещая это с параллелизмом. Это базовый навык
для любого клиента к стороннему сервису.

## Что нужно знать

Конвейер из двух стадий: стадия 1 поставляет `userIDs` в канал, стадия 2 —
пул воркеров, дёргающих `callAPI` (см. [паттерны](/book/patterns)):

```go
ids := make(chan int)
go func() {
    defer close(ids)
    for _, id := range userIDs { ids <- id }
}()
```

Лимитер темпа — **один на весь пул**. Простейший — `time.Ticker` с интервалом
`time.Second / rps`: он отправляет тик каждые `1/rps` секунды, и воркер перед
каждым вызовом ждёт тик из общего канала `ticker.C`:

```go
ticker := time.NewTicker(time.Second / time.Duration(rps))
defer ticker.Stop()
// в воркере:
<-ticker.C       // разрешение на один вызов
callAPI(id)
```

Поскольку `ticker.C` один на всех, тики «разбирают» воркеры наперегонки — это и
даёт суммарный лимит `rps` независимо от числа воркеров. Параллелизм при этом
сохраняется: до `workers` вызовов могут идти одновременно, просто старты
размазаны тиком.

## Идиомы и паттерны

- **Общий тикер как лимитер.** Один `time.Ticker`, чей канал гейтит каждый вызов.
  Ключевое слово — *общий*: лимит на пул, а не на воркера.
- **Fan-out из одного канала задач.** `workers` горутин читают из `ids` через
  `for range`; закрытие `ids` корректно завершает всех.
- **Сбор результатов под мьютексом.** `append` в общий срез из нескольких горутин
  — гонка; защищаем `sync.Mutex` (или собираем через отдельный канал).
- **`sync.WaitGroup` для завершения.** Ждём всех воркеров, потом возвращаем
  результат.

## Подводные камни

- **Лимитер на воркера, а не на пул.** Если у каждого воркера свой `ticker`, общий
  темп станет `workers × rps` — лимит нарушен. Тикер должен быть один.
- **Гонка на срезе результатов.** Конкурентный `append` без мьютекса — дата-рейс;
  под `-race` падает, в проде — порча данных.
- **`time.Second / rps == 0`.** При очень больших `rps` целочисленное деление
  даёт 0, а `NewTicker(0)` паникует. Нормализуй `rps >= 1` и помни про границу.
- **Утечка тикера.** Без `defer ticker.Stop()` тикер продолжает тикать и держать
  ресурсы.
- **Ожидание тика на пустом пуле.** Если воркеры ждут `<-ticker.C` уже после того,
  как `ids` закрыт, они не дёрнут лишний вызов — но следи, чтобы `<-ticker.C` было
  **внутри** цикла по задачам, а не до него.
- **Burst в начале.** `Ticker` не накапливает «кредиты»: если воркеры стартовали и
  ждут, первый тик придёт через интервал — это сглаживает старт, но не даёт
  «всплеска». Для разрешённых всплесков нужен token-bucket.

## Как подступиться

1. Нормализуй `workers >= 1`, `rps >= 1`.
2. Стадия 1: горутина шлёт все `userIDs` в `ids` и закрывает канал.
3. Создай один `ticker := time.NewTicker(time.Second / rps)`, `defer Stop`.
4. Заведи `mu` и `results []string`.
5. Стадия 2: `workers` горутин под `WaitGroup`; в каждой
   `for id := range ids { <-ticker.C; res := callAPI(id); mu.Lock(); append; mu.Unlock() }`.
6. `wg.Wait()`, верни `results`.

Дальше — реализуй сам. Разбор открывай после.
