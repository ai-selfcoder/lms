## Идея решения

Два этапа: горутина-поставщик шлёт `userIDs` в канал, пул из `workers` воркеров
читает их. Темп ограничивает **один общий** `time.Ticker` с интервалом
`time.Second/rps`: воркер перед каждым `callAPI` ждёт тик из общего канала.
Поскольку канал тиков один на всех, суммарный темп по пулу не превышает `rps`,
при этом до `workers` вызовов идут параллельно. Результаты собираются в срез под
мьютексом.

## Разбор эталона по шагам

Нормализация входа защищает от вырожденных значений:

```go
if workers < 1 { workers = 1 }
if rps < 1 { rps = 1 }
```

`rps < 1` важен и для `time.Second / rps`: иначе деление на 0. (Очень большой
`rps` дал бы интервал 0 и панику `NewTicker(0)` — в проде это тоже нормализуют, но
тесты гоняют умеренные значения.)

Стадия 1 — поставщик:

```go
ids := make(chan int)
go func() {
    defer close(ids)
    for _, id := range userIDs {
        ids <- id
    }
}()
```

Небуферизованный `ids`: воркеры разбирают id по мере готовности.
`defer close(ids)` сигналит воркерам «входов больше нет» — их `for range`
завершится.

Общий лимитер — сердце решения:

```go
ticker := time.NewTicker(time.Second / time.Duration(rps))
defer ticker.Stop()
```

Один `ticker` на всю функцию. Его канал `ticker.C` тикает каждые `1/rps` секунды.
`defer ticker.Stop()` гасит тикер при выходе — без него тикер продолжит работать и
течь.

Сбор результатов защищён мьютексом:

```go
var (
    mu      sync.Mutex
    results []string
)
```

Стадия 2 — пул воркеров:

```go
var wg sync.WaitGroup
wg.Add(workers)
for i := 0; i < workers; i++ {
    go func() {
        defer wg.Done()
        for id := range ids {
            <-ticker.C            // разрешение от общего лимитера
            res := callAPI(id)
            mu.Lock()
            results = append(results, res)
            mu.Unlock()
        }
    }()
}
```

Разберём ключевое:

- **`<-ticker.C` внутри цикла, перед каждым `callAPI`.** Все воркеры читают из
  **одного** канала тиков. Тики раздаются по одному, наперегонки — кто свободен,
  тот и забрал. Поэтому за любую секунду из канала уйдёт примерно `rps` тиков, то
  есть пройдёт не больше `rps` вызовов суммарно по пулу. Это и есть «общий лимит».
- **Параллелизм сохранён.** Получив тик, воркер тут же зовёт `callAPI` и, пока тот
  работает, другой воркер может забрать следующий тик. Одновременно «в полёте» до
  `workers` вызовов — лимитер ограничивает темп *стартов*, а не степень
  параллелизма.
- **`mu.Lock()` вокруг `append`.** Несколько воркеров пишут в общий срез — без
  мьютекса это дата-рейс. Критическая секция короткая: только `append`.

Финал — дождаться всех и вернуть:

```go
wg.Wait()
return results
```

`wg.Wait()` блокирует, пока все воркеры не выйдут из `for range` (то есть после
закрытия `ids` и обработки всех id).

## Почему именно так

- **Лимит соблюдён.** Тест проверяет две вещи: нижнюю границу по времени (`n`
  вызовов при `rps` не успевают пройти быстрее ~`n/rps` секунд) и что ни в одном
  скользящем окне в 1 секунду нет больше `rps + запас` вызовов. Общий тикер даёт
  обе гарантии.
- **Все id обработаны ровно раз.** Каждый id уходит в `ids` единожды, забирается
  одним воркером; тест сверяет полное множество результатов.
- **Нет гонок и утечек.** Срез — под `mu`, тикер останавливается через `defer`,
  воркеры завершаются по закрытию `ids`, `wg` ловит их. `-race` чист.

## Альтернативы и их минусы

- **Тикер на каждого воркера.** Дало бы суммарный темп `workers × rps` — лимит
  нарушен. Классическая ошибка; лимитер обязан быть общим.
- **`golang.org/x/time/rate` (token bucket).** Идиоматичный лимитер:
  `limiter.Wait(ctx)` перед каждым вызовом. Гибче тикера — поддерживает burst
  (накопленные токены) и работает с `context`. В проде предпочтительнее; здесь
  условие требует реализовать вручную, и тикер — самый простой корректный вариант.
  Главное отличие: `Ticker` не накапливает «кредиты» простоя, а bucket — да.
- **Семафор ёмкости `rps` без тикера.** Ограничит *параллелизм*, но не *темп*:
  быстрые вызовы пролетят пачкой и превысят RPS. Семафор — про concurrency,
  лимитер — про rate; это разные оси.
- **Сбор через канал результатов вместо мьютекса.** Тоже корректно; выбор между
  `mu` и каналом — вкусовой, на маленькой критической секции мьютекс дешевле.

## Сложность и поведение под нагрузкой

Время выполнения снизу ограничено `~n/rps` секунд — это by design. Память —
O(числа результатов). Контеншн на `mu` минимален (только `append`), на `ticker.C`
— воркеры конкурируют за тики, но это лёгкая операция приёма из канала. При
`workers` ≫ нужного для насыщения `rps` лишние воркеры просто чаще ждут на
`<-ticker.C` — вреда нет, но и пользы тоже: число воркеров стоит брать соизмеримо
`rps × средняя_латентность_callAPI`.

## Что спросит интервьюер дальше

- **«Почему тикер общий, а не на воркера?»** Чтобы лимит был на пул: с тикером на
  воркера суммарный темп вырос бы в `workers` раз.
- **«Чем `time.Ticker` хуже token-bucket?»** Тикер не разрешает всплесков: после
  простоя нельзя «нагнать» — каждый вызов ждёт следующий тик. `rate.Limiter`
  копит токены и допускает burst.
- **«Что при `rps`, дающем интервал 0?»** `time.Second/rps == 0` → `NewTicker(0)`
  паникует; нужно ограничить минимальный интервал или взять другой лимитер.
- **«Как добавить отмену/таймаут?»** Прокинуть `context`: в воркере
  `select { case <-ctx.Done(): return; case <-ticker.C: }`, или сразу
  `rate.Limiter.Wait(ctx)`.
- **«Гарантирует ли это ровно `rps`, а не меньше?»** Нет — это *верхняя* граница.
  Если воркеров мало или `callAPI` медленный, реальный темп будет ниже лимита.

## В проде

Так строят клиентов к сторонним API с квотами (платёжные шлюзы, гео/SMS-сервисы),
краулеры с вежливым темпом, throttling исходящих вызовов в микросервисах.
Стандарт де-факто — `golang.org/x/time/rate` (token bucket) вместо ручного тикера;
для распределённого лимита (на весь кластер) — Redis-based лимитеры. Фундамент —
пайплайны и семафоры из главы [паттерны](/book/patterns), каналы и `select` из
[channels](/book/channels) и [select](/book/select).
