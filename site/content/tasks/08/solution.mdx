## Идея решения

Счётчик незавершённых задач под `sync.Mutex`. `Wait` спит на `sync.Cond` в цикле
`for counter != 0`, отпуская лок на время сна. `Add`/`Done` меняют счётчик под
тем же локом и, когда он достигает нуля, будят всех ждущих через `Broadcast`.

## Разбор эталона по шагам

Структура и ленивая инициализация `Cond`:

```go
type MyWaitGroup struct {
	mu      sync.Mutex
	cond    *sync.Cond
	counter int
}

func (wg *MyWaitGroup) ensureCond() {
	if wg.cond == nil {
		wg.cond = sync.NewCond(&wg.mu)
	}
}
```

`sync.Cond` нельзя получить нулевым значением — ему нужен `Locker`. Поэтому
`ensureCond` создаёт его лениво. Комментарий «вызывается под mu» важен: создание
`cond` тоже под мьютексом, иначе два первых вызова могли бы создать его дважды
(гонка). Так zero-value `MyWaitGroup{}` остаётся готовым к работе, как настоящий
`sync.WaitGroup`.

`Add` меняет счётчик и будит ждущих при нуле:

```go
func (wg *MyWaitGroup) Add(delta int) {
	wg.mu.Lock()
	defer wg.mu.Unlock()
	wg.ensureCond()
	wg.counter += delta
	if wg.counter < 0 {
		panic("MyWaitGroup: отрицательный счётчик")
	}
	if wg.counter == 0 {
		wg.cond.Broadcast()
	}
}
```

Всё под `mu` — счётчик меняется атомарно относительно `Wait`. `panic` при
`counter < 0` повторяет контракт `sync.WaitGroup`: уход в минус — баг
вызывающего. `Broadcast` при достижении нуля будит *всех* ждущих в `Wait`
(их может быть несколько).

`Done` — просто `Add(-1)`:

```go
func (wg *MyWaitGroup) Done() {
	wg.Add(-1)
}
```

Никакого дублирования логики: `Done` переиспользует пробуждение и проверки `Add`.

`Wait` спит, пока счётчик не ноль:

```go
func (wg *MyWaitGroup) Wait() {
	wg.mu.Lock()
	defer wg.mu.Unlock()
	wg.ensureCond()
	for wg.counter != 0 {
		wg.cond.Wait()
	}
}
```

Ключевые детали:

- **`cond.Wait()` под `mu`.** `Wait` атомарно отпускает `mu` и засыпает; при
  пробуждении снова берёт `mu`. Поэтому весь метод под `Lock`/`defer Unlock`.
- **`for`, а не `if`.** После `Broadcast` все ждущие проснутся, но захватят `mu`
  по очереди; цикл перепроверяет `counter != 0` при каждом пробуждении —
  защита от ложных и групповых пробуждений. Если счётчик уже 0, цикл вообще не
  входит в `Wait` и возвращается сразу (`TestMyWaitGroupZeroReturnsImmediately`).

## Почему именно так

- **Корректное пробуждение.** `TestMyWaitGroupWaitsForAll` (50 горутин) требует,
  чтобы `Wait` вернулся только после всех `Done`. Последний `Done` делает
  `counter == 0` → `Broadcast` → `Wait` выходит из цикла.
- **Нет преждевременного выхода.** `TestMyWaitGroupAddDoneBalance` дёргает `Done`
  по одному и проверяет, что `Wait` не вернулся, пока есть незавершённые задачи —
  `Broadcast` шлётся только на нуле.
- **Нет гонок и busy-loop.** Счётчик всегда под `mu`; `Wait` спит, а не крутит
  цикл. `-race` чист.

## Альтернативы и их минусы

- **Закрытие канала вместо `Cond`.** Держать `done chan struct{}`; `Wait` —
  `<-done`; когда счётчик дошёл до нуля, `close(done)` (broadcast через
  закрытие). Элегантно, но плохо переживает повторное использование (`Add` после
  нуля), требует пересоздавать канал и аккуратной синхронизации — `Cond`
  естественнее для «многоразового» барьера.
- **Busy-loop с мьютексом.** `for { mu.Lock(); n:=counter; mu.Unlock(); if n==0
  {return} }` — корректно, но жжёт CPU и не идиоматично. Тест намекает «без
  busy-loop».
- **`atomic` + спинлок.** Запрещено условием, да и `Wait` без блокировки
  превратится в спин. `Cond` паркует горутину в планировщике — дешевле.
- **`Signal` вместо `Broadcast`.** Разбудит одного ждущего; если `Wait`-ов
  несколько (как в тестах с отдельной горутиной-ждуном их может быть много),
  остальные зависнут. Нужен `Broadcast`.

## Сложность и поведение под нагрузкой

`Add`/`Done` — O(1) под коротким мьютексом. `Wait` спит в планировщике, не
потребляя CPU. `Broadcast` будит всех ждущих — O(числа ждущих), что в норме
немного. Контеншн только на `mu`, и критические секции крошечные. Настоящий
`sync.WaitGroup` быстрее за счёт атомиков и отсутствия мьютекса на горячем
`Done`, но функционально эталон эквивалентен.

## Что спросит интервьюер дальше

- **«Почему `for`, а не `if` вокруг `Wait`?»** Групповое пробуждение через
  `Broadcast` + перезахват лока по очереди: условие надо перепроверять.
- **«Почему `Broadcast`, а не `Signal`?»** Ждущих может быть несколько, всех
  надо разбудить на нуле.
- **«Зачем `Wait` под мьютексом?»** `cond.Wait` атомарно отпускает и снова берёт
  тот же лок; вне лока — паника/гонка.
- **«Почему `Cond` создаётся лениво под `mu`?»** Нет валидного zero-value у
  `Cond`; создание под локом исключает двойную инициализацию.
- **«Чем настоящий `WaitGroup` отличается?»** Внутри на атомиках, `Done` без
  мьютекса — быстрее; плюс защита от повторного использования и проверок vet.
- **«Что при `Add` после нуля?»** Можно переиспользовать — счётчик снова растёт,
  `Wait` снова заблокируется; именно поэтому `Cond` удобнее закрытия канала.

## В проде

`sync.Cond` встречается там, где горутины ждут изменения общего состояния:
очереди с ограниченной ёмкостью (producer/consumer), пулы соединений
(`database/sql` исторически), кэши с ожиданием заполнения. Сам `sync.WaitGroup`
— основной инструмент «дождаться группы горутин» (часто в паре с `errgroup`).
Понимание паттерна condition variable — база для любых самописных барьеров и
семафоров; см. [sync: примитивы](/book/sync-primitives).
