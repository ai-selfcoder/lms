## Зачем это на собесе

Это задача «покажи, что понимаешь синхронизацию изнутри». Реализовать
`WaitGroup` без `sync.WaitGroup` и без `atomic` можно только через condition
variable: счётчик под мьютексом + `sync.Cond`. Проверяют редкое умение —
правильно пользоваться `Cond`: проверка условия *в цикле под локом* и
пробуждение через `Broadcast`. Большинство кандидатов `Cond` живьём не писали,
поэтому задача отлично разделяет.

## Что нужно знать

`sync.Cond` — это «список ожидания» при мьютексе. Три операции:

```go
cond := sync.NewCond(&mu)
cond.Wait()      // атомарно: Unlock + сон; при пробуждении снова Lock
cond.Signal()    // разбудить одного ждущего
cond.Broadcast() // разбудить всех ждущих
```

`Wait()` вызывают, **держа мьютекс**: он атомарно отпускает лок и засыпает, а
при пробуждении снова берёт лок. Поэтому условие проверяют **в цикле**:

```go
mu.Lock()
for !condition {
	cond.Wait() // защита от ложных и групповых пробуждений
}
mu.Unlock()
```

Цикл (а не `if`) обязателен: после `Broadcast` все проснутся, но захватят лок по
очереди, и условие могло снова стать ложным. Подробнее — [sync: примитивы](/book/sync-primitives)
и [модель памяти](/book/memory-model).

## Идиомы и паттерны

- **Счётчик под мьютексом.** `counter int` меняется только под `mu` — никакого
  `atomic` (он и запрещён условием).
- **`Wait` спит в цикле `for counter != 0`.** Классический condition-variable
  паттерн.
- **`Broadcast` при достижении нуля.** `Done`/`Add` будят *всех* ждущих, когда
  `counter` дошёл до 0.
- **Ленивая инициализация `Cond`.** `sync.NewCond(&mu)` нельзя сделать в
  zero-value структуры; создаём при первом обращении под локом.

## Подводные камни

- **`if` вместо `for` вокруг `Wait`.** Ложное/групповое пробуждение — и горутина
  выйдет из `Wait` при ненулевом счётчике. Всегда `for counter != 0`.
- **`Wait` без удержания мьютекса.** `cond.Wait()` без `mu.Lock()` — паника или
  гонка. `Wait` должен вызываться под тем же локом, что передан в `NewCond`.
- **`Signal` вместо `Broadcast`.** Если `Wait`-ящих несколько, `Signal` разбудит
  одного — остальные зависнут. На «дошли до нуля» нужно разбудить всех →
  `Broadcast`.
- **Busy-loop вместо `Cond`.** `for { mu.Lock(); n:=counter; mu.Unlock(); if n==0
  {break} }` — корректно, но жжёт процессор и не идиоматично. Тест намекает на
  «без busy-loop».
- **Отрицательный счётчик.** `Add(-1)` ниже нуля — баг вызывающего; настоящий
  `WaitGroup` паникует, и здесь это уместно.

## Как подступиться

1. Поля: `mu sync.Mutex`, `cond *sync.Cond`, `counter int`.
2. Хелпер `ensureCond()` под `mu`: если `cond == nil`, создать `sync.NewCond(&mu)`.
3. `Add(delta)`: под `mu` — `ensureCond`, `counter += delta`, паника при
   `counter < 0`, `Broadcast` при `counter == 0`.
4. `Done()` = `Add(-1)`.
5. `Wait()`: под `mu` — `ensureCond`, затем `for counter != 0 { cond.Wait() }`.
6. Проверь мысленно: `Add(50)`, 50 горутин вызывают `Done`; последний `Done`
   делает `counter==0` и `Broadcast` будит `Wait`.

Реши сам, затем открывай разбор.
