## Идея решения

Минимум воркеров запускается сразу и помечается как «постоянный». Отдельный
менеджер по тикеру смотрит на бэклог (`len(tasks)`) и спавнит временных воркеров,
пока есть место до `maxWorkers`. Временные воркеры сами уходят по таймауту
простоя, но только если воркеров больше `minWorkers`. Всё состояние числа
воркеров — под мьютексом, пик — через atomic-CAS, остановка — через закрытие
`stopCh`.

## Разбор эталона по шагам

Состояние пула разделено на «защищённое мьютексом» и «atomic»:

```go
mu     sync.Mutex
active int   // текущее число воркеров — только под mu
peak   int32 // пиковое число — atomic

wg       sync.WaitGroup
stopCh   chan struct{}
stopOnce sync.Once
```

`active` трогают несколько горутин (спавн, выход воркера, проверки границ),
поэтому он живёт под `mu`. `peak` обновляется на горячем пути спавна — для него
дешевле atomic.

`Start` поднимает минимум постоянных воркеров и менеджер:

```go
func (p *ScalingPool) Start() {
    for i := 0; i < p.minWorkers; i++ {
        p.spawn(true)   // permanent
    }
    p.wg.Add(1)
    go p.manager()
}
```

`spawn` — критическая секция «проверка границы + инкремент»:

```go
func (p *ScalingPool) spawn(permanent bool) {
    p.mu.Lock()
    if p.active >= p.maxWorkers {
        p.mu.Unlock()
        return                 // места нет — выходим, ничего не запустив
    }
    p.active++
    cur := int32(p.active)
    p.mu.Unlock()

    for {
        old := atomic.LoadInt32(&p.peak)
        if cur <= old || atomic.CompareAndSwapInt32(&p.peak, old, cur) {
            break
        }
    }

    p.wg.Add(1)
    go p.worker(permanent)
}
```

Проверка `active >= maxWorkers` и `active++` — под одним `Lock`. Это и есть
защита от TOCTOU: даже если менеджер и `Start` зовут `spawn` одновременно,
суммарно за `maxWorkers` не выйдет. Пик поднимается CAS-циклом: читаем текущий
максимум, и если `cur` больше — пытаемся записать; конкурентный спавн просто
повторит итерацию. `wg.Add(1)` делается **до** `go`, иначе `Stop` мог бы
проскочить ещё не учтённого воркера.

Сердце — воркер с тремя ветками `select`:

```go
func (p *ScalingPool) worker(permanent bool) {
    defer p.wg.Done()
    defer func() {
        p.mu.Lock()
        p.active--
        p.mu.Unlock()
    }()

    idle := time.NewTimer(50 * time.Millisecond)
    defer idle.Stop()

    for {
        if !idle.Stop() {
            select { case <-idle.C: default: }
        }
        idle.Reset(50 * time.Millisecond)

        select {
        case <-p.stopCh:
            return
        case task, ok := <-p.tasks:
            if !ok { return }
            if task != nil { task() }
        case <-idle.C:
            if !permanent {
                p.mu.Lock()
                if p.active > p.minWorkers {
                    p.mu.Unlock()
                    return        // лишний воркер уходит
                }
                p.mu.Unlock()
            }
        }
    }
}
```

Разберём нетривиальные места:

- **`defer ...; p.active--`** — кто бы ни вернул воркера (стоп, закрытие
  `tasks`, простой), счётчик корректно уменьшится под мьютексом.
- **Сброс таймера перед каждым ожиданием.** `idle.Stop()` + слив `idle.C` через
  `select { default: }` гасят «протухший» тик от прошлой итерации, и только потом
  `Reset`. Без этого ветка `idle.C` могла бы сработать мгновенно.
- **`case <-p.stopCh`** — отдельная ветка завершения: воркер, висящий в `select`,
  проснётся на закрытии `stopCh`, а не зависнет на `<-tasks`. Это то, что ловит
  тест на утечки.
- **Уход по простою только если `active > minWorkers`** и только для
  непостоянных. Проверка под мьютексом гарантирует, что пул не схлопнется ниже
  минимума.

Менеджер масштабирует вверх по давлению очереди:

```go
case <-ticker.C:
    if len(p.tasks) > 0 {
        p.mu.Lock()
        room := p.active < p.maxWorkers
        p.mu.Unlock()
        if room {
            p.spawn(false)
        }
    }
```

`len(p.tasks) > 0` — индикатор бэклога буферизованного канала. Заметь: проверка
`room` и `spawn` не атомарны между собой, но это безопасно — внутри `spawn`
граница перепроверяется под мьютексом, так что лишний воркер не родится.

`Stop` закрывает `stopCh` один раз и ждёт всех:

```go
func (p *ScalingPool) Stop() {
    p.stopOnce.Do(func() { close(p.stopCh) })
    p.wg.Wait()
}
```

`sync.Once` делает `Stop` идемпотентным — повторный вызов не паникует на
double-close. `wg.Wait()` дожидается и воркеров, и менеджера.

## Почему именно так

- **Нет гонок.** Весь доступ к `active` — под `mu`; `peak` — через atomic; стоп —
  через закрытие канала. `-race` чист.
- **Нет утечек.** Каждая горутина имеет ветку выхода: воркеры — на `stopCh` /
  закрытии `tasks` / простое, менеджер — на `stopCh`. `wg` учитывает всех. Тест
  сверяет `runtime.NumGoroutine()` до и после.
- **Границы соблюдены.** Верхняя — перепроверкой в `spawn` под мьютексом;
  нижняя — условием `active > minWorkers` при уходе.

## Альтернативы и их минусы

- **Семафор на буферизованном канале вместо менеджера.** Лимитировать
  параллелизм через `chan struct{}` ёмкости `max` проще, но он не *сворачивает*
  простаивающих воркеров — это лимитер, а не автоскейлер.
- **Спавн «один воркер на задачу» без верхней границы.** Под всплеском нагрузки
  создаст тысячи горутин и съест память — ровно та беда, от которой пул и
  защищает.
- **`x/sync/semaphore` с `Acquire/Release`.** Хорош для ограничения
  параллелизма с контекстом, но опять же не масштабирует число долгоживущих
  воркеров вниз по простою.

## Сложность и поведение под нагрузкой

Память и число горутин — O(текущего числа воркеров), ограничены `maxWorkers`.
На горячем пути спавна — одна короткая критическая секция и CAS-цикл (обычно одна
итерация). Под устойчивой нагрузкой пул быстро доходит до `max` и держится там;
когда бэклог рассасывается, временные воркеры отваливаются за один интервал
простоя, возвращая память. Контеншн на `mu` низкий: блокировка держится лишь на
инкремент/декремент счётчика, а не на время выполнения задачи.

## Что спросит интервьюер дальше

- **«Почему `len(tasks)` — годный сигнал, а если канал небуферизованный?»** Для
  небуферизованного `len` всегда 0; тогда нужен другой сигнал давления — например,
  счётчик «задач в полёте» или измерение времени ожидания воркеров.
- **«Как сделать масштабирование вниз плавным, без дёрганья?»** Гистерезис:
  разные пороги на up и down, минимальное время жизни воркера, скользящее среднее
  загрузки.
- **«Зачем atomic для peak, если active и так под мьютексом?»** Чтобы `Peak()`
  читался без захвата `mu` и не конкурировал с горячим путём.
- **«Что будет, если задача паникует?»** Уронит воркера и сломает учёт — нужна
  recover-обёртка (см. задачу 24).
- **«Как корректно дренировать оставшиеся задачи на Stop?»** Не закрывать `stopCh`
  сразу, а сначала дать воркерам вычитать `tasks` до закрытия канала задач.

## В проде

Это паттерн любого пула ресурсов: `database/sql` держит соединения в диапазоне
`SetMaxIdleConns..SetMaxOpenConns` и закрывает простаивающие; HTTP-серверы и gRPC
скейлят обработчики; автоскейлеры k8s/HPA — та же идея на уровне подов. Базовые
кирпичи — [паттерны](/book/patterns) (worker pool, semaphore),
[sync](/book/sync-primitives) (Mutex, WaitGroup, Once) и контроль
[утечек](/book/leaks-and-races).
