## Зачем это на собесе

Статический пул из N воркеров — это всегда компромисс: мало — копится бэклог,
много — горутины простаивают и жгут память. Автомасштабируемый пул решает обе
беды: он наращивает воркеров под нагрузкой и сворачивает их, когда работа
кончилась. Интервьюер проверяет, умеешь ли ты управлять **жизненным циклом
горутин** — запускать, останавливать, не плодить утечек — и координировать это
без гонок. Это ровно те навыки, которыми живут пулы соединений в БД, executor'ы
и автоскейлеры в проде.

## Что нужно знать

Базовый воркер-пул — это набор горутин, читающих из одного канала задач, плюс
`sync.WaitGroup` для ожидания их завершения (см. [паттерны](/book/patterns) и
[sync](/book/sync-primitives)):

```go
for i := 0; i < n; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for task := range tasks { task() }
    }()
}
```

Динамика добавляет две оси:

- **Масштабирование вверх** — отдельный «менеджер», который смотрит на давление
  очереди. Для буферизованного канала давление видно через `len(tasks)`: это
  число уже накопленных, но ещё не разобранных задач.
- **Масштабирование вниз** — воркер сам решает уйти, если слишком долго не
  получал работу. Здесь нужен таймер простоя через `time.Timer` и ветка
  таймаута в [select](/book/select):

```go
select {
case task := <-tasks: task()
case <-idle.C:   // долго ничего не приходило — кандидат на завершение
}
```

И ещё: общее состояние (`active`, `peak`) читают и пишут несколько горутин —
значит, нужен мьютекс для счётчика воркеров и `sync/atomic` для пика.

## Идиомы и паттерны

- **`stopCh` + `sync.Once` для остановки.** Закрытый канал — это broadcast:
  закрыли один раз, все воркеры и менеджер увидели сигнал в своём `select`.
  `sync.Once` страхует от повторного `close` (паника).
- **«Постоянные» и «временные» воркеры.** Минимум `minWorkers` помечают как
  permanent — они не уходят по простою. Остальные — temporary, завершаются сами.
- **Atomic-CAS для пика.** `Peak` обновляют циклом `CompareAndSwap`, чтобы
  атомарно поднять максимум без мьютекса на горячем пути.
- **Граница под мьютексом.** Решение «можно ли ещё спавнить» (`active < max`) и
  «можно ли уйти» (`active > min`) принимают под одним мьютексом — иначе две
  горутины одновременно «протиснутся» за границу.

## Подводные камни

- **Гонка проверки и инкремента.** `if active < max { active++ }` без мьютекса —
  классический TOCTOU: два менеджера прочитают `active == max-1` и оба
  заспавнят воркера. Превышение `maxWorkers` обеспечено.
- **Уход всех воркеров.** Если воркер уходит по простою без проверки
  `active > min`, пул может схлопнуться в ноль и больше никогда не разобрать
  новые задачи. Нижнюю границу проверяют строго под мьютексом.
- **Утечка после Stop.** Воркер, заблокированный на `<-tasks`, не услышит
  закрытие — нужна отдельная ветка `case <-stopCh: return` в `select`. Тест
  ловит это через `runtime.NumGoroutine()`.
- **`time.Timer` и «протухший» тик.** Если переиспользовать таймер через
  `Reset`, перед этим нужно корректно его остановить и слить старое значение из
  `t.C`, иначе ветка простоя сработает ложно:

```go
if !idle.Stop() {
    select { case <-idle.C: default: }
}
idle.Reset(d)
```

## Как подступиться

1. Заведи состояние: `minWorkers`, `maxWorkers`, `tasks`, `mu`, `active int`,
   `peak int32` (atomic), `wg`, `stopCh`, `stopOnce`.
2. `spawn(permanent bool)` — под мьютексом проверь `active < max`, инкременти
   `active`, обнови `peak` через CAS, запусти горутину воркера.
3. Воркер в цикле: сбрось idle-таймер, затем `select` по трём веткам —
   `stopCh` (выход), `tasks` (выполнить задачу), `idle.C` (если не permanent и
   `active > min` — уйти). В `defer` декрементируй `active`.
4. `manager` по тикеру смотрит `len(tasks) > 0` и зовёт `spawn(false)`, пока есть
   место.
5. `Stop` — `stopOnce.Do(close(stopCh))`, затем `wg.Wait()`.
