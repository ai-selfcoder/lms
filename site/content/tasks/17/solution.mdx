## Идея решения

Одна фоновая горутина-«метроном» на каждый тик `Ticker`'а пытается передать ровно
один пропуск через небуферизованный канал `gate`. `Acquire()` блокируется на
чтении из `gate`, поэтому ожидающие выпускаются по одному раз в `interval`.
Сигнальный канал `stop` корректно гасит горутину без утечки.

## Разбор эталона по шагам

Структура и конструктор:

```go
type LeakyBucket struct {
	gate chan struct{}
	stop chan struct{}
}

func NewLeakyBucket(interval time.Duration) *LeakyBucket {
	lb := &LeakyBucket{
		gate: make(chan struct{}), // без буфера — точка рандеву
		stop: make(chan struct{}),
	}
	go lb.run(interval)
	return lb
}
```

`gate` намеренно **без буфера**: тик «материализуется» в пропуск только если
кто-то его прямо сейчас забирает. Это и даёт сглаживание — накопить пропуски
впрок нельзя.

Фоновый цикл:

```go
func (lb *LeakyBucket) run(interval time.Duration) {
	ticker := time.NewTicker(interval)
	defer ticker.Stop()
	for {
		select {
		case <-lb.stop:
			return
		case <-ticker.C:
			select {
			case lb.gate <- struct{}{}:
			case <-lb.stop:
				return
			}
		}
	}
}
```

Два вложенных `select` — главная тонкость:

- **Внешний** ждёт либо сигнал остановки, либо тик. Ветка `<-lb.stop` гарантирует,
  что горутина завершится по `Stop()` — нет утечки.
- **Внутренний** (на тике) пытается отдать пропуск. Если очередь пуста, отправка
  `lb.gate <- struct{}{}` заблокировала бы горутину навсегда, и `Stop()` тоже бы
  повис. Поэтому здесь *снова* слушаем `<-lb.stop`: остановка прерывает зависшую
  отправку. Это защита от дедлока.

`defer ticker.Stop()` отдаёт таймер рантайму при выходе.

Публичные методы тривиальны:

```go
func (lb *LeakyBucket) Acquire() { <-lb.gate }

func (lb *LeakyBucket) Stop() { close(lb.stop) }
```

`Acquire()` просто ждёт пропуск. `Stop()` закрывает `stop` — закрытый канал как
broadcast мгновенно будит все ветки `<-lb.stop` (см. [каналы](/book/channels)).

## Почему именно так

- **Нет утечки горутин.** Любое место, где `run` может заблокироваться (внешний
  `select`, внутренняя отправка в `gate`), параллельно слушает `<-lb.stop`.
  После `Stop()` горутина гарантированно выходит. Проверяется goroutine-профилем
  или `goleak` (см. [утечки и гонки](/book/leaks-and-races)).
- **Нет гонок.** Всё общение между вызывающими и метрономом идёт через каналы —
  передача через канал создаёт happens-before, разделяемой памяти под мьютексом
  нет. `-race` чист.
- **Сглаживание гарантировано.** Небуферизованный `gate` + «один пропуск на тик»
  означают, что N запросов завершатся не раньше, чем за ~`(N-1)*interval`. Тест и
  проверяет нижнюю границу `>=70ms` для 10 запросов по 10мс.

## Альтернативы и их минусы

- **`time.Sleep(interval)` в каждом `Acquire`.** Кажется проще, но это не очередь:
  10 горутин, заснувших одновременно, проснутся почти одновременно — всплеск не
  сгладится. Нужна именно сериализация через общие ворота.
- **Мьютекс + «время следующего пропуска».** `Acquire` под мьютексом считает
  `next = max(now, next) + interval` и спит до `next`. Работает и без фоновой
  горутины (это, по сути, leaky bucket «по часам»), но нужно аккуратно спать вне
  критической секции, иначе сериализуешь сами `Sleep`'ы.
- **`golang.org/x/time/rate` с burst=1.** `rate.NewLimiter(rate.Every(interval),
  1)` + `lim.Wait(ctx)` даёт эквивалентное поведение и поддерживает отмену через
  контекст — в проде берут его.

## Сложность и поведение под нагрузкой

Память — O(1): одна горутина, два канала, один тикер независимо от числа
ожидающих. Очередь ожидающих живёт в самом рантайме каналов (список
заблокированных получателей `gate`). Пропускная способность жёстко ограничена
`1/interval` — это и есть цель. Порядок выпуска для небуферизованного канала
рантаймом не гарантируется строго FIFO, но «по одному за тик» соблюдается всегда.

## Что спросит интервьюер дальше

- **«Как добавить отмену ожидания по контексту?»** `Acquire(ctx)` делает
  `select { case <-lb.gate: case <-ctx.Done(): return ctx.Err() }`.
- **«Что если `Stop()` позвать дважды?»** Текущий код паникует на повторном
  `close`. Защита — обернуть в `sync.Once`.
- **«Чем это отличается от token bucket (задача 16)?»** Token bucket разрешает
  burst и не блокирует; leaky bucket выравнивает поток и заставляет ждать.
- **«Порядок выпуска FIFO?»** Не гарантирован для простого канала; для строгого
  FIFO нужна явная очередь тикетов.
- **«Что будет с памятью, если 100k горутин позовут `Acquire`?»** Все встанут в
  список ожидающих канала — это дёшево по памяти, но они реально заблокированы;
  обычно перед лимитером ставят тайм-аут/контекст.

## В проде

Leaky bucket встречается в API gateway и прокси (nginx `limit_req` — это leaky
bucket), в клиентах к строго rate-limited сервисам и в очередях на запись.
В Go-коде его роль чаще играет `golang.org/x/time/rate` с малым burst. Паттерн
«фоновый метроном + небуферизованные ворота + stop-канал» — это переиспользуемый
шаблон любого периодического воркера с graceful shutdown.
