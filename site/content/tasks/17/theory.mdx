## Зачем это на собесе

Leaky bucket — второй классический ограничитель. В отличие от token bucket он не
говорит «можно/нельзя», а **выстраивает запросы в очередь** и выпускает их строго
по одному раз в `interval`. Любой всплеск превращается в ровный поток. Так
защищают строго rate-limited downstream (внешний API с жёстким QPS, запись в
БД), где важно не «пропустить как можно больше», а «не превысить никогда».
Интервьюер смотрит, умеешь ли ты сериализовать конкурентных вызывающих через
канал и корректно гасить фоновую горутину без утечки.

## Что нужно знать

**Блокирующая семантика.** Здесь `Acquire()` *ждёт* своей очереди, а не
возвращает `false`. Это меняет дизайн: нужна точка рандеву между «воротами»,
которые открываются по таймеру, и горутинами, стоящими в очереди.

**`time.Ticker` как метроном.** Тикер шлёт в свой канал значение раз в `interval`
(см. [select](/book/select)). На каждый тик мы «выпускаем» ровно одного
ожидающего.

**Ненулевой канал как точка сериализации.** Если сделать `gate chan struct{}`
*без буфера*, то отправка `gate <- {}` завершится только когда кто-то делает
`<-gate`. Это и есть рандеву: фоновая горутина на каждый тик пытается передать
один «пропуск», а `Acquire()` его забирает:

```go
func (lb *LeakyBucket) Acquire() {
	<-lb.gate // блокируемся, пока ворота не выпустят нас
}
```

**Graceful shutdown.** Фоновая горутина живёт в `for { select {...} }`. Чтобы
она не утекла после `Stop()`, нужен сигнальный канал `stop` и ветка `case
<-stop: return` — closed-channel-as-broadcast из главы [каналы](/book/channels).

## Идиомы и паттерны

- **`done`/`stop`-канал + `close` как broadcast.** `Stop()` делает
  `close(lb.stop)`; все `select`-ветки `<-lb.stop` мгновенно разблокируются.
- **Вложенный `select` на отправке в `gate`.** Когда тик пришёл, а желающих нет,
  отправка `gate <- {}` заблокировала бы горутину навсегда. Поэтому отправку
  оборачивают во второй `select`, который слушает ещё и `stop`:
  ```go
  select {
  case lb.gate <- struct{}{}:
  case <-lb.stop:
      return
  }
  ```
- **`defer ticker.Stop()`** в фоновой горутине — освобождает таймер рантайма,
  иначе тикер продолжит тикать.

## Подводные камни

- **Утечка фоновой горутины.** Если `Stop()` не сигналит горутине, она навсегда
  останется в `select` на тикере — классическая goroutine leak (см.
  [утечки и гонки](/book/leaks-and-races)). Обнаруживается goroutine-профилем или
  `goleak`.
- **Дедлок на отправке в ворота.** Без вложенного `select` со `stop` фоновая
  горутина на тике зависнет в `gate <- {}` при пустой очереди, и `Stop()`,
  ждущий её завершения, повиснет тоже.
- **Буферизованный gate.** Если дать `gate` буфер, тики «накапливаются» и всплеск
  пройдёт залпом — сглаживание сломается. Канал должен быть **без буфера**.
- **Двойной `close(stop)`.** `Stop()`, вызванный дважды, паникует на повторном
  `close`. Если это допустимо по контракту — защищаются `sync.Once`.

## Как подступиться

1. Поля: `gate chan struct{}` (без буфера), `stop chan struct{}`. Конструктор
   создаёт каналы и запускает `go lb.run(interval)`.
2. В `run`: `ticker := time.NewTicker(interval)`, `defer ticker.Stop()`, цикл
   `for { select { case <-stop: return; case <-ticker.C: ... } }`.
3. На тике — попытка отдать пропуск: вложенный `select` на `gate <- {}` и
   `<-stop`.
4. `Acquire()` = `<-lb.gate`. `Stop()` = `close(lb.stop)`.
5. Проверь мысленно тест: 10 `Acquire` при `interval=10ms` → последний уйдёт
   примерно через `9*10ms`, все вернутся; `Stop()` не паникует и не виснет.
