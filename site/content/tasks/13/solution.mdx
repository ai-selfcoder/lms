## Идея решения

Поверх переданного `ctx` навешиваем производный контекст с жёстким таймаутом
200 мс, привязываем его к запросу через `http.NewRequestWithContext` и читаем тело.
Контекст отменится по 200 мс (или раньше, если отменили родителя), и транспорт сам
прервёт зависший запрос. `defer cancel()` и `defer resp.Body.Close()` гарантируют,
что ни таймер, ни соединение не утекут.

## Разбор эталона по шагам

Жёсткий потолок:

```go
ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
defer cancel()
```

`WithTimeout` создаёт потомка `ctx`, который отменится через 200 мс или вместе с
родителем — что раньше. Переприсваивание `ctx` (тенением) гарантирует, что дальше
используется именно ограниченный контекст. `defer cancel()` стоит сразу: он
остановит внутренний таймер и освободит узел контекста на любом пути выхода —
успех, ошибка построения, ошибка чтения. Без него таймер дожил бы до 200 мс даже
после быстрого ответа — мелкая, но реальная утечка под нагрузкой.

Построение запроса с контекстом:

```go
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
    return nil, err
}
```

Именно `...WithContext` привязывает отмену к запросу. Ошибка тут — обычно битый
URL; возвращаем как есть. Тело запроса `nil` — это GET.

Выполнение:

```go
resp, err := http.DefaultClient.Do(req)
if err != nil {
    return nil, err
}
defer resp.Body.Close()
```

`Do` блокируется до ответа или до отмены контекста. На медленном сервере через
~200 мс контекст отменится, и `Do` вернёт ошибку, обёрнутую вокруг
`context.DeadlineExceeded` — её и отдаём наверх. `defer resp.Body.Close()` ставится
**только после** проверки `err`: при ошибке `resp` может быть `nil`, и закрывать
нечего. На успешном пути закрытие тела возвращает соединение в keep-alive пул.

Чтение тела:

```go
body, err := io.ReadAll(resp.Body)
if err != nil {
    return nil, err
}
return body, nil
```

`io.ReadAll` вычитывает тело целиком. Если контекст отменится посреди чтения
(сервер отдал заголовки, но тянет тело), чтение прервётся ошибкой — функция всё
равно не зависнет. `defer` к этому моменту уже гарантирует закрытие тела.

## Почему именно так

- **Запрос реально прерывается.** Контекст привязан к транспорту, поэтому отмена
  по 200 мс рвёт соединение/чтение, а не просто «бросает» горутину. Тест с
  1-секундным сервером проверяет, что `DoRequest` возвращается заметно раньше
  (порог 800 мс) с ошибкой.
- **Нет утечек.** `defer cancel()` чистит таймер контекста; `defer
  resp.Body.Close()` — соединение. Фоновых горутин функция не создаёт.
- **Жёсткий потолок поверх ctx.** `WithTimeout` берёт минимум из 200 мс и дедлайна
  родителя — потолок не превышается ни при каком внешнем `ctx`.

## Альтернативы и их минусы

- **`http.Client{Timeout: 200ms}`.** Таймаут на весь запрос на уровне клиента.
  Проще, но: (1) не комбинируется с переданным `ctx` (его отмена игнорируется
  полем `Timeout`), (2) таймаут глобален для клиента, а не для конкретного вызова.
  Контекстный подход гибче и уважает родительскую отмену.
- **`time.AfterFunc` + ручная отмена горутины.** Можно по таймеру вернуть ошибку,
  но сам `Do` продолжит висеть в фоне — утечка горутины и соединения. Антипаттерн.
- **`context.WithDeadline`.** Эквивалент `WithTimeout`, если дедлайн считаешь сам.
  Здесь относительный таймаут удобнее.
- **Свой `http.Client` с настроенным `Transport`** (таймауты на dial, TLS, response
  header). В проде так и делают для разных фаз, но для «жёсткого общего потолка»
  контекста достаточно.

## Сложность и поведение под нагрузкой

Аллокации — стандартные для одного запроса: контекст-узел, `*http.Request`, буфер
`io.ReadAll`. Горутин функция не плодит (фоновые — внутри транспорта, они
завершаются по отмене). Под нагрузкой ключевое — `defer resp.Body.Close()`: без него
соединения не возвращаются в пул, и при росте RPS клиент упирается в лимит
коннектов. Жёсткий таймаут защищает от «эффекта домино», когда один тормозящий
апстрим выедает все горутины-обработчики.

## Что спросит интервьюер дальше

- **«Чем `WithTimeout` лучше `Client.Timeout`?»** Комбинируется с родительским
  `ctx` и задаётся per-call, а не глобально на клиента.
- **«Что вернётся при таймауте?»** Ошибка от `Do`, обёрнутая вокруг
  `context.DeadlineExceeded`; ловится `errors.Is(err, context.DeadlineExceeded)`.
- **«Почему `defer cancel()` важен даже при успехе?»** Останавливает таймер и
  освобождает узел контекста; иначе утечка до дедлайна.
- **«Где ставить `defer resp.Body.Close()`?»** Строго после проверки `err != nil`,
  иначе разыменуешь `nil`.
- **«А если сервер отдал заголовки, но тело тянет вечно?»** Контекст отменит
  чтение тела — `io.ReadAll` вернёт ошибку, зависания нет.

## В проде

Это базовая гигиена HTTP-клиента: всякий вызов апстрима оборачивают контекстом с
таймаутом, прокидывая родительский `ctx` из хендлера (где живёт дедлайн всего
запроса). Так устроены клиенты к БД, gRPC (`context` — первый аргумент каждого
вызова), вызовы между микросервисами. Жёсткий потолок поверх входящего `ctx` —
типовой приём в middleware и SDK облачных провайдеров. Связанные главы —
[context](/book/context), [утечки и гонки](/book/leaks-and-races).
