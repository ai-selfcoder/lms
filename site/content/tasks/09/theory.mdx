## Зачем это на собесе

Fan-in — это «сборщик потоков»: из нескольких независимых источников нужно
получить один поток данных. В проде так сливают воркеров, которые параллельно
тянут данные из разных партиций/шардов/реплик, а потребитель хочет читать всё
через один `range`. Интервьюер проверяет, понимаешь ли ты, кто и когда закрывает
выходной канал, и умеешь ли не оставить висящих горутин, когда входов несколько.

## Что нужно знать

Главный вопрос fan-in — **«кто закрывает выход?»**. Закрывать канал должен
отправитель, и ровно один раз. Но отправителей у нас несколько (по горутине на
вход), значит ни одна из них не может закрыть `out` сама — иначе остальные будут
писать в закрытый канал и поймают панику. Нужен арбитр, который дождётся **всех**
и закроет один раз.

Этот арбитр — [`sync.WaitGroup`](/book/sync-primitives). Он считает живых
отправителей: каждый при завершении делает `Done`, а отдельная горутина ждёт
`Wait` и закрывает выход:

```go
var wg sync.WaitGroup
wg.Add(n)
// ... n горутин, каждая defer wg.Done()
go func() { wg.Wait(); close(out) }()
```

Второе — `for v := range c` по входному каналу. Цикл сам завершится, когда вход
закроют. Так пересыльщик «доедает» источник до конца, потом умирает. Подробнее —
в главе про [каналы](/book/channels).

## Идиомы и паттерны

- **Горутина-пересыльщик на каждый вход.** Тело — `for v := range c { out <- v }`.
  Простая, читаемая, легко масштабируется на N входов.
- **`WaitGroup` + закрывающая горутина.** Каноничный способ закрыть общий выход
  «когда все доели». Это базовый кирпич [паттернов](/book/patterns) fan-in/fan-out.
- **Захват переменной цикла.** В Go до 1.22 переменную `ch` нужно передавать
  параметром в горутину (`go func(c <-chan int){...}(ch)`), иначе все горутины
  увидят последнее значение. В 1.22+ переменная цикла своя на каждой итерации, но
  явная передача параметром всё ещё читается чище.

## Подводные камни

- **`close(out)` из пересыльщика.** Если каждая горутина закроет `out` после
  своего входа, то вторая попытка — паника double-close, а ещё хуже — запись в
  уже закрытый канал. Закрывает только арбитр после `Wait`.

  ```go
  // как НЕ надо
  go func(c <-chan int) {
      for v := range c { out <- v }
      close(out) // паника, если горутин больше одной
  }(ch)
  ```

- **Неблокирующий выход и утечка.** Выход небуферизованный — пересыльщик
  блокируется на `out <- v`, пока потребитель не прочитает. Если потребитель
  бросит чтение на полпути, все пересыльщики зависнут на отправке навсегда —
  утечка горутин (см. [утечки и гонки](/book/leaks-and-races)). Контракт: читатель
  обязан вычитать выход до закрытия.

- **Краевой случай `Merge()`.** Нулей входов часто забывают. С нулём входов
  `wg.Add(0)`, `Wait` проходит мгновенно, арбитр сразу закрывает `out` — и
  `range` по нему завершается без единого значения. Проверь, что твой код это даёт.

## Как подступиться

1. Создай `out := make(chan int)`.
2. Заведи `WaitGroup`, `wg.Add(len(channels))`.
3. На каждый вход запусти горутину: `defer wg.Done()`, внутри
   `for v := range c { out <- v }`.
4. Отдельной горутиной: `wg.Wait(); close(out)`.
5. Верни `out`. Проверь мысленно `Merge()` без входов — выход должен закрыться
   сразу, и пустой `range` завершиться.

Дальше — решай в редакторе. Разбор эталона открывай после.
