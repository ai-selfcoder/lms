## Идея решения

На каждый вход — горутина-пересыльщик, перекладывающая значения в общий `out`.
`WaitGroup` считает живых пересыльщиков, а отдельная горутина закрывает `out`
ровно один раз, когда все они доели свои входы. Закрытие — из одной точки, поэтому
никаких гонок и double-close.

## Разбор эталона по шагам

Создаём выход и счётчик отправителей:

```go
out := make(chan int)

var wg sync.WaitGroup
wg.Add(len(channels))
```

`wg.Add(len(channels))` сразу проставляет число живых пересыльщиков. Важно делать
это **до** запуска горутин — иначе закрывающая горутина могла бы успеть вызвать
`Wait`, пока счётчик ещё нулевой, и закрыть `out` преждевременно. С нулём входов
`Add(0)` — счётчик ноль, `Wait` пройдёт мгновенно.

Пересыльщики:

```go
for _, ch := range channels {
    go func(c <-chan int) {
        defer wg.Done()
        for v := range c {
            out <- v
        }
    }(ch)
}
```

Канал `ch` передаётся параметром `c` — это защита от классической ловушки захвата
переменной цикла (в Go до 1.22 все горутины иначе видели бы последний `ch`).
`for v := range c` вычитывает вход до закрытия, а `defer wg.Done()` срабатывает,
когда вход закрыт и цикл завершён. Заметь: пересыльщик сам `out` **не закрывает** —
он только пишет.

Арбитр-закрыватель:

```go
go func() {
    wg.Wait()
    close(out)
}()

return out
```

Эта горутина блокируется на `Wait`, пока счётчик не дойдёт до нуля, то есть пока
**все** пересыльщики не доели свои входы. Только тогда `close(out)` — однократно,
из одной горутины. Функция возвращает `out` сразу, не дожидаясь данных: вся работа
идёт асинхронно, а потребитель читает через `range`.

## Почему именно так

- **Нет double-close.** `close(out)` вызывается ровно в одном месте и ровно один
  раз — после `Wait`. Пересыльщики только пишут.
- **Нет потери данных.** Каждый пересыльщик дочитывает свой вход до `close`, а
  закрытие выхода наступает строго после завершения всех. Значит ни одно значение
  не потеряно — тест и проверяет, что мультимножество собранного равно объединению
  входов.
- **`-race` чист.** Синхронизация только через каналы и `WaitGroup` — общей
  изменяемой памяти нет. `WaitGroup.Wait` устанавливает happens-before между
  `Done` пересыльщиков и `close`, поэтому потребитель видит все значения корректно.

## Альтернативы и их минусы

- **`select` по всем входам в одной горутине.** Можно слушать все каналы в одном
  `select`, отключая закрытые ветки переводом канала в `nil`. Работает без N
  горутин, но код заметно сложнее: нужно вручную считать живые входы и зануллять
  ветки. На произвольном N горутина-на-вход проще и идиоматичнее.
- **`reflect.Select`.** Динамический `select` по срезу каналов через рефлексию.
  Спасает, когда входы добавляются на лету, но медленный и неидиоматичный —
  на ревью почти всегда минус.
- **Буферизованный `out`.** Снизит блокировку пересыльщиков, но не отменяет
  контракт «читатель обязан вычитать»; буфер лишь сдвигает момент блокировки.

## Сложность и поведение под нагрузкой

Горутин — ровно N (по числу входов) плюс одна закрывающая; памяти — O(N). Каждое
значение проходит через выход один раз. Узкое место — небуферизованный `out`:
все пересыльщики сериализуются на нём, потребитель — единственный, поэтому реальная
пропускная способность ограничена скоростью читателя, а не числом входов. Если
нужен throughput — буферизуй выход или ставь fan-out на потреблении. Аллокаций
почти нет: один канал и горутины.

## Что спросит интервьюер дальше

- **«Кто закрывает `out` и почему не пересыльщик?»** Закрывает арбитр после
  `Wait`; пересыльщиков несколько, закрытие из любого из них — гонка и паника.
- **«Что будет, если потребитель перестанет читать?»** Пересыльщики зависнут на
  `out <- v` — утечка. Лечится `context`/`done`-каналом в `select` на отправке.
- **«Как добавить отмену?»** Прокинуть `ctx` и в пересыльщике делать
  `select { case out <- v: case <-ctx.Done(): return }`.
- **«Сохраняется ли порядок?»** Нет — значения чередуются недетерминированно.
  Порядок внутри одного входа сохраняется, между входами — нет.
- **«А `Merge()` без входов?»** `Add(0)`, мгновенный `Wait`, сразу закрытый
  пустой выход.

## В проде

Fan-in — фундамент [паттернов](/book/patterns) конвейеров: так сливают выходы
worker pool в один поток результатов, агрегируют события из нескольких партиций
Kafka, объединяют стримы. Тот же приём «`WaitGroup` + закрывающая горутина»
встречается в стадиях конвейера (задача 11) и в сборе результатов параллельных
запросов. В стандартной библиотеке родственная логика — в `errgroup`, где `Wait`
тоже синхронизирует завершение группы горутин.
