## Идея решения

Заменяем конкурентный `append` в общий слайс на **запись по индексу в
предвыделённый слайс**: каждый воркер пишет результат в свою ячейку
`results[index]`. Разные индексы — разные ячейки, пересечений нет, синхронизация
на результате не нужна вовсе. Кеш остаётся под мьютексом. Мультимножество с
порядком (повторы id → повторы в ответе) сохраняется автоматически.

## Что было сломано (starter.go)

```go
var results []UserProfile
...
for id := range ids {
	p := uf.getProfile(id)
	results = append(results, p) // БАГ: конкурентный append из 5 воркеров
}
```

Единственный, но серьёзный баг: пять воркеров одновременно делают `append` в
общий `results`. `append` читает `len`/`cap`, пишет в массив и обновляет `len` —
без синхронизации это:

- **data race** на заголовке слайса и на массиве (под `-race` — «write at /
  previous write at»);
- **логическая потеря записей**: два воркера прочитали один `len`, оба записали в
  одну ячейку, один результат пропал; при росте массива копии и вовсе расходятся.

Кеш (`getProfile`) в starter'е уже корректен — под мьютексом с double-check;
основной баг именно в сборке результата.

## Разбор эталона по шагам

Структура кеша (без изменений — она была верна):

```go
type UserFetcher struct {
	cache map[int]UserProfile
	mu    sync.Mutex
}

func (uf *UserFetcher) getProfile(id int) UserProfile {
	uf.mu.Lock()
	if p, ok := uf.cache[id]; ok {
		uf.mu.Unlock()
		return p
	}
	uf.mu.Unlock()

	p := uf.fetchFromRemoteAPI(id) // медленный вызов вне мьютекса

	uf.mu.Lock()
	uf.cache[id] = p
	uf.mu.Unlock()
	return p
}
```

Кеш под мьютексом, причём медленный `fetchFromRemoteAPI` зовётся *вне* лока —
иначе все воркеры сериализовались бы на одном мьютексе. (Цена: при гонке двух
промахов по одному id оба сходят в API — для строгой дедупликации был бы нужен
singleflight из задачи 18, но контракт этого не требует.)

Передача позиции вместе с id:

```go
type job struct {
	index int
	id    int
}
```

Чтобы воркер знал, *куда* писать, он получает `index` — позицию id в исходном
запросе.

Предвыделённый результат и пул воркеров:

```go
func (uf *UserFetcher) FetchUsersData(userIDs []int) []UserProfile {
	const workers = 5

	results := make([]UserProfile, len(userIDs)) // длина фиксирована заранее
	jobs := make(chan job)

	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs {
				results[j.index] = uf.getProfile(j.id) // запись в свой индекс
			}
		}()
	}

	for i, id := range userIDs {
		jobs <- job{index: i, id: id}
	}
	close(jobs)

	wg.Wait()
	return results
}
```

Почему это устраняет гонку:

- **`results := make([]UserProfile, len(userIDs))`** — длина и массив выделены
  *до* запуска воркеров. Заголовок слайса больше не меняется (`append` нет), поэтому
  его никто не пишет конкурентно.
- **`results[j.index] = ...`** — каждый воркер пишет в *свою* ячейку. Индексы
  уникальны (по позиции в запросе), значит две горутины никогда не пишут в один и
  тот же адрес. Без мьютекса, без канала результатов — zero-contention сборка.
- **`for j := range jobs` + `close(jobs)` + `wg.Wait()`** — фиксированный пул из 5
  воркеров (ограниченный параллелизм), корректное завершение: закрытие `jobs`
  останавливает циклы, `Wait` дожидается всех записей перед `return`.

`wg.Wait()` до `return` даёт happens-before между всеми записями `results[i]` и
финальным чтением слайса — поэтому возврат безопасен.

## Почему именно так

- **Гонки на результате нет.** Разные индексы — непересекающиеся адреса; заголовок
  слайса не мутируется. `-race` чист (см.
  [модель памяти](/book/memory-model)).
- **Полнота и порядок.** Ровно `len(userIDs)` ячеек, по одной на каждый
  запрошенный id (включая повторы); позиция сохраняется. Тест проверяет
  мультимножество `id → count` и корректные имена.
- **Кеш потокобезопасен.** Доступ к map — под мьютексом, паники «concurrent map
  write» нет.

## Альтернативы и их минусы

- **Мьютекс вокруг `append`.** `mu.Lock(); results = append(results, p);
  mu.Unlock()`. Корректно убирает гонку, но сериализует воркеров на сборке и
  **теряет порядок** — для контракта «по одному на каждый id в порядке запроса»
  пришлось бы возвращать пару `{index, profile}` и сортировать. Запись по индексу
  проще и быстрее.
- **Канал результатов.** Воркеры шлют `job{index, profile}` в `out`, отдельный
  сборщик раскладывает по `results[index]`. Чисто, но это лишний канал и ещё одна
  горутина — оверкилл, когда длина известна заранее.
- **Горутина на каждый id.** Убирает пул, но при больших входах — тысячи горутин и
  неограниченный параллелизм к API. Пул из 5 воркеров ограничивает нагрузку на
  downstream.

## Сложность и поведение под нагрузкой

Время — `len(userIDs)/workers × latency` (плюс кеш-хиты мгновенны). Память —
предвыделённый слайс O(n) + кеш. Параллелизм ограничен 5 воркерами — defensive по
отношению к API. Узкое место — `fetchFromRemoteAPI`; кеш срезает повторные id.
Сборка результата по индексу не создаёт контеншена, в отличие от мьютекса на
`append`.

## Что спросит интервьюер дальше

- **«Как `-race` диагностирует append-гонку?»** Печатает конкурентные «write at»
  по адресу слайса/массива из разных воркер-горутин без happens-before.
- **«Почему запись по индексу не требует мьютекса, а append требует?»** Индексная
  запись не меняет заголовок слайса и адресует непересекающиеся ячейки; `append`
  читает/пишет общий `len` и может реаллоцировать массив.
- **«Как гарантировать ровно один вызов API на id при гонке?»** singleflight
  (задача 18) или `LoadOrStore` будущего результата в кеш.
- **«Что если число id неизвестно заранее (стрим)?»** Тогда предвыделить нельзя —
  собирают через канал результатов или мьютекс + `append`.
- **«Зачем `fetchFromRemoteAPI` вне мьютекса?»** Иначе медленный сетевой вызов
  сериализует все воркеры на кеш-мьютексе — теряется параллелизм.

## В проде

Пул воркеров с записью результата по индексу — стандартный приём для «параллельно
обработать список, сохранив соответствие вход↔выход»: батч-запросы к API,
параллельная валидация, map-фаза map-reduce. Кеш с double-check под мьютексом —
типовой клиентский кеш; при высокой конкуренции его усиливают singleflight.
Главный урок review-задачи: конкурентный `append` в общий слайс — почти всегда
баг, и у него есть несколько чистых альтернатив.
