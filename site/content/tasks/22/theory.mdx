## Зачем это на собесе

Вторая review-задача — про самую частую гонку в worker-pool коде: несколько
воркеров делают `append` в один общий слайс результатов без синхронизации. Код
компилируется и «обычно работает», но под `-race` падает, а в проде теряет и
путает записи. Интервьюер проверяет, видите ли вы, почему `append` из нескольких
горутин небезопасен, и знаете ли несколько способов собрать результат корректно.

## Что нужно знать

**Почему `append` в общий слайс — гонка.** `append` читает и пишет заголовок
слайса (ptr, len, cap), а при росте — выделяет новый массив и копирует. Две
горутины одновременно:

```go
results = append(results, p) // читают старый len, оба пишут в одну ячейку,
                             // оба обновляют len → одна запись теряется
```

Это и data race (по `results` и по массиву), и логическая потеря/перезапись
элементов. `go test -race` показывает «write at / previous write at» по адресу
слайса. См. [модель памяти](/book/memory-model) и
[утечки и гонки](/book/leaks-and-races).

**Три способа собрать результат безопасно:**

1. **Предвыделенный слайс + запись по индексу.** `results := make([]T, n)`; каждый
   воркер пишет в *свой* индекс `results[i]`. Разные индексы — разные ячейки, без
   пересечений, без синхронизации (заголовок слайса не меняется — `len`
   фиксирован).
2. **Мьютекс вокруг `append`.** Корректно, но сериализует всех воркеров на одном
   локе.
3. **Канал результатов.** Воркеры шлют в канал, отдельный сборщик делает `append`.
   Чисто, но лишний канал и горутина.

**Сохранение мультимножества с порядком.** В этой задаче повторы id в запросе
должны дать повторы в ответе, по одному на каждый запрошенный id. Запись по
индексу естественно это сохраняет: позиция `i` ↔ `userIDs[i]`.

## Идиомы и паттерны

- **`job{index, id}` через канал.** Чтобы воркер знал, в какую ячейку писать,
  передают вместе с id его позицию в исходном запросе.
- **Предвыделенный результат — zero-contention сборка.** `make([]T, len(input))`
  и запись по индексу — самый дешёвый способ: воркеры не конфликтуют вообще.
- **Worker pool на фиксированном числе горутин.** Канал задач + N воркеров +
  `WaitGroup` — ограниченный параллелизм вместо «горутина на каждый id». См.
  [паттерны](/book/patterns).
- **Потокобезопасный кеш.** Доступ к `map` кеша — под мьютексом; иначе
  concurrent map read/write паникует.

## Подводные камни

- **`append` в общий слайс из воркеров.** Главный баг starter'а. Чинится одним из
  трёх способов выше.
- **`map`-кеш без мьютекса.** Конкурентные `cache[id]` без защиты — гонка и паника
  рантайма. (В этом коде кеш уже под мьютексом — обрати внимание, что он *не*
  источник основного бага, но проверь его корректность.)
- **Захват переменной цикла.** `go func(){ use(id) }()` без передачи параметра — до
  Go 1.22 баг; в worker-pool обычно читают из канала, что проблему снимает.
- **Потеря порядка/количества.** При `append` под мьютексом порядок результата
  становится недетерминированным; если тест требует «по одному на каждый id» —
  запись по индексу надёжнее.
- **Кеш не убирает дубли вызовов API при гонке.** Если два воркера одновременно
  промахнулись по одному id, оба сходят в API. Для строгой дедупликации нужен
  singleflight (задача 18); здесь по контракту достаточно «обычно не дёргать
  дважды».

## Как подступиться

1. Найди гонку: `results = append(results, p)` из нескольких воркеров.
2. Выбери способ сборки. Самый чистый под этот контракт — **предвыделенный слайс +
   запись по индексу**: тогда не нужен ни мьютекс на результат, ни сортировка, и
   мультимножество с порядком сохраняется автоматически.
3. Передавай в воркер `index` вместе с `id` (через `job{index, id}`), пиши
   `results[index] = ...`.
4. Убедись, что кеш потокобезопасен (он уже под мьютексом — проверь логику
   double-check).
5. Проверь тест: `len(got) == len(userIDs)`, каждый id встречается ровно столько
   раз, сколько запрошен, имена корректны, `-race` чист.

Это review-задача: конкретный фикс пробуй сам. Разбор эталона — после.
