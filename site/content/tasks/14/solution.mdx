## Идея решения

Все задачи запускаются с общим `ctx`. Когда внешний код отменяет контекст,
`RunService` начинает отсчёт grace: оборачивает `wg.Wait()` в `done`-канал и через
`select` ждёт либо завершения всех задач (`nil`), либо истечения grace (ошибка
принудительного завершения). Зависшую задачу не ждём дольше grace.

## Разбор эталона по шагам

Запуск задач:

```go
var wg sync.WaitGroup
for _, task := range tasks {
    wg.Add(1)
    go func(t func(ctx context.Context)) {
        defer wg.Done()
        t(ctx)
    }(task)
}
```

Каждая задача — отдельная горутина с общим `ctx`. `wg.Add(1)` стоит до `go` —
иначе `Wait` мог бы пройти раньше, чем горутина успела зарегистрироваться. `task`
передаётся параметром `t` — защита от захвата переменной цикла (в Go до 1.22 без
этого все горутины запустили бы последнюю задачу). `defer wg.Done()` отмечает
завершение задачи, как только `t(ctx)` вернулась.

Ожидание сигнала на остановку:

```go
<-ctx.Done()
```

`RunService` блокируется здесь, пока внешний код не вызовет `cancel()`. Это
момент, с которого начинается grace. До этой строки сервис «работает» — задачи
крутятся.

Превращение `Wait` в событие:

```go
done := make(chan struct{})
go func() {
    wg.Wait()
    close(done)
}()
```

`wg.Wait()` сам по себе блокирующий — на нём нельзя поставить таймаут. Поэтому
отдельная горутина ждёт завершения всех задач и закрывает `done`. Теперь «все
задачи доделали» — это селектируемое событие `<-done`. Та же идиома, что закрывает
выход в fan-in.

Гонка «успели vs grace»:

```go
select {
case <-done:
    return nil
case <-time.After(grace):
    return errors.New("принудительное завершение: задачи не уложились в grace")
}
```

`select` выбирает первое наступившее:

- `<-done` — все задачи завершились в пределах grace → graceful, `return nil`. Тест
  `TestRunServiceGraceful` отменяет `ctx`, все три задачи видят `ctx.Done()`,
  завершаются, `done` закрывается раньше grace.
- `<-time.After(grace)` — grace истёк, а кто-то ещё жив (зависшая задача) →
  принудительное завершение, возвращаем ошибку. Тест `TestRunServiceForced` даёт
  задачу `time.Sleep(2s)`, игнорирующую `ctx`; при grace 300 мс `select` выбирает
  таймаут, и `RunService` возвращается, **не дожидаясь** застрявшей задачи.

Важно: `time.After(grace)` создаётся **после** `<-ctx.Done()`, поэтому grace
отсчитывается от момента отмены, а не от старта сервиса.

## Почему именно так

- **Древовидная отмена.** Один `ctx` на всех — отмена доходит до каждой задачи
  одновременно через закрытие `ctx.Done()`.
- **Не зависаем на застрявшей задаче.** `select` против `time.After` гарантирует
  возврат не позже grace. Это сознательный компромис: убить горутину извне нельзя,
  поэтому застрявшая задача «утекает», но сервис всё равно останавливается.
- **`nil`/`error` различают исходы.** Тесты явно проверяют оба пути: `nil` при
  успешном graceful и ошибку при форсе.
- **`-race` чист.** Общее состояние — только `WaitGroup` и каналы; `wg.Wait()`
  устанавливает happens-before между `Done` задач и `close(done)`.

## Альтернативы и их минусы

- **`wg.Wait()` напрямую без grace.** Проще, но фатально: одна зависшая задача
  блокирует shutdown навсегда. В проде это «pod не завершается, k8s бьёт SIGKILL».
- **Производный `context.WithTimeout(ctx, grace)` для ожидания.** Можно дождаться
  `<-graceCtx.Done()` вместо `time.After`. Эквивалентно, но `time.After` тут проще
  и не требует второго `cancel`.
- **Канал завершения на каждую задачу + ручной подсчёт.** Больше кода, чем
  `WaitGroup`; легче ошибиться в счётчике. `WaitGroup` идиоматичнее.
- **`errgroup` с контекстом.** Удобно, когда задачи возвращают ошибки и нужна
  отмена по первой. Здесь задачи `func(ctx)` без возврата — `WaitGroup` достаточно.

## Сложность и поведение под нагрузкой

Горутин — `N` задач плюс одна закрывающая `done`; память O(N). Накладные расходы
ничтожны: один `WaitGroup`, один канал, один таймер. Время остановки ограничено
сверху ровно `grace` — детерминированный потолок, что критично для оркестраторов
(k8s `terminationGracePeriodSeconds`). Под нагрузкой важно, чтобы задачи реально
слушали `ctx.Done()` — иначе каждый shutdown стоит полный grace и оставляет
утёкшие горутины.

## Что спросит интервьюер дальше

- **«Почему нельзя просто `wg.Wait()`?»** Зависшая задача заблокирует навсегда;
  нужен потолок по grace.
- **«Что происходит с застрявшей горутиной после форса?»** Она продолжает жить —
  утечка. Убить горутину извне в Go нельзя; задача обязана сама слушать `ctx`.
- **«Откуда берётся сигнал отмены в реальном сервисе?»** `signal.NotifyContext` на
  SIGTERM/SIGINT — отменяет `ctx` по сигналу ОС.
- **«Как сделать grace производным контекстом?»**
  `gctx, _ := context.WithTimeout(context.Background(), grace)` и ждать
  `<-gctx.Done()` вместо `time.After`.
- **«Что если grace = 0?»** `time.After(0)` сработает почти сразу — фактически
  «без grace», вернётся ошибка, если задачи не успели мгновенно.

## В проде

Это скелет graceful shutdown HTTP-сервера и фоновых воркеров: `http.Server.Shutdown`
изнутри устроен похоже — перестаёт принимать новые соединения и ждёт активные до
дедлайна контекста. В связке с `signal.NotifyContext` (отмена по SIGTERM) и
`errgroup` это стандартный паттерн `main` любого Go-сервиса. Kubernetes даёт поду
`terminationGracePeriodSeconds` — ровно тот же grace на уровне оркестратора.
