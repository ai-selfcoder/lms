## Зачем это на собесе

Не все задачи равны: оплата важнее аналитики, healthcheck важнее фоновой
переиндексации. Приоритетный пул всегда берёт в работу самую важную из доступных
задач, а `Submit` при этом не должен подвешивать вызывающего. Интервьюер
проверяет связку, которую многие знают по отдельности, но редко собирают вместе:
`container/heap` для упорядочивания + `sync.Cond` для блокировки воркеров на
пустой очереди без busy-wait. Это прямой аналог планировщиков задач и очередей с
QoS.

## Что нужно знать

**`container/heap`** даёт двоичную кучу за O(log n) на вставку и извлечение. Ты
реализуешь интерфейс `heap.Interface` (`Len/Less/Swap` + `Push/Pop`), а пакет
делает sift-up/sift-down (см. [паттерны](/book/patterns)):

```go
func (h taskHeap) Less(i, j int) bool {
    return h[i].Priority > h[j].Priority // больший приоритет — «меньше», т.е. раньше
}
```

**`sync.Cond`** — переменная условия поверх мьютекса. Воркер засыпает на
`cond.Wait()`, когда очередь пуста, и просыпается, когда `Submit` сделает
`Signal`. Это то место, где `sync.Cond` уместнее канала (см.
[sync](/book/sync-primitives)):

```go
for queue.empty() && !stopped {
    cond.Wait()   // атомарно отпускает mu и засыпает; при пробуждении снова берёт mu
}
```

Ключевая дисциплина `Cond`: ждать **всегда в цикле** по предикату, потому что
пробуждение может быть «ложным» или состояние могло измениться, пока воркер
просыпался.

## Идиомы и паттерны

- **heap под мьютексом.** Куча не потокобезопасна; весь доступ (`Push`/`Pop`) —
  под `p.mu`, тем же, на котором построен `Cond` (`sync.NewCond(&p.mu)`).
- **`seq` для FIFO при равном приоритете.** Куча не стабильна. Монотонный
  счётчик-tiebreaker в `Less` даёт предсказуемый порядок «равные — по времени
  прихода».
- **`Signal` на Submit, `Broadcast` на Stop.** Одна новая задача будит одного
  воркера (`Signal`); остановка должна разбудить **всех** ждущих, чтобы они
  увидели `stopped` и вышли (`Broadcast`).
- **Неблокирующий `Submit`.** Очередь — это куча в памяти, а не канал
  фиксированного размера: `Submit` просто кладёт элемент и сигналит, никогда не
  блокируясь.

## Подводные камни

- **`if` вместо `for` вокруг `Wait`.** `if queue.empty() { cond.Wait() }` —
  баг: после ложного пробуждения или гонки воркер дёрнет `Pop` из пустой кучи и
  упадёт. Только `for`.
- **`Signal`, а не `Broadcast`, на остановке.** Если на Stop разбудить лишь
  одного, остальные ждущие воркеры зависнут навсегда — утечка. На остановке —
  `Broadcast`.
- **Работа задачи под мьютексом.** Если вызвать `task.Run()`, не отпустив `mu`,
  пул сериализуется в один поток и `Submit` встанет. `Pop` под мьютексом —
  `Unlock` — потом `Run()`.
- **Гонка на куче.** `heap.Push`/`heap.Pop` без мьютекса — дата-рейс на срезе.
  Под `-race` падает сразу.
- **Потеря пробуждения.** Если сигналить **до** того, как положили задачу, воркер
  проснётся, увидит пустую очередь и снова уснёт; следующая задача уже не
  разбудит «занятого» — порядок «положили → Signal» обязателен.

## Как подступиться

1. Реализуй `heap.Interface` на срезе `pqItem{task, seq}`; в `Less` — приоритет по
   убыванию, при равенстве — меньший `seq`.
2. В пуле: `mu`, `cond = sync.NewCond(&mu)`, `pq`, `seq`, `stopped`, `wg`.
3. `Submit`: под `mu` проверь `stopped`, `heap.Push`, `seq++`, `Unlock`,
   `cond.Signal()`.
4. Воркер: под `mu` цикл `for pq.Len()==0 && !stopped { cond.Wait() }`; если пусто
   и stopped — выйти; иначе `heap.Pop`, `Unlock`, выполнить `Run()`.
5. `Stop`: под `mu` `stopped = true`, `Unlock`, `cond.Broadcast()`, `wg.Wait()`.

Дальше — реализуй сам. Разбор открывай после.
