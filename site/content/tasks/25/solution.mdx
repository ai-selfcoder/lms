## Идея решения

Очередь задач — двоичная куча `container/heap`, упорядоченная по убыванию
приоритета (при равенстве — FIFO через монотонный `seq`). Доступ к куче — под
мьютексом. Воркеры спят на `sync.Cond.Wait()`, пока очередь пуста; `Submit`
кладёт задачу и будит одного воркера через `Signal`; `Stop` ставит флаг и будит
всех через `Broadcast`. `Submit` неблокирующий — куча растёт в памяти.

## Разбор эталона по шагам

Куча реализует `heap.Interface`. Главное — функция сравнения:

```go
func (h taskHeap) Less(i, j int) bool {
    if h[i].task.Priority != h[j].task.Priority {
        return h[i].task.Priority > h[j].task.Priority // больший приоритет — раньше
    }
    return h[i].seq < h[j].seq // при равенстве — кто пришёл раньше
}
```

`heap` извлекает «минимальный» по `Less` элемент. Мы инвертируем сравнение
приоритета (`>`), так что «минимум» — это максимальный приоритет. Tiebreaker по
`seq` чинит нестабильность кучи: задачи одного приоритета выходят в порядке
прихода. `Push`/`Pop` работают с хвостом среза:

```go
func (h *taskHeap) Push(x any) { *h = append(*h, x.(pqItem)) }
func (h *taskHeap) Pop() any {
    old := *h
    n := len(old)
    it := old[n-1]
    *h = old[:n-1]
    return it
}
```

`Cond` строится на том же мьютексе, что защищает кучу:

```go
p := &PriorityPool{workers: workers}
p.cond = sync.NewCond(&p.mu)
```

Это обязательное условие: `cond.Wait()` атомарно отпускает именно `p.mu`, на
котором мы держим инвариант очереди.

`Submit` — неблокирующий, кладёт и сигналит:

```go
func (p *PriorityPool) Submit(t Task) {
    p.mu.Lock()
    if p.stopped {
        p.mu.Unlock()
        return
    }
    heap.Push(&p.pq, pqItem{task: t, seq: p.seq})
    p.seq++
    p.mu.Unlock()
    p.cond.Signal()
}
```

Порядок критичен: сначала **под мьютексом** положили в кучу и увеличили `seq`,
потом отпустили `mu`, и только затем `Signal`. Так проснувшийся воркер
гарантированно увидит задачу. `Signal` после `Unlock` — лёгкая оптимизация:
разбуженный воркер сразу сможет взять мьютекс. Проверка `stopped` отбрасывает
задачи после остановки.

Сердце — воркер с цикличным `Wait`:

```go
func (p *PriorityPool) worker() {
    defer p.wg.Done()
    for {
        p.mu.Lock()
        for p.pq.Len() == 0 && !p.stopped {
            p.cond.Wait()
        }
        if p.pq.Len() == 0 && p.stopped {
            p.mu.Unlock()
            return
        }
        it := heap.Pop(&p.pq).(pqItem)
        p.mu.Unlock()

        if it.task.Run != nil {
            it.task.Run()
        }
    }
}
```

Разберём:

- **`for p.pq.Len()==0 && !p.stopped { cond.Wait() }`** — ждём строго в цикле по
  предикату. `Wait` отпускает `mu`, усыпляет горутину и при пробуждении снова
  берёт `mu`. После пробуждения предикат перепроверяется: вдруг другой воркер уже
  забрал задачу или пришёл `stopped`.
- **Выход — только когда очередь пуста И stopped.** Это и есть «дренаж»: пока в
  куче что-то есть, даже после `Stop` воркеры доделывают принятые задачи.
- **`Pop` под мьютексом, `Run()` — после `Unlock`.** Куча трогается только под
  `mu`, а сама задача выполняется без него — поэтому пул реально параллелен и
  `Submit` других не блокирует.

`Stop` будит всех и ждёт:

```go
func (p *PriorityPool) Stop() {
    p.mu.Lock()
    p.stopped = true
    p.mu.Unlock()
    p.cond.Broadcast()   // всех ждущих — иначе зависнут
    p.wg.Wait()
}
```

`Broadcast`, а не `Signal`: на остановке надо разбудить **каждого** ждущего
воркера, чтобы все увидели `stopped` и вышли. `wg.Wait()` дожидается, пока они
дренируют кучу и завершатся.

## Почему именно так

- **Корректный приоритет.** Тест держит единственного воркера занятым блокером,
  наполняет очередь смешанными приоритетами `{1,3,1,3,2}` и проверяет порядок
  выполнения `{3,3,2,1,1}`. Куча + `seq` дают именно его.
- **`Submit` неблокирующий.** Тест шлёт 1000 задач из одной горутины и требует,
  чтобы цикл завершился мгновенно — куча в памяти не упирается в ёмкость канала.
- **Нет гонок и утечек.** Куча — всегда под `mu`; пробуждения — циклом по
  предикату; на Stop — `Broadcast` + `wg.Wait()`. `-race` чист, горутины
  завершаются.

## Альтернативы и их минусы

- **Несколько каналов-«корзин» (по каналу на приоритет) + `select`.** Воркер в
  `select` сначала пробует high-канал. Проще без `Cond`, но: число приоритетов
  фиксировано, `select` равновероятен (нужны вложенные `select` с `default` —
  громоздко), а ёмкость каналов делает `Submit` потенциально блокирующим.
- **Один канал + сортировка на каждом приёме.** O(n) на выбор, не масштабируется.
- **Busy-wait вместо `Cond`.** Воркер крутит цикл с `time.Sleep` на пустой
  очереди — жжёт CPU и добавляет латентность. `Cond` спит ровно до сигнала.
- **`container/heap` обёрнутый в `Mutex`, но `Signal` через канал.** Можно, но
  `Cond` ровно для этого и существует — это идиоматичнее.

## Сложность и поведение под нагрузкой

`Submit` и взятие задачи — O(log n) на операции с кучей под коротким мьютексом.
Память — O(числа ожидающих задач): неблокирующий `Submit` — это потенциально
неограниченный рост очереди, за которым в проде надо следить. Контеншн
сосредоточен на `p.mu`, но держится он лишь на push/pop, а не на выполнение
задачи, поэтому при тяжёлых `Run()` пул хорошо параллелится. `Cond` устраняет
busy-wait: простаивающие воркеры спят, не нагружая CPU.

## Что спросит интервьюер дальше

- **«Почему `Wait` в `for`, а не в `if`?»** Из-за ложных пробуждений и гонок:
  пока воркер просыпался, очередь могли опустошить. Предикат надо перепроверять.
- **«Зачем `seq`, ведь куча и так упорядочена?»** Куча не стабильна — без
  tiebreaker задачи равного приоритета выходят в произвольном порядке. `seq` даёт
  FIFO.
- **`Signal` vs `Broadcast`?** `Signal` будит одного (хватает на одну новую
  задачу), `Broadcast` — всех (нужно на остановке, чтобы никто не завис).
- **«Как ограничить рост очереди?»** Сделать `Submit` с backpressure (вернуть
  ошибку/false при переполнении) или ограничить ёмкость — но тогда он перестанет
  быть строго неблокирующим.
- **«Можно ли без `Cond`, на голых каналах?»** Можно через приоритетные каналы и
  `select`, но динамический набор приоритетов и неблокирующий submit там делать
  неудобно.

## В проде

Приоритетные очереди с `Cond`/`heap` — основа планировщиков: очереди задач с QoS,
шедулеры в БД, приоритизация в брокерах сообщений. Сам `container/heap`
используют в `time` (таймеры рантайма — это куча по дедлайнам) и в реализациях
Дейкстры/A\*. `sync.Cond` встречается реже каналов, но именно он канонично решает
«разбудить ждущих при изменении общего состояния» — см.
[sync](/book/sync-primitives) и [паттерны](/book/patterns).
