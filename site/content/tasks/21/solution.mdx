## Идея решения

Передаём буфер во владение **единственной фоновой горутине**: `AddMetric` лишь
шлёт метрику в канал, а горутина накапливает её в локальном `buffer`, который
больше никто не трогает — гонка на буфере исчезает по построению. Flush копирует
батч в свежий слайс (нет aliasing). `Stop()` закрывает канал и ждёт, пока горутина
досбросит остаток и завершится — нет утечки и нет потерь.

## Что было сломано (starter.go)

```go
type MetricsAggregator struct {
	buffer []Metric   // трогают и run, и (через aliasing) Save
	ch     chan Metric
	db     *ClickHouseClient
}

case m := <-ma.ch:
	ma.buffer = append(ma.buffer, m)
	if len(ma.buffer) >= flushSize {
		go ma.db.Save(ma.buffer)   // БАГ 1: отдали слайс в горутину...
		ma.buffer = ma.buffer[:0]  // ...и тут же переиспользуем тот же массив
	}
case <-ticker.C:
	if len(ma.buffer) > 0 {
		go ma.db.Save(ma.buffer)   // та же беда + неупорядоченные горутины
		ma.buffer = ma.buffer[:0]
	}

func (ma *MetricsAggregator) Stop() {
	// БАГ 2: пусто — горутина утекает, остаток буфера теряется
}
```

Три класса багов:

1. **Aliasing слайса.** `go Save(ma.buffer)` и сразу `ma.buffer = ma.buffer[:0]`
   с последующим `append` — горутина `Save` читает тот самый массив, который
   агрегатор перезаписывает. Data race + повреждённые/потерянные данные.
2. **Неупорядоченные `go Save`.** Каждый flush — новая горутина; flush по таймеру
   и по размеру конкурируют, итоговый счёт «ровно N» становится недостижим, плюс
   нет гарантии, что все `Save` успели до проверки.
3. **Утечка горутины + потеря остатка.** `Stop()` ничего не делает: фоновая
   горутина живёт вечно, а последние < `flushSize` метрик никогда не сбрасываются.

## Разбор эталона по шагам

Структура: буфер ушёл из полей внутрь горутины, добавлен `done`:

```go
type MetricsAggregator struct {
	ch   chan Metric
	db   *ClickHouseClient
	done chan struct{}
}
```

Буфер теперь — **локальная переменная** фоновой горутины, недоступная снаружи.
Это и есть «single-writer»: раз к буферу обращается только одна горутина,
синхронизация не нужна вовсе.

Фоновый цикл с безопасным flush:

```go
func (ma *MetricsAggregator) run() {
	defer close(ma.done)

	ticker := time.NewTicker(5 * time.Millisecond)
	defer ticker.Stop()

	var buffer []Metric

	flush := func() {
		if len(buffer) == 0 {
			return
		}
		batch := make([]Metric, len(buffer)) // свежий массив
		copy(batch, buffer)
		ma.db.Save(batch)                    // Save владеет своей копией
		buffer = buffer[:0]                  // переиспользуем буфер безопасно
	}

	for {
		select {
		case m, ok := <-ma.ch:
			if !ok {              // канал закрыт в Stop() → досбросить и выйти
				flush()
				return
			}
			buffer = append(buffer, m)
			if len(buffer) >= flushSize {
				flush()
			}
		case <-ticker.C:
			flush()
		}
	}
}
```

Что чинит каждый приём:

- **`batch := make(...); copy(...)`** — устраняет aliasing (БАГ 1). `Save` получает
  собственный массив; `buffer = buffer[:0]` теперь безопасен — мы переиспользуем
  *свой* массив, а `Save` смотрит в копию.
- **`flush()` синхронный, из той же горутины** — устраняет неупорядоченные `go
  Save` (БАГ 2). Flush по таймеру и по размеру вызывают одну и ту же функцию
  последовательно; данные не пересекаются и не дублируются. Здесь даже `copy`
  избыточен для корректности (вызов синхронный), но оставлен как защита: батч
  уходит наружу, и владение им однозначно отделено.
- **`case m, ok := <-ma.ch; if !ok { flush(); return }`** + **`defer
  close(ma.done)`** — устраняет утечку и потерю остатка (БАГ 3).

Публичные методы:

```go
func (ma *MetricsAggregator) AddMetric(m Metric) {
	ma.ch <- m
}

func (ma *MetricsAggregator) Stop() {
	close(ma.ch)   // сигнал «данных больше не будет»
	<-ma.done      // ждём, пока горутина досбросит остаток и выйдет
}
```

`Stop()` закрывает входной канал — горутина видит `ok == false`, делает финальный
`flush()` и закрывает `done` через `defer`. `Stop()` блокируется на `<-ma.done`,
пока всё не сохранится. Рандеву без гонки.

## Почему именно так

- **Гонки нет: single-writer.** Буфер — локальная переменная одной горутины;
  никто извне его не видит. Метрики приходят через канал (канал даёт
  happens-before, см. [модель памяти](/book/memory-model)). `-race` чист.
- **Aliasing исключён.** Наружу уходит копия (`batch`), а буфер переиспользуется
  только внутри. Даже если потом сделать `Save` асинхронным — копия уже своя.
- **Утечки нет.** `Stop()` детерминированно завершает горутину и дожидается её
  через `done` — проверяемо `goleak` (см. [утечки и гонки](/book/leaks-and-races)).
- **Счёт точный.** Каждая метрика проходит через канал ровно один раз и сохраняется
  в одном `Save`; финальный flush ловит остаток. Тест видит `Total() == N` и
  `Count(name) == 1`.

## Альтернативы и их минусы

- **Мьютекс на `buffer` вместо канала.** `AddMetric` под `mu` делает `append`;
  фоновая горутина под `mu` забирает батч. Работает, но flush обязан отдавать
  *копию* (иначе aliasing остаётся), и легко передержать мьютекс на время `Save`.
  Канал-подход чище: владение буфером не размазано.
- **Асинхронный `go Save(batch)` с копией.** Если `Save` медленный, можно вынести
  его в горутину — но тогда `Stop()` должен дождаться *всех* таких горутин
  (`sync.WaitGroup`), иначе снова потеря. Усложнение ради сомнительного выигрыша.
- **`AddMetric` с буфером без канала и фоновой горутиной по таймеру.** Возвращает
  все проблемы starter'а — общий `buffer` под конкурентным доступом.

## Сложность и поведение под нагрузкой

`AddMetric` — O(1) отправка в канал (ёмкость 1024 сглаживает всплески). Flush —
O(batch). Память — буфер + одна копия на flush. Под высокой нагрузкой узкое место —
`Save`; если он медленный, канал заполнится и `AddMetric` начнёт блокироваться
(backpressure — это нормально, защищает от OOM). Хотите не блокировать —
увеличивают буфер или роняют метрики через `select { default: }`.

## Что спросит интервьюер дальше

- **«Как `-race` показывает этот баг?»** Печатает «write at buffer[i]» из
  агрегатора и «read at buffer[i]» из `Save` с разными горутинами и без
  happens-before между ними.
- **«Что если `AddMetric` позвать после `Stop()`?»** Отправка в закрытый канал —
  паника. По контракту это запрещено; при необходимости защищаются флагом/`Once`.
- **«Зачем `copy`, если `Save` синхронный?»** Для синхронного — не обязателен, но
  это дешёвая страховка на случай, если `Save` станет асинхронным или сохранит
  ссылку на слайс.
- **«Как дождаться нескольких асинхронных Save?»** `sync.WaitGroup`: `wg.Add(1)`
  перед `go Save`, `wg.Done()` внутри, `Stop()` ждёт `wg.Wait()`.
- **«Почему single-writer лучше мьютекса?»** Нет разделяемого изменяемого
  состояния → нечему гоняться; код проще доказать корректным.

## В проде

Батч-агрегаторы метрик/логов (отправка в ClickHouse, Kafka, S3) устроены ровно
так: канал на вход, одна горутина-владелец буфера, flush по размеру/таймеру,
graceful shutdown с досбросом. Паттерн «single-writer + канал + done» — основа
надёжных фоновых воркеров; именно его проверяют этой review-задачей.
