## Идея решения

Слушаем все входные каналы одним рекурсивным `select` и закрываем общий выходной
канал на первом же событии. Рекурсия сворачивает «хвост» каналов в ещё один `or`,
а чтобы вложенные горутины не утекли, в каждый вложенный вызов добавляется сам
выходной канал — его закрытие каскадом будит всё дерево.

## Разбор эталона по шагам

Сначала — вырожденные случаи без единой горутины:

```go
switch len(channels) {
case 0:
	return nil          // нечего ждать
case 1:
	return channels[0]  // один источник и есть результат
}
```

Это не только оптимизация: `or()` обязан вернуть валидное значение (`nil`-канал
блокирует навсегда — корректное «никогда не сработает»), а `or(c)` не должен
плодить лишнюю горутину.

Дальше — выходной канал и горутина, которая закроет его ровно один раз:

```go
orDone := make(chan interface{})
go func() {
	defer close(orDone) // закрытие случится при выходе из select
	...
}()
return orDone
```

`defer close(orDone)` — ключевой приём: как только `select` ниже разблокируется
(сработал любой вход), горутина выходит и закрывает `orDone`. Закрытие — из одной
горутины и однократно, поэтому никакой паники double-close.

Сердце — `select` с рекурсией по хвосту:

```go
switch len(channels) {
case 2:
	select {
	case <-channels[0]:
	case <-channels[1]:
	}
default:
	select {
	case <-channels[0]:
	case <-channels[1]:
	case <-channels[2]:
	case <-or(append(channels[3:], orDone)...):
	}
}
```

Случай `2` — база рекурсии. В `default` мы слушаем первые три канала напрямую, а
все остальные сворачиваем рекурсивным `or(channels[3:]…)`. И вот главная деталь:
в хвост добавлен **`orDone`**. Зачем? Когда сработал, скажем, `channels[0]`,
верхняя горутина закрывает `orDone`. Вложенный `or`, который сейчас висит в своём
`select`, слушает в том числе `orDone` — он просыпается, закрывает свой канал,
его родитель тоже просыпается, и так до листьев. Без этой добавки нижние горутины
дерева остались бы висеть навсегда — классическая утечка.

## Почему именно так

- **Нет утечки.** Любое срабатывание распространяется вниз по дереву через
  `orDone`, поэтому каждая запущенная горутина гарантированно завершится. Тест
  это и проверяет, замеряя, что выход закрылся «по самому быстрому» каналу.
- **Именно закрытие, а не значение.** Выход закрывается (`close`), поэтому
  повторные чтения тоже не блокируют — сигнал «виден» навсегда. Тест читает из
  выхода дважды, проверяя `ok == false`.

## Альтернативы и их минусы

- **Горутина на каждый канал + общий `done`.** Запускаем `len(channels)` горутин,
  каждая `select`-ит свой вход и общий `done`; первый закрывает `done` через
  `sync.Once`. Работает и проще читается, но создаёт N горутин сразу
  (рекурсивный вариант — тоже ~N, но «лесенкой»). На собесе именно рекурсивный
  `or` считается «каноном» из книги *Concurrency in Go*.
- **`reflect.Select`.** Один `select` по динамическому набору каналов через
  рефлексию. Избавляет от рекурсии, но медленный и неидиоматичный — почти всегда
  минус на ревью.

## Сложность и поведение под нагрузкой

Горутин и каналов — порядка O(N) от числа входов, памяти столько же. После
срабатывания всё схлопывается за O(глубины дерева). Аллокации — по одному каналу
на уровень; для типичных «несколько источников отмены» это копейки. `or` —
одноразовый: сработал и умер, долгоживущего состояния нет.

## Что спросит интервьюер дальше

- **«А если канал не закрывают, а шлют значение?»** Тоже сработает: `select`
  разблокируется и на получении значения. Но выход мы всё равно *закрываем* —
  это сигнал, а не передача данных.
- **«Как сделать то же через `context`?»** `context.WithCancel` + горутины,
  закрывающие общий `cancel`. По сути `or` — ручной аналог слияния нескольких
  `ctx.Done()`.
- **«Сколько горутин останется после срабатывания?»** Ноль — в этом вся суть
  добавления `orDone` в рекурсию.
- **«Что вернёт `or()` без аргументов и почему это безопасно?»** `nil`-канал;
  чтение из него блокируется навсегда — корректное «событие никогда не наступит».

## В проде

Это ядро отмены в Go: [context](/book/context) внутри устроен похоже —
`Done()`-каналы образуют дерево, и отмена родителя закрывает каналы детей.
Тот же паттерн «первый сигнал побеждает» лежит в основе таймаутов
(`context.WithTimeout`), graceful shutdown и гонок реплик (см. задачу 15
«First Successful»).
