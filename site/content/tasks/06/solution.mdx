## Идея решения

Обычная `map` плюс `sync.RWMutex`. Чтения берут `RLock` и идут параллельно;
записи и удаления берут эксклюзивный `Lock`. На read-heavy профиле (95% чтений)
читатели не блокируют друг друга — это и есть выигрыш против `sync.Mutex`.

## Разбор эталона по шагам

Структура и конструктор:

```go
type Cache struct {
	mu sync.RWMutex
	m  map[string]interface{}
}

func NewCache() *Cache {
	return &Cache{
		m: make(map[string]interface{}),
	}
}
```

`make` в конструкторе обязателен: запись в `nil`-map паникует. Кэш возвращается
по указателю — `sync.RWMutex` нельзя копировать после использования.

Запись — под эксклюзивным `Lock`:

```go
func (c *Cache) Set(key string, value interface{}) {
	c.mu.Lock()
	c.m[key] = value
	c.mu.Unlock()
}
```

`Lock` гарантирует, что во время записи ни один читатель и ни один другой
писатель не трогает map — иначе был бы `fatal error: concurrent map read and
map write`.

Чтение — под разделяемым `RLock`:

```go
func (c *Cache) Get(key string) (interface{}, bool) {
	c.mu.RLock()
	v, ok := c.m[key]
	c.mu.RUnlock()
	return v, ok
}
```

Несколько `Get` могут держать `RLock` одновременно — параллельные чтения не
ждут друг друга. `Lock` писателя дождётся, пока все читатели отпустят. Возвращаем
`v, ok` уже после `RUnlock` — копия значения и флага лежат на стеке, держать лок
во время `return` не нужно.

Удаление — снова `Lock`, и оно идемпотентно:

```go
func (c *Cache) Delete(key string) {
	c.mu.Lock()
	delete(c.m, key)
	c.mu.Unlock()
}
```

`delete` отсутствующего ключа — no-op, поэтому повторный `Delete` и удаление
несуществующего ключа безопасны без проверок (`TestCacheDelete` это проверяет).

## Почему именно так

- **Нет гонок и нет `fatal error`.** Любая мутация под `Lock`, любое чтение под
  `RLock`. `TestCacheConcurrent` гоняет 8 писателей и 64 читателя по 2000
  операций под `-race` — чисто.
- **Параллельные чтения.** На 95% чтений `RWMutex` пропускает читателей
  одновременно; `Mutex` сериализовал бы их в очередь.
- **Корректная семантика.** `Get` отсутствующего ключа возвращает `nil, false`
  (нулевые значения от map-lookup), перезапись обновляет значение — это берётся
  из штатного поведения map.

## Альтернативы и их минусы

- **`sync.Mutex`.** Проще, но сериализует и чтения — на read-heavy теряет
  параллелизм. Для write-heavy, наоборот, нередко *быстрее* RWMutex (у RWMutex
  выше накладные расходы на запись).
- **`sync.Map`.** Стандартная конкурентная map, оптимизирована под два сценария:
  «ключ пишется один раз, читается много» и «непересекающиеся наборы ключей у
  горутин». Без дженериков (`interface{}`), API специфичный (`Load`/`Store`).
  Для общего read-heavy кэша с произвольными перезаписями обычная map + RWMutex
  часто предсказуемее и быстрее.
- **Шардированная map (N бакетов, лок на бакет).** Снимает contention на одном
  локе при экстремальной нагрузке (как в `groupcache`, BigCache). Сложнее;
  оправдано только при доказанном узком месте.

## Сложность и поведение под нагрузкой

Каждая операция — O(1) амортизированно (map-lookup/insert/delete) плюс
захват лока. На read-heavy throughput читателей растёт почти линейно с числом
ядер. Узкое место — сам `RWMutex`: при росте доли записей `Lock` чаще
эксклюзивно останавливает всех, и преимущество испаряется — там, где записей
много, обычный `Mutex` или шардирование лучше. RWMutex также дороже на запись,
чем Mutex, из-за учёта читателей.

## Что спросит интервьюер дальше

- **«Почему `RWMutex`, а не `Mutex`?»** 95% чтений — читатели идут параллельно;
  `Mutex` сериализовал бы их.
- **«Когда `RWMutex` хуже `Mutex`?»** При высокой доле записей: накладные
  расходы выше, частые эксклюзивные `Lock` сводят выигрыш на нет.
- **«Когда взять `sync.Map`?»** «Записал раз — читаешь много» или
  непересекающиеся ключи; для произвольных перезаписей чаще лучше map+RWMutex.
- **«Почему `make` в конструкторе?»** Запись в `nil`-map паникует.
- **«Как масштабировать дальше?»** Шардирование по хешу ключа — лок на бакет,
  меньше contention.
- **«TTL/вытеснение?»** Добавить срок жизни в значение и фоновую/ленивую
  чистку — отдельная большая тема.

## В проде

map + `sync.RWMutex` — рабочая лошадка кэшей в Go-сервисах: конфиг-снапшоты,
кэши DNS/метаданных, мемоизация. `sync.Map` используется внутри стандартной
библиотеки (например, кэши `reflect`, `encoding/json`). При экстремальной
нагрузке переходят на шардированные кэши (`groupcache`, `bigcache`,
`ristretto`). Подробнее — [sync: примитивы](/book/sync-primitives).
