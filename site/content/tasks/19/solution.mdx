## Идея решения

Делим хранилище на 32 независимых шарда, каждый — отдельная `map` под своим
`sync.RWMutex`. Ключ детерминированно маршрутизируется в шард по FNV-хешу.
Операции с ключами из разных шардов идут параллельно; чтения берут `RLock` и не
мешают друг другу.

## Разбор эталона по шагам

Шард и контейнер:

```go
const shardCount = 32

type shard struct {
	mu sync.RWMutex
	m  map[string]interface{}
}

type ShardedMap struct {
	shards [shardCount]*shard
}

func NewShardedMap() *ShardedMap {
	m := &ShardedMap{}
	for i := 0; i < shardCount; i++ {
		m.shards[i] = &shard{m: make(map[string]interface{})}
	}
	return m
}
```

Каждый шард — самостоятельная единица синхронизации со своей `map`. Конструктор
обязательно инициализирует все 32 внутренних map: запись в `nil`-map паникует.

Маршрутизация ключа:

```go
func (m *ShardedMap) shardFor(key string) *shard {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return m.shards[h.Sum32()%shardCount]
}
```

FNV-1a — быстрый равномерный хеш. `% shardCount` детерминированно выбирает шард:
один ключ всегда попадает в один и тот же сегмент, поэтому данные не «теряются».

Операции записи и чтения:

```go
func (m *ShardedMap) Set(key string, value interface{}) {
	s := m.shardFor(key)
	s.mu.Lock()
	s.m[key] = value
	s.mu.Unlock()
}

func (m *ShardedMap) Get(key string) (interface{}, bool) {
	s := m.shardFor(key)
	s.mu.RLock()
	v, ok := s.m[key]
	s.mu.RUnlock()
	return v, ok
}
```

`Set`/`Delete` берут эксклюзивный `Lock`, `Get` — разделяемый `RLock`. Под
`RLock` несколько читателей одного шарда работают параллельно — это и есть выигрыш
`RWMutex` на read-heavy нагрузке. Значение возвращается уже после `RUnlock`, но
само чтение из map — строго под локом.

Подсчёт размера:

```go
func (m *ShardedMap) Len() int {
	n := 0
	for i := 0; i < shardCount; i++ {
		s := m.shards[i]
		s.mu.RLock()
		n += len(s.m)
		s.mu.RUnlock()
	}
	return n
}
```

`Len` обходит все шарды, суммируя `len` под `RLock` каждого. Это снимок «по
шардам»: глобально не атомарен (между шардами кто-то мог что-то записать), но
каждый отдельный `len` корректен и без гонки.

## Почему именно так

- **Нет гонок.** К внутренней map шарда обращаются только под его мьютексом.
  `-race` чист; не возникает и паники рантайма «concurrent map read and write»
  (см. [модель памяти](/book/memory-model)).
- **Меньше контеншена.** Две горутины конфликтуют, только если их ключи попали в
  один шард, — вероятность падает в ~32 раза против одного глобального мьютекса.
- **Корректность подтверждается тестом.** 1000 различных ключей → `Len()==1000`
  (раскиданы по шардам, но все доступны); конкурентная нагрузка из 64 воркеров
  под `-race` не находит несоответствий.

## Альтернативы и их минусы

- **Один `sync.RWMutex` на всю map.** Проще, но под нагрузкой все писатели и часть
  читателей сериализуются на одном объекте — узкое место.
- **`sync.Map`.** Стандартный потокобезопасный контейнер, оптимизирован под два
  сценария: «много чтений стабильных ключей» и «каждая горутина пишет свои
  ключи». Не требует ручного шардирования, но `interface{}`-API, нет дешёвого
  `Len`, и на «много записей в общие ключи» он *медленнее* шардированной map.
  Выбор зависит от профиля доступа — см. [sync](/book/sync-primitives).
- **Lock-free хеш-таблица.** Максимальная масштабируемость, но крайне сложна и
  ошибкоопасна; в Go почти всегда берут шардирование.

## Сложность и поведение под нагрузкой

`Get`/`Set`/`Delete` — амортизированно O(1) (хеш ключа + операция с map).
`Len` — O(shardCount). Память — N элементов плюс 32 мелких структуры.
Масштабирование: пропускная способность растёт примерно линейно с числом шардов,
пока ключи распределены равномерно и число ядер позволяет. Если шардов слишком
мало — остаётся контеншен; слишком много — растут накладные расходы и хуже
локальность кеша. 32 — разумный дефолт; на практике берут степень двойки около
числа ядер ×несколько.

## Что спросит интервьюер дальше

- **«Почему 32, а не 1000 шардов?»** Больше шардов — меньше контеншена, но больше
  памяти и хуже локальность; обычно подбирают эмпирически около `GOMAXPROCS`×k.
- **«Чем заменить `%`?»** При степени двойки — `& (shardCount-1)`, чуть быстрее.
- **«`sync.Map` vs шардирование?»** `sync.Map` хорош для read-mostly со
  стабильными ключами; шардированная map универсальнее на смешанной нагрузке.
- **«Атомарный `Len` по всей map?»** Нужен глобальный счётчик (atomic),
  инкрементируемый при `Set`/`Delete`, — но он сам станет точкой контеншена.
- **«Как сделать `Range`/итерацию?»** Обходить шарды по очереди под `RLock`;
  глобально консистентного снимка без полной блокировки всех шардов не будет.

## В проде

Шардированные map — основа кешей, метрик-агрегаторов, пулов соединений и таблиц
сессий. Похожий приём (striped locks) есть в Java `ConcurrentHashMap`. В Go
популярна библиотека `orcaman/concurrent-map` — это ровно та же идея. Понимание
этой задачи учит главному навыку highload: находить горячий мьютекс и «размазывать»
его, сохраняя корректность под `-race`.
