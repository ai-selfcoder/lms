## Зачем это на собесе

Один `sync.Mutex` на всю map — это глобальный сериализатор: под высокой нагрузкой
все горутины выстраиваются в очередь за одной блокировкой, даже если работают с
разными ключами. Шардирование разбивает map на N независимых сегментов со своими
мьютексами, и операции с разными ключами идут параллельно. Это базовый приём
проектирования lock-friendly структур, и интервьюер проверяет, понимаешь ли ты,
*откуда* берётся контеншен и как его «размазать».

## Что нужно знать

**Контеншен на мьютексе.** Когда K горутин одновременно хотят один мьютекс, K-1
из них спят. Чем «горячее» мьютекс, тем больше времени уходит на ожидание, а не
на работу. Шардирование уменьшает вероятность, что две горутины попадут в один
мьютекс, в N раз. См. [sync](/book/sync-primitives).

**`RWMutex` для read-heavy.** Если чтений сильно больше записей, `RLock()`
позволяет множеству читателей работать параллельно; писатель берёт эксклюзивный
`Lock()`. Для кеша (читаем часто, пишем редко) это заметно лучше обычного
`Mutex`.

**Детерминированный выбор шарда по хешу.** Один и тот же ключ обязан всегда
попадать в один шард, иначе данные «потеряются». Берём хеш (FNV) и `% shardCount`:

```go
h := fnv.New32a()
h.Write([]byte(key))
shard := shards[h.Sum32()%shardCount]
```

## Идиомы и паттерны

- **Массив указателей на шарды.** `[32]*shard`, каждый — `{ mu sync.RWMutex; m
  map[string]interface{} }`. Степень двойки (32) позволяет при желании заменить
  `%` на `& (shardCount-1)`.
- **`RLock` на чтение, `Lock` на запись/удаление.** Чёткое разделение: `Get`
  берёт `RLock`, `Set`/`Delete` — `Lock`.
- **`Len()` обходит все шарды.** Суммируем `len(s.m)` под `RLock` каждого шарда —
  снимок не атомарен по всей map, но по каждому шарду корректен.
- **FNV — дешёвый неблокирующий хеш.** Не криптостойкий, но равномерный и быстрый;
  для распределения по бакетам этого достаточно.

## Подводные камни

- **Забыть инициализировать внутренние map.** `make(map...)` нужно сделать для
  каждого шарда в конструкторе; запись в `nil`-map паникует.
- **Concurrent map access без блокировки.** Любой `Get`/`Set` без захвата мьютекса
  шарда — это и data race, и потенциальная паника рантайма «concurrent map
  read/write». `-race` это ловит (см. [модель памяти](/book/memory-model)).
- **Неравномерный хеш.** Плохой хеш сваливает большинство ключей в один шард —
  контеншен возвращается. FNV распределяет равномерно.
- **`Get` под `Lock` вместо `RLock`.** Не сломается, но теряется весь смысл
  `RWMutex`: читатели начнут блокировать друг друга.
- **Слишком мелкая критическая секция, утёкшая наружу.** Возвращать значение
  нужно *после* `RUnlock`, но само чтение из map — строго под локом.

## Как подступиться

1. `const shardCount = 32`; `type shard struct { mu sync.RWMutex; m
   map[string]interface{} }`; `ShardedMap{ shards [shardCount]*shard }`.
2. Конструктор: цикл `make(map...)` для каждого шарда.
3. Хелпер `shardFor(key) *shard` через FNV `% shardCount`.
4. `Set`/`Delete` — под `s.mu.Lock()`; `Get` — под `s.mu.RLock()`.
5. `Len()` — обход всех шардов, суммируем под `RLock`.
6. Проверь: 1000 разных ключей → `Len()==1000`, всё читается; тяжёлая
   конкурентная нагрузка из условия проходит под `-race`.
