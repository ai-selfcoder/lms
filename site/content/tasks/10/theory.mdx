## Зачем это на собесе

Ограниченный пул воркеров — самый частый прод-сценарий: обработать много задач,
но не более `w` одновременно, чтобы не положить базу/внешний сервис, и при первой
критической ошибке быстро всё остановить, не дорабатывая остаток впустую.
Интервьюер проверяет три вещи сразу: умеешь ли ограничить параллелизм ровно `w`,
умеешь ли отменить остальных через [context](/book/context) и не оставить ни
утечки горутин, ни гонки на общей переменной ошибки.

## Что нужно знать

Есть два способа ограничить параллелизм. Первый — **семафор на буферизованном
канале** ёмкости `w`: перед задачей пишешь токен, после — забираешь. Второй —
**фиксированный пул из `w` горутин**, читающих из общего канала задач. Эталон
идёт вторым путём, и он чаще предпочтителен: число горутин фиксировано и не растёт
с числом задач.

```go
tasks := make(chan int)
for i := 0; i < w; i++ {
    go func() { for id := range tasks { process(id) } }()
}
```

Второе — **отмена через [context](/book/context)**. Первая ошибка вызывает
`cancel()`, а воркеры в `select` слушают `ctx.Done()` и перестают брать новые
задачи. И раздатчик задач тоже должен слушать `ctx.Done()`, иначе зависнет на
`tasks <- id`, когда все воркеры уже ушли.

Третье — **первая ошибка под мьютексом**. Несколько воркеров могут упасть почти
одновременно; писать в `firstErr` нужно под `sync.Mutex` и только если он ещё
`nil`. Подробнее про мьютексы — в главе [sync](/book/sync-primitives).

## Идиомы и паттерны

- **Пул горутин на общем канале задач.** `w` воркеров, один `tasks`-канал;
  раздатчик пишет, воркеры читают. Закрытие `tasks` сигналит «задач больше нет».
- **`context.WithCancel` как «стоп-кран».** Первая ошибка дёргает `cancel()`,
  и это broadcast: все воркеры и раздатчик видят `ctx.Done()` закрытым.
- **`select` с двумя ветками в воркере** — `<-ctx.Done()` и `<-tasks`. Так
  воркер реагирует на отмену даже посреди ожидания задачи.
- **`WaitGroup` для дожидания воркеров** перед возвратом ошибки — гарантия, что
  ни одна горутина не переживёт функцию.

## Подводные камни

- **Раздатчик без `ctx.Done()`.** Если раздавать задачи просто `tasks <- id`, а
  все воркеры уже вышли по отмене, раздатчик зависнет навсегда на отправке —
  дедлок. Раздача обязана быть в `select` против `ctx.Done()`.

  ```go
  // как НЕ надо: зависнет, когда воркеры ушли по cancel
  for _, id := range orderIDs {
      tasks <- id
  }
  ```

- **Гонка на `firstErr`.** Запись без мьютекса из нескольких воркеров — data race,
  `-race` это поймает. Нужен `mu.Lock()` и проверка `if firstErr == nil`.

- **Утечка через `close(tasks)`.** Закрыть `tasks` нужно один раз после раздачи.
  Если забыть закрыть — воркеры, дочитавшие очередь, навсегда зависнут в `range`/
  `<-tasks`. Об утечках — глава [утечки и гонки](/book/leaks-and-races).

- **Превышение `w`.** Если на каждую задачу плодить новую горутину «под семафор»,
  легко промахнуться и пустить больше `w`. Тест замеряет максимум параллелизма и
  валит решение при превышении.

## Как подступиться

1. Нормализуй `w` (минимум 1). Создай `ctx, cancel := context.WithCancel(...)`,
   `defer cancel()`.
2. Заведи `tasks := make(chan int)`, `WaitGroup` на `w`, `mu` и `firstErr`.
3. Запусти `w` воркеров: в цикле `select` по `ctx.Done()` и `tasks`; на ошибке —
   под мьютексом записать `firstErr` (если пуст), вызвать `cancel()` и выйти.
4. Раздай задачи в `select` против `ctx.Done()`, затем `close(tasks)`.
5. `wg.Wait()`, верни `firstErr` под мьютексом.

Дальше — решай сам. Эталон открывай после.
