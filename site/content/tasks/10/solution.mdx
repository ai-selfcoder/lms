## Идея решения

Фиксированный пул из `w` горутин читает задачи из общего канала — это и есть
ограничение параллелизма. Первая ошибка пишется под мьютексом и дёргает
`cancel()`, после чего и воркеры, и раздатчик видят `ctx.Done()` и прекращают
работу. `WaitGroup` гарантирует, что функция не вернётся, пока живы воркеры.

## Разбор эталона по шагам

Нормализация и контекст:

```go
if w < 1 {
    w = 1
}

ctx, cancel := context.WithCancel(context.Background())
defer cancel()
```

`w < 1` чинит вырожденный ввод — без этого `for i := 0; i < w` не запустит ни
одного воркера и раздатчик зависнет. `defer cancel()` обязателен: даже на happy
path он освобождает ресурсы контекста и снимает возможные блокировки.

Общее состояние и пул:

```go
tasks := make(chan int)

var (
    mu       sync.Mutex
    firstErr error
)

var wg sync.WaitGroup
wg.Add(w)
for i := 0; i < w; i++ {
    go func() {
        defer wg.Done()
        for {
            select {
            case <-ctx.Done():
                return
            case id, ok := <-tasks:
                if !ok {
                    return
                }
                if err := process(id); err != nil {
                    mu.Lock()
                    if firstErr == nil {
                        firstErr = err
                    }
                    mu.Unlock()
                    cancel()
                    return
                }
            }
        }
    }()
}
```

Ровно `w` горутин — больше параллелизма быть не может, тест это и замеряет. Внутри
бесконечный цикл с `select` из двух веток:

- `<-ctx.Done()` — кто-то упал или раздача завершилась с отменой; воркер выходит.
- `id, ok := <-tasks` — если `ok == false`, канал закрыт, задач нет, выходим.
  Иначе обрабатываем.

Ключевая деталь — запись ошибки: `mu.Lock()`, и `firstErr` пишется **только если
он ещё `nil`**. Так фиксируется именно *первая* ошибка, даже если несколько
воркеров упали одновременно. Сразу после — `cancel()`: это стоп-кран для всех
остальных. И `return` — упавший воркер больше задач не берёт.

Раздача задач:

```go
feed:
for _, id := range orderIDs {
    select {
    case <-ctx.Done():
        break feed
    case tasks <- id:
    }
}
close(tasks)
```

Каждая отправка — в `select` против `ctx.Done()`. Это критично: если воркеры уже
ушли по отмене, никто не читает `tasks`, и простое `tasks <- id` зависло бы
навсегда. Метка `feed` и `break feed` выходят из внешнего цикла при отмене.
`close(tasks)` после — сигнал «задач больше нет» для воркеров, которые ещё живы
на happy path (они получат `ok == false`).

Финал:

```go
wg.Wait()

mu.Lock()
defer mu.Unlock()
return firstErr
```

`wg.Wait()` дожидается всех воркеров — после него гарантированно нет живых горутин
пула. Чтение `firstErr` под мьютексом — формально для happens-before, чтобы
гонок не было даже теоретически.

## Почему именно так

- **Параллелизм ровно `w`.** Горутин ровно `w`, каждая обрабатывает одну задачу
  за раз — больше `w` одновременных `process` невозможно.
- **Нет утечек.** Все выходы воркеров покрыты: `ctx.Done()`, закрытие `tasks`,
  ошибка. После `wg.Wait()` живых горутин нет. `defer cancel()` подчищает контекст.
- **Нет гонок.** Единственное общее изменяемое состояние — `firstErr`, и оно под
  `mu`. `-race` чист. Счётчики в тесте — атомики, тоже без гонок.
- **Первая ошибка, не любая.** Проверка `if firstErr == nil` под мьютексом делает
  выбор детерминированным по смыслу: возвращается первая зафиксированная ошибка.

## Альтернативы и их минусы

- **Семафор на буфер-канале.** `sem := make(chan struct{}, w)`, на каждую задачу
  своя горутина, токен в `sem` ограничивает параллелизм. Гибче (легко на задачу
  навесить разный вес), но плодит горутину на каждую задачу — при миллионе задач
  это миллион горутин против фиксированных `w`.
- **`errgroup.WithContext` + `SetLimit`.** Идиоматичный прод-вариант: группа сама
  отменяет контекст по первой ошибке и ограничивает параллелизм. В задаче явно
  просят без `golang.org/x/sync`, чтобы показать механику руками.
- **Без `context`, через `done`-канал и `sync.Once`.** Тоже отменяет всех
  закрытием канала. Работает, но `context` идиоматичнее и интегрируется с прокидом
  отмены вглубь `process`.

## Сложность и поведение под нагрузкой

Горутин — фиксированные `w + 1` (пул плюс раздатчик в той же горутине, что и
вызывающая). Память — O(w), не зависит от числа задач. Контеншн только на `mu`,
и то лишь на пути ошибки — на happy path мьютекс не трогается вообще. Узкое место —
небуферизованный `tasks`: раздатчик и воркеры рандеву-синхронизируются, что
естественно балансирует нагрузку. Под отменой остановка быстрая: `cancel()` —
broadcast, остаток задач не раздаётся.

## Что спросит интервьюер дальше

- **«Почему раздача в `select`, а не просто `tasks <- id`?»** Иначе дедлок: после
  отмены никто не читает `tasks`.
- **«Зачем мьютекс, если есть только запись?»** Записей несколько и из разных
  горутин — это data race; плюс нужна проверка «первая ли».
- **«Можно ли заменить мьютекс на канал ошибок?»** Да: буферизованный
  `errCh` размером 1 + `select` с `default`. Эквивалентно по смыслу.
- **«Что вернётся, если `process` упадёт у нескольких разом?»** Первая
  зафиксировавшая `mu` ошибка — остальные отсекаются проверкой `firstErr == nil`.
- **«Как добавить ретраи/частичные ошибки?»** Накапливать `[]error`
  (`errors.Join`) вместо остановки по первой — но тогда меняется контракт.

## В проде

Это скелет любого пула: обработка очереди заказов, рассылка, параллельные вызовы
к внешним API с ограничением RPS. В реальном коде чаще берут
`golang.org/x/sync/errgroup` с `SetLimit(w)` — он внутри устроен похоже: общий
отменяемый контекст, отмена по первой ошибке, `Wait` для синхронизации. Паттерн
«семафор на буфер-канале» — в `golang.org/x/sync/semaphore`. Связанные главы —
[паттерны](/book/patterns), [context](/book/context),
[утечки и гонки](/book/leaks-and-races).
